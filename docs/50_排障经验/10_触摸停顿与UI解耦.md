# 10_触摸 I2C 停顿与"把读搬出 UI 线程"

> 写于 2026-11-04。**触摸一按 UI 就顿一下 / `ui:responsive` 出现几百毫秒尖峰**时读这篇。

## 一句话结论

**触摸读原本跑在 LVGL 的输入定时器里（也就是 UI 线程里），而这条 I2C0 与相机 SCCB、
ES8311 共用，单次读的墙钟最坏可达 230~800ms ⇒ UI 跟着卡。
解法不是去优化 I2C，而是"换个人去等"：把读搬到独立线程，UI 只读最新样本。**

## 根因链（每一环都有实测）

1. `lv_nuttx_init()` 收到 `input_path` 就会建一个**设备 indev**，它的
   `read(/dev/input0)` 由 LVGL 的输入定时器调用 —— 也就是在
   `lv_timer_handler()`（UI 线程）里执行。
2. 这条 I2C0 上不只触摸：**相机 SCCB、ES8311 共用**（板级事实）；
   GT911 的 **INT 引脚没有引到 SoC**，只能轮询（`esp32p4_touch_gt911.c` 注释写明）。
3. 实测触摸读墙钟：**1539ms**（改 `gt9xx` 的 `devlock` trylock 前）→ **419ms** → 310ms →
   **最坏 800ms**。`ui:responsive` 的 `max_busy` 随之在 130 / 180 / 250 / **1540 ms** 之间跳。

## 两个决定性否证（别再往这两个方向使劲）

| 试过 | 结果 | 结论 |
|---|---|---|
| 把 I2C 总线锁改成**有界等待**（60ms） | 单次最大 419 → 310ms，仍会很大 | 只压住"等锁"，压不住传输本身 |
| 把系统 tick 10ms → **1ms** | 平均 16.9 → 13.6ms，最大仍 ~500ms | 不是 tick 粒度 |
| 把 I2C 超时 500ms → **50ms** | **单次最大仍是 501ms** | **那 500ms 不是超时，是线程被抢占的墙钟** |
| 把 LVGL 输入读周期 30 → 50ms | 反而更差（撞上更长的停顿） | 读得少≠停顿少 |

⇒ **触摸读的墙钟 = 极短的总线时间 + 调度延迟（被抢占）**。

## 解法：把"等"移出 UI 线程

```c
/* dm_display.c：别把设备交给 LVGL（否则 read() 会回到 UI 定时器里） */
info.input_path = NULL;

/* dm_touch.c：独立低优先级线程轮询，UI 只读快照 */
fd = open(DM_INPUT_PATH, O_RDONLY | O_NONBLOCK);
for (;;) {
    poll(&pfd, 1, 50);                 /* 带超时 */
    read(fd, &sample, sizeof(sample)); /* 非阻塞 */
    /* 写进无锁 seq 快照：g_hw_x / g_hw_y / g_hw_pressed / g_hw_seq */
}
/* LVGL indev 回调：只读快照，零阻塞（注入优先，其次硬件样本） */
```

**实测效果**：

| 指标 | 改前 | 改后 |
|---|---|---|
| `ui:responsive` 的 `max_busy` | 130 / 180 / 250 / **1540 ms** | **20 ~ 30 ms** |
| 触摸判据（自检） | PASS | **PASS** |
| 完整自检 | 29/29 | **29/29** |

关键断言：**`g_dbg_touch_i2c_us_max` 依旧可以很大，但 UI 不受影响** ——
I2C 再慢也只影响"触摸样本的新鲜度"。

## 配套诊断量（JTAG 可读）

`g_dbg_touch_i2c_us(_max)`（读总耗时）、`g_dbg_touch_xfer_calls/_us/_us_max`
（**只算 `I2C_TRANSFER`**）、`g_dbg_touch_hw_reads/_us/_us_max`（轮询线程侧）。

> 计时器要放在**确定被链接**的文件里（这里是 `nuttx/drivers/input/gt9xx.c`）——
> 详见 [08_驱动层调优与多副本陷阱.md](08_驱动层调优与多副本陷阱.md)。

## 教训

- **别让 UI 线程碰慢设备**：只要回调在 `lv_timer_handler` 里，任何慢 I/O 都会变成整屏卡顿；
  正确做法是"生产者线程 + 最新样本快照"。
- **优化前先分清"谁在等"**：本次三个看似合理的优化方向（锁、tick、超时）全部无效，
  真正的答案是改变等待发生的位置。

## 附：改了之后"触摸没反应"怎么查（本项目的实战顺序）

1. **先分清是"屏幕冻住"还是"触摸坏"**：读驱动维护的 `g_disp_commits` 是否增长。
   冻住是相机抢带宽（见 [09_显示卡死复盘.md](09_显示卡死复盘.md)），不是触摸问题。
2. **看轮询线程的计数**：`g_dbg_touch_hw_reads / _ok / _err / _hits`。
   - `reads` 不涨 ⇒ 线程没起来；
   - `err` 涨 ⇒ read 被驱动拒（长度/缓冲不匹配，按 LVGL 做法用
     `ioctl(TSIOC_GETMAXPOINTS)` + `SIZEOF_TOUCH_SAMPLE_S(maxpoint)`）；
   - `ok` 涨但 `hits` 永远 0 ⇒ **没人按**或驱动没报按下 → 用 `--touch-wr x y`
     直接往 GT911 寄存器造一次按下，看 `hits` 是否增长（这会端到端验证整条链路）。
3. **`hits` 会涨但 UI 不响应** ⇒ 问题在坐标/控件层；注意 **按下帧可能只报一帧**
   （GT911 轮询型），要加**按下锁存**（本项目用 120ms），否则点击会丢。
