## 六、真机网络攻坚：eth0 未注册 → 打通（8/30–9/1）

### 问题
ai_agent 需要的 eth0（RJ45）一直未注册：`/proc/net` 空、`ifconfig` 无输出、`ifup eth0` Failed。已确认 NSH→BOARDIOC_INIT→board_app_initialize→esp_bringup→board_emac_init 反汇编链路正确，且 board_emac_init 确实执行（g_hr_timer_initialized=1），但 `g_esp_emac` 结构全 0 → esp_emac_init 在 `dev.ops` 赋值前失败。

### 根因（决定性证据）
- EMAC DMA buffers 由 `heap_caps_aligned_calloc` 从**堆**分配：`(RX20+TX20)×1600B ≈ 48KB`
- 但固件是 **SRAM-only**（512KB PMP 窗口），bss 已占满，堆只剩 **~35KB**（0x4ffb72b4 → 0x4ffc0000）
- `esp_eth_mac_new_esp32` 分配 DMA buffers 失败返回 NULL → `esp_emac_init` 返回 -EIO → eth0 不注册
- 定位方法：OpenOCD 读 `g_esp_emac`（0x4ffac3e0）全 0 vs `g_hr_timer_initialized`=1；对比 defconfig 的 `CONFIG_ESPRESSIF_ETH_NRXDESC/NTXDESC=20` 与堆大小

### 修复
```
CONFIG_ESPRESSIF_ETH_NRXDESC=4
CONFIG_ESPRESSIF_ETH_NTXDESC=4
```
DMA 需求 (4+4)×1600 ≈ 13KB，35KB 堆够用。验证结果：
```
eth0  Link encap:Ethernet HWaddr e8:f6:0a:e3:a6:a5 at RUNNING mtu 576
      inet addr:10.0.0.2 DRaddr:10.0.0.1 Mask:255.255.255.0
```
eth0 RUNNING + 自动获取 IP 10.0.0.2；ps 可见 `esp_timer` + `emac_rx` 任务（EMAC 完全初始化）。

### 经验
1. **DMA buffer 数量要按堆预算算**：ESP32-P4 无 PSRAM 初始化时，大块 DMA 内存只能来自 35KB 堆
2. **OpenOCD RAM flag 证据法**：console 不可用时，靠 `g_hr_timer_initialized`/`g_esp_emac` 内存值反推执行路径（hw bp 在 SMP boot 早期不可靠）
3. **VMware USB 直通抖动**是主要环境障碍：OpenOCD 连接会杀死 USJ console、USB 频繁重新枚举、esptool 时断时连——调试需重试/触发枚举

### ai_agent assert 根因分析（内存不足，已备修复）
- **症状**：ai_agent_main printf 后崩溃，OpenOCD pc 停在 `_assert` 死循环
- **根因**：36KB 堆 vs ai_agent 线程栈需求 ~88KB（agent_loop 32K + voice 16K + outbound 16K + cli 16K + cron 8K）；eth0 打通后 EMAC DMA + 网络栈又占 ~20KB → 堆耗尽 assert

### ai_agent assert 最终根因 + 修复（9/1 续）
- **最终根因（直接）**：`CONFIG_FS_TMPFS` 未启用 → ai_agent Phase 0 `mount(/data, tmpfs)` 失败 → `/data/agent` 不存在 → config.json 无法创建 → `claw_config_get` 读不到配置（load_json 返回空/异常）

## 七、USB 直通不稳定调查(9/1)——根因确认 + 修复

### 调查结论
1. **设备无自发断开**:4.5 分钟监控 devnum 稳定(53),零自发断开
2. **断开 = esptool `--before default_reset` 触发**:每次 esptool 硬件复位→设备重新枚举(正常现象)
3. **复位后立即稳定**:esptool 后 3 秒 console 正常(47B NSH)
4. **CP210x 零断开**:排除 VMware USB 直通/总线问题(同总线设备稳定)
5. **OpenOCD 打不开 ≠ USB 问题**:固件运行时 USB-JTAG 的 JTAG 功能被占用,仅 ROM bootloader 可用(用 esptool 串口代替)
6. **供电隐患**:设备请求 500mA,USB 1.1 端口(VMware UHCI 模拟)供电可能不足,建议独立供电

### 修复(已固化 tools/)
- `tools/build_flash/usb_stable.sh`(原 /tmp/stable_usb.sh):esptool 操作后 `wait_stable`(等 ttyACM0+可打开+3s 缓冲)+ 重试
- `tools/test/verify_aiagent.sh`:复位→启动 ai_agent→多次读取检测 READY
- 经验:USB 操作后 sleep 3-5s;console 单连接;避免高频 esptool chip_id

### 关联发现:ai_agent 内存不足(独立深层问题)
- 打点定位:ai_agent 入口 `[MEM0] arena=29336 used=22664`——入口就用 22.6KB 堆(arena 仅 28.7KB)
- SIMPLE_BOOT PMP 锁定 [0x4FF40000, 0x4FFC0000),bss 已到 0x4ffb8114,堆只剩 28.7KB
- ai_agent 启动 Phase 0 后剩 5.9KB,无法支撑 Phase 1+ → 非确定性卡住
- **根本方案:PSRAM(32MB)初始化后堆放 PSRAM**(大工程,列入 backlog);短期可减 ai_agent 启动内存/延迟初始化

### ai_agent 内存不足详细定位(9/1 续)
- **根因**:NSH 系统(网络栈+EMAC+NSH)启动后已用堆 23.2KB(`free` 命令:used=23744),堆 arena 仅 28.7KB(SIMPLE_BOOT PMP 锁定,SRAM 512KB 满),剩 5.5KB

- **已做优化**:ai_agent 主栈 32→16KB(`CONFIG_EXAMPLES_AI_AGENT_VELA_STACKSIZE=16384`);线程栈裁剪;TLS 缓冲 16→8KB;EMAC DMA 2
- **根本方案**:初始化 32MB PSRAM,把堆放 PSRAM(0x48000000)→ 彻底解决;列入 backlog
- 系统内存占用大户:网络栈(IOB/socket)、EMAC、mbedtls——需逐一核算

## 9.2 弯路:先被"没喂狗"带偏

## 9.3 真正根因(决定性证据:USJ 读回 flash)
USJ(ttyACM0)读回 flash 三个偏移各 16B:
```
0x0000: e906022f   ← 固件头(SPI flash 头)
0x2000: f60f99c2   = 0xc2990ff6 ← 固件 offset 0x2000 的数据
0x4000: 82801c41
```
- **ESP32-P4 ROM 从 flash 0x2000 读 boot header(SPI_FAST_FLASH_BOOT),不是 0x0**
- 固件烧在 0x0 时,flash 0x2000 = 固件代码数据(0xc2990ff6 小端 f6 0f 99 c2)→ ROM 读到 invalid header → 死循环
- **修复:固件必须烧 flash 0x2000**

## 9.4 正确烧录命令(已固化)
```
esptool.py --chip esp32p4 -p /dev/ttyACM0 -b 921600 \
  --before default_reset --after hard_reset \
  write_flash --no-compress 0x2000 nuttx.bin
```
- USJ(ttyACM0)烧录稳定 ~1386 kbit/s;`--before default_reset` 自动进下载(等效按 BOOT+EN),`--after hard_reset` 自动复位运行
- UART0(ttyUSB0)115200 慢且 stub 易断,仅用于观察

## 9.5 修复后正常启动链路

free: 29608 total / 23696 used / 5912 free

- **SIMPLE_BOOT 的 `SHA-256 comparison failed: Calculated <hash> / Expected ffff...` 是正常现象**(ram-only 镜像 digest 未追加),不要当错误处理

# 十、PSRAM 写 hang 深度调试(9/3–9/4)——最终根因:bootloader PMP 时序缺陷(非硬件 bug)

## 10.1 已确认的事实
- **PSRAM 检测/初始化成功**:esp_psram_chip_init/esp_psram_init ret=0,32MB 映射 0x48000000–0x4a000000
- **CPU 读 PSRAM OK**(cache 读 + 非 cache 0x88000000 读都 OK)
- **CPU 写 PSRAM 卡死(hang)**:任何地址(0x48000000/0x88000000)、任何宽度(1/4/128B)都 hang;无 trap(装了 trap handler 无输出 = 总线等待,非异常)
- **直接 MSPI 写 OK**:psram_ctrlr_ll_common_transaction(SPIMEM3 PERI)写 OK,数据正确
- 差异本质:**CPU/cache 走 SPIMEM2(SYSTEM)写 hang,直接事务走 SPIMEM3(PERI)写 OK**

## 10.2 已排除(40+ 项,每项构建+烧录+测试 ~3-5 分钟)
- SPIRAM 速度 20/80/200M(无关)
- cache 启用(L1/L2 autoload、cache_hal_enable、cache_ll enable)(无关)
- CLIC 中断启用/禁用(无关)
- MMU 权限(mmu_ll 无只读位)(无关)
- PSRAM LDO 供电(esp_ldo_acquire_channel 1.8V)(无关)
- DDR/SDR 模式(PSRAM 必须 DDR;SDR 直接 init 失败)(无关)
- 8-line / hex 数据线(无关)
- wr_splice/rd_splice、split_trans、var_dummy、dqs_loop、outminbytelen、cmd_dis、tx_ddr_msk、addr_4byte、AXI 仲裁(无关)
- cache writeback/invalidate(写回本身不 hang,store hang)
- 烧录地址(已修复)、console(已切 UART0)

## 10.3 对比 NuttX 官方 PSRAM 支持(PR #18754,2026-04 已合并)
- 官方 `esp32p4-function-ev-board:psram_usrheap` defconfig 测试 **PSRAM 写正常**(free 显示 32MB Umem,heap 测试分配 0x480018c0 成功)
- openvela 的 esp_start.c / esp_allocateheap.c / hal_esp32p4.cmake / linker 脚本与 PR 改动逐一核对——**全部都有**
- PR 后无新的 esp32p4 PSRAM 提交
- 配置对齐(SPIRAM=y + MM_REGIONS=2 + MM_KERNEL_HEAP + MEMTEST + 200M)后写仍 hang

## 10.4 核心结论（9/4 修正：推翻"硬件 bug"假设）
- **芯片 rev 判定（决定性）**：`efuse_hal_chip_revision() = major×100 + minor`（esp32p4 特化实现返回 wafer_version_major×100 + wafer_version_minor）→ **302 = v3.2**，与 esptool "revision v3.2" 完全一致
- **此前"302<310 有 bug"是编码误读**：310 不是有效编码（v3.1=301），芯片实际是 **v3.2 ≥ v3.1 修复线**
- ESP32-P4 勘误表 [MSPI-749/750/751 + APM-560](https://documentation.espressif.com/projects/esp-chip-errata/en/latest/esp32p4/03-errata-description/index.html) 明确 **"Fixed in chip revision v3.1"** → 本芯片**硬件已修复，无该 cache/PSRAM bug**
- openvela 的 esp_start.c 已调用官方 PR 全部初始化（esp_mspi_pin_init(634)/esp_mspi_pin_reserve(679)/bootloader_init_mem(681)/esp_mmu_map_init(641)）
- **结论反转：写 hang 是 openvela/NuttX 移植的软件缺陷，不是硬件 bug → 应该能在软件层解决**

## 10.5 判定方法（如何验证"硬件 bug vs 软件 bug"）
1. **芯片 rev 判定**：查 `efuse_hal_chip_revision()` 编码实现（major×100+minor），对照 esptool；再对照勘误表"Fixed in revision"确认硬件是否含该 bug
2. **决定性对照实验（同板跑官方 ESP-IDF）**：同一块板烧 ESP-IDF 官方 PSRAM 测试固件——ESP-IDF 写 OK → 100% 是 NuttX/openvela 移植 bug（软件可修）；ESP-IDF 也 hang → 才可能硬件问题
3. **排除法已做**：PR #18754 改动全部对齐、配置对齐、trap handler 确认非异常（总线等待）、直接 MSPI 写 OK

## 10.6 最终根因与修复（9/4 晚，OpenOCD 决定性诊断）

### 决定性诊断（OpenOCD）
- `halt` → **`Halt cause (7) - PMP Store access fault`**（之前一直误判为"总线 hang"，实际是 PMP 权限拒绝！）
- `mepc=0x4ff4d56a` = `sw a5,0(a4)` 写 PSRAM 指令（riscv_addregion 内）
- 关键：**之前 trap handler 没捕获 + 一直以为是 hang，是因为 PMP fault 是同步异常且死循环 → LP WDT 复位 → UART0 0B 假象**

### 完整根因链
1. `bootloader_init_mem`(bootloader_init 内、**PSRAM init 之前**)在 `CONFIG_BOOTLOADER_REGION_PROTECTION_ENABLE=1` 时调用 `esp_cpu_configure_region_protection()`
2. 此时 `esp_psram_get_heap_size_to_protect()=0`（PSRAM 未初始化）→ PMP 条目 11 配成**空 TOR 区间** `[0x12000000, 0x12000000)`（pmpaddr11=0x12000000 = PSRAM 物理 0x48000000>>2）且 **L 位锁定**
3. PSRAM init 后 region protection 尝试重配 pmpaddr11=0x12800000（32MB），但 **L 锁定 → CSR 写入被硬件拒绝**（固件 + OpenOCD 都写不进）
4. PMP 无 RW 条目覆盖 PSRAM → 默认拒绝写 → **PMP Store access fault** → 死循环

### 修复（2 处）
1. **bootloader_mem.c**：`bootloader_init_mem` 里 `#if 0` 禁用 bootloader 阶段的 region protection（避免 PSRAM init 前错误锁定）：
```c
#if 0 /* openvela: skip bootloader PMP (locks PSRAM write before PSRAM init) */
    esp_cpu_configure_region_protection();
#endif
```
2. **esp_start.c**：`esp_cpu_configure_region_protection()` 在 PSRAM init **后**调用（`CONFIG_ESPRESSIF_REGION_PROTECTION=y`，默认开启，**不要禁用**——之前为"排除 APM-560"禁用它反而加剧了问题）

### 验证（决定性）
- pmpaddr11 = **0x12800000**（正确 RW 覆盖 32MB PSRAM）
- PSRAM 0x48000100 = **0xdeadbeef**（写入成功）
- 系统 boot 到 **idle**（esp_cpu_wait_for_intr），halt cause = **11（ECALL 正常）**，无 PMP fault
- **PSRAM 写 hang 彻底解决，不是硬件 bug、不是 cache 写路径——是 PMP 配置时序缺陷**

### 关键调试经验
- **先看 halt cause**：7=PMP fault vs 11=ECALL，一眼区分"权限拒绝"vs"正常运行"
- **PMP pmpaddr 寄存器存 addr>>2**（0x48000000>>2=0x12000000）
- **esp_usb_jtag 的 OpenOCD 读 CSR 不准、写更无效**（写 pmpaddr11 无效）→ 用固件 `csrr` 读存内存再 OpenOCD 读内存
- **固件里手动 csrw pmpaddr11 被拒（L 锁定）**是定位"PMP 配置失败"的关键证据
- **UART0 被 tabby 占用时 python 读不到**（ttyUSB0 fuser 可见）

## 10.7 最终验证（9/4，tabby MCP 调试）—— PSRAM 32MB 完全可用
- **clean 固件**（bootloader_mem.c 禁用 bootloader PMP + esp_start.c region protection 在 PSRAM init 后 + 移除全部调试打印）正常 boot 到 NSH
- `free` 输出（通过 tabby MCP 发命令 + 读缓冲）：
```
nsh> free
      total       used       free    maxused    maxfree  nused  nfree name
   33576240      23720   33552520      24096   33552440     65      4 Umem
```
- **Umem = PSRAM 32MB 用户堆，完全可用** → ai_agent 内存问题彻底解决
- **调试手段升级：tabby MCP**（tabby-mcp-server 1.6.2，SSE `http://localhost:3001/mcp`）——`get_terminal_buffer` 读 NSH 缓冲、`send_input` 发命令、`close_tab` 关串口会话释放端口（ttyACM0 被 tabby 占用时 esptool 烧录失败，close_tab 解决）、`get_session_list` 定位会话

## 10.8 ai_agent 完整启动成功（9/4，tabby MCP + OpenOCD 联调）—— 主线闭环

### 10.8.1 现象
PSRAM 32MB heap 就绪后，ai_agent 能启动但卡死在 `llm_router_init` 之后的 `tool_registry_init`
（"Router initialized" 后无输出），随后反复 **PMP Load access fault**，整机看似"卡死"。

### 10.8.2 Root cause（OpenOCD 断点/栈分析确认）
1. ai_agent 作为 NSH 前台 builtin 命令，实际在 **nsh_main 任务栈（仅 1984B）** 上执行
   （task_spawn 后 proxy 先行、preemption disabled 期间深 init 链跑在当前任务栈）
2. ai_agent init 的深调用 + cJSON/mbedTLS 栈需求远超 1984B → **nsh_main 栈溢出**
3. 栈溢出写穿覆盖 TLS 区 → **TLS[0]（`tl_task`）被写为 0**
4. `getumask` / `fdopen`（经 `lib_get_streams`：`g_readytorun[112]→[0]→+296`）读空指针偏移
   → **PMP Load access fault**（mtval=0x128），异常进 up_mdelay 死循环 → 整机"卡死"

**定位证据链**（为什么是栈问题而非 PMP/cache）：
- OpenOCD 断点命中 ai_agent_main：`sp=0x4ffbb9c0` 挤在 nsh_main 栈顶（0x4ffbb410）附近，
  `g_readytorun` 仍指向 nsh_main（pid=2）→ 前台复用 nsh_main 栈，而非独立 16KB 任务栈
- fault 现场反复出现 `TLS[0]=0`（复位后正确值 0x4ffbb058）→ TLS 头被覆盖
- `sp=0x4ffb0898` 低于 nsh_main 栈底 ~744B → 栈已溢出写穿

### 10.8.3 修复
```
CONFIG_DEFAULT_TASK_STACKSIZE=16384   # defconfig：nsh_main 栈 1984B → 16320B
```
- 安全网（保留，防同类 TLS 损坏）：`lib_umask.c` 的 `getumask()` 加 `info != NULL` 判断

### 10.8.4 验证（决定性）
- `ps`：nsh_main STACK 从 `0001984` → `0016320`
- ai_agent 完整输出 **P0→P5 全 rc=0**：
  P0 timezone/storage/heap → P1 config_store/message_bus/memory_store/session_mgr →

- 系统自由运行 **30s+ 无 PMP fault**（OpenOCD Halt cause **11 = ECALL 正常**）
- ai_agent 线程栈分配在 **PSRAM**（当前任务 0x4800fc90，heartbeat 线程 pid6 @0x4800caa0）→ PSRAM 32MB 完整可用

### 10.8.5 运行模式说明与遗留
- **P6 CLI**：ai_agent 前台由 NSH spawn 后 main 线程进入 `while(!g_shutdown_requested) sleep(1)`

  （提示符 `vela> `），演示环境建议以系统服务/自启方式接入而非 NSH 前台
- **遗留**：`ai_agent &`（NSH 后台运行）会触发 ROM 区（0x4fc1b674，libc 内空指针）PMP fault，

# 十三、本轮最大教训(写给自己)

1. **先验证物理事实,再猜根因**:烧录问题 3 秒读回 flash 就能定(0x2000 vs 0x0),却先做了半天 WDT 分析。凡"复位循环/启动失败",第一步永远是读回 flash / 抓完整 boot 日志,确认固件到底在不在正确位置。
2. **console 通道决定你能看到什么**:USJ console 不可见 ≠ 系统没启动。改 console 到 UART0(esp_rom_printf)前,不要下"卡死"结论。
3. **盲试配置是最贵的调试**:PSRAM 写 hang 40+ 次构建+烧录(每次 3-5 分钟),很多是重复的寄存器排列组合。应更早:(a) 用 trap handler 区分 hang vs trap(一次就排除异常);(b) 对比官方 PR #18754 的已验证配置(早该查);(c) 一次验证"官方配置能否跑"而非逐一改寄存器。
4. **决定性问题优先**:验证"是否硬件 bug"应靠"官方同样代码在别的板/rev 能否写 PSRAM",而不是靠穷举我的配置。
5. **保留基线**:每轮调试前确认有一个可跑固件(当前:禁 SPIRAM 基线),避免改坏后无退路。
6. **sed 大段删除会误伤**:清理调试代码用 edit 精确操作,别用 sed 匹配删除。

## 19.4 根因：代码空间而非内存（9/10 晚实测修正）
- 桩掉的理由注释是「省 512KB SRAM」；实测占用 **text 337KB + rodata 67KB + bss 53KB + data 6KB ≈ 463 KB / 512 KB** → 仅余 ~49 KB
- PSRAM 32MB 只能做 heap，**救不了代码空间**
- ⚠️ **修正初判**：512KB **无法扩容**，不是"768KB 里只用了 512KB"：
  - `SOC_DIRAM_ROM_RESERVE_HIGH = 0x4ff40000`（`soc.h:183`）→ 低 **256KB 是 ROM 保留区**（ROM data/bss + L2 cache 存储）
  - `esp32p4_flat_memory.ld:37-43`：ROM bootloader arms **locked PMP** 覆盖 [0x4FF40000, 0x4FFC0000)（RW）；低区是 L2 cache storage 且复位被擦除 → **不能放镜像**
  - `CONFIG_SPIRAM_XIP_FROM_PSRAM` 仅在 ld 引用、**Kconfig 未定义** → "PSRAM 执行代码"是死代码
  - L2 cache 128/256/512KB 选项**不移动 ROM 保留边界** → 改 cache 不增加窗口

# 二十、SRAM 空间攻坚：cron 启用 + 静态内存移 PSRAM（9/10 深夜，真机验证）

> 📌 **结论**：512KB SRAM 窗口**无法扩容**，但通过"把静态运行内存搬进 PSRAM"把 **cron 定时任务真实跑起来**（赛题③），
> 且 SRAM 静态占用反而比改造前更低。

## 20.1 起初的错误假设与实测推翻
| 假设 | 实测结论 |
|---|---|
| "ESP32-P4 有 768KB SRAM，当前只用 512KB，扩窗口即可" | ❌ **推翻**：`SOC_DIRAM_ROM_RESERVE_HIGH=0x4ff40000` → 低 256KB 是 ROM 保留区（ROM data + L2 cache 存储）；ROM 已**锁定 PMP** 覆盖 [0x4FF40000,0x4FFC0000)，窗口边界不可改 |
| "可以启用 PSRAM XIP 跑代码" | ❌ `CONFIG_SPIRAM_XIP_FROM_PSRAM` **仅被 ld 引用、Kconfig 未定义** → 死代码 |
| "调小 L2 cache 就能多出内存" | ❌ 不移动 ROM 保留边界，窗口不变 |

**关键事实**：当前是 **ram-only 镜像**（`esptool image_info` 显示全部 6 个段 load 到 `0x4ff4xxxx`，无 flash/PSRAM 段）→
16MB flash 只当"仓库"，32MB PSRAM 只当"堆"。**代码只能在 512KB SRAM 里跑**，这才是真瓶颈。

## 20.2 真正的解法：静态运行内存搬到 PSRAM
`free` 证实堆就是 PSRAM（Umem=33.5MB），线程栈也已落 PSRAM（`0x4800xxxx`）→
**把 .bss 里的大块静态缓冲改成堆分配，即可把 SRAM 让给代码**：

| 改动 | 释放 SRAM | 说明 |
|---|---|---|
| `vela_tls.c`：8KB 静态 TLS 原始缓冲 → `malloc` | 8.0 KB | 带 NULL 保护（`-ENOMEM`） |
| `cron_service.c`：11.4KB 静态作业表 `s_jobs[16]` → `calloc` | 11.1 KB | 新增 `cron_ensure_jobs()` 惰性分配 + 5 个入口保护 |

# 二十一、MCUboot 二级引导打通 —— 代码迁入 Flash(9/11,真机验证)

> 📌 **里程碑**：SRAM 占用从 **460KB → 83KB**（9/11 首测；9/17 干净树复测 **120.3KB**，见 `docs/04` §3.2），text+rodata 全部在 **16MB flash 中 XIP 执行**，
> NuttX 经 MCUboot 引导启动到 NSH，ai_agent P0→P3 全 rc=0。**这是 LVGL/摄像头/语音等大功能的解锁前提。**

## 21.1 为什么必须切二级引导（实测证据）
| 证据 | 结论 |
|---|---|
| `esptool image_info`：SIMPLE_BOOT 固件 6 个段全 load 到 `0x4ff4xxxx` | 代码只在 512KB SRAM 跑，16MB flash 仅当"仓库" |
| `SOC_DIRAM_ROM_RESERVE_HIGH=0x4ff40000` + ROM **锁定 PMP** | 低 256KB 是 ROM 保留区，**512KB 窗口无法扩容** |
| `CONFIG_SPIRAM_XIP_FROM_PSRAM` 仅被 ld 引用、Kconfig 未定义 | "PSRAM 跑代码"在 SIMPLE_BOOT 下是死代码 |
| 只加 cron 即 `region 'sram_seg' overflowed by 4496 bytes` | 代码空间已到极限 |

## 21.2 五道集成障碍与修复（全部做成持久化补丁）
`nuttx/tools/espressif/mcuboot_p4_fixup.sh`（挂 `PATCH_COMMAND`，幂等；MCUboot 每次 update 会重置源码，手工改会被抹掉——踩过）：

## 21.3 让 NuttX 应用能在 Flash 中执行（两个自研工具）
MCUboot 的 p4 端口**不执行 ESP 镜像格式**，而是读 `esp_image_load_header_t`（magic `0xace637d3`）——NuttX 的集成不生成它，且只 memcpy SRAM 段。新增：

1. **`tools/espressif/mcuboot_mkloadhdr.py`** —— 从 `esptool elf2image` 产物重排为：
   ```
   +0x0000  MCUboot 头 (imgtool -H 32)
   +0x0020  load header (0x60B)      ← MCUboot 读这里
   +0x0080  SRAM 段 (IRAM/DRAM)      ← MCUboot memcpy 到 RAM
   +0x10000 XIP 段 (text+rodata)     ← 64KB 对齐，由 MMU 映射，原地执行
   ```
   内含 XIP 偏移断言（与链接脚本常量互锁，防止 SRAM 变化后静默错位）。
2. **`tools/espressif/mcuboot_p4_loader_patch.py`** —— 给 MCUboot 加载器补：
   - 跳转前 **MMU 映射 IROM 区**（`mmu_hal_map_region`）
   - **使能 L1 cache 总线**（`cache_ll_l1_get_bus` / `cache_ll_l1_enable_bus`）——缺这步取指必失败（对照 ESP-IDF `bootloader_utility.c` 得出）
   - 跳过 0 长度段（P4 上 IRAM/DRAM 同窗，DRAM 段为 0 时 `bootloader_mmap` 会报错）
3. **`espressif_mkimage.cmake`**：MCUboot 分支改为「先 elf2image → 再生成 load header → 再 `imgtool sign`」（原来直接拿 Intel HEX 去签名，imgtool 算出 512MB 幻影大小）

## 21.4 两个"改了会挂"的关键点（真机定位）
| 现象 | 根因 | 修复 |
|---|---|---|
| MCUboot 映射成功、跳到应用后**无任何输出** | `esp_start.c` 的 `map_rom_segments()` 用 `槽偏移 + LOADADDR(.flash.text)` 当物理地址，而 p4 链接脚本**无 `AT>` 规则** → `LOADADDR` 返回虚拟地址 `0x40000000`，算出 `0x40020000` 垃圾值 | `esp32p4_sections*.ld`：MCUboot 模式下把 `_image_irom_lma/_image_drom_lma` 显式定义为**槽内 flash 偏移**（`0x10000 + (ADDR - 0x40000000)`） |
| 映射对了，仍卡死（无输出） | `esp_clk_init()` 末尾 `rtc_clk_cpu_freq_set_config()` **改 CPU PLL**；此时代码正从 flash 取指，flash 时序未按新频率重调 → 取指停顿直到 WDT 复位（SIMPLE_BOOT 时代码在 SRAM，同调用无害） | MCUboot 模式下**跳过 `esp_clk_init()`**（二级引导已配好时钟） |

## 21.5 Flash 布局（16MB 物理 / MCUboot 管前 4MB）
```
0x000000 - 0x002000  ROM 引导
0x002000 - 0x020000  MCUboot 引导 (24.6KB)      ← 烧 0x2000
0x020000 - 0x1E0000  OTA_0 主槽 (1.75MB)        ← 烧 0x20000
0x1E0000 - 0x3A0000  OTA_1 副槽 (1.75MB)
0x3A0000 - 0x3E0000  scratch (256KB)
─────────────── MCUboot 视野上限 4MB ───────────────
0x400000 - 0x1000000 其余 12MB：归应用（数据分区）
```
- ⚠️ **MCUboot 引导期 MMU 窗口只覆盖 4MB**：声明 16MB 会让它在 `bootloader_init()` 早期 `Load access fault`（实测），故 MCUboot 保持 4MB 视野，槽位全部落在 4MB 内
- **升级模式改 `UPGRADE_ONLY`**：引导期无法映射多 MB scratch，交换模式不可用（引导因此从 30KB 瘦到 24.6KB）

## 22.2 🔴 四个平台级缺陷（本轮最大价值）

### 缺陷 1：板级 Kconfig 静默失效（影响所有 esp32p4 板）

**现象**：往 `boards/.../esp32p4-function-ev-board/Kconfig` 加的任何选项都不生效，
`.config` 里查不到；显示/触摸功能的编译开关形同虚设。

**根因**（`nuttx/CMakeLists.txt:315-331`）：
CMake 只在 `CONFIG_ARCH_BOARD_CUSTOM` 为真时把板级 Kconfig 软链到
`$BINDIR/boards/dummy/Kconfig`（由 `boards/Kconfig` source）。而该板走的是
"自定义板"路径（defconfig 里只有 `CONFIG_ARCH_BOARD="..."`），
于是走了 `file(TOUCH ...)` 分支 → **生成 0 字节占位文件** → 之后 `if(NOT EXISTS ...)`
永远为假 → **Kconfig 永远不会被软链**，板级选项全部丢失。

**为什么隐蔽**：构建**完全成功**、毫无告警。0 字节文件被 `source` 时是合法的空文件。

**修复**（两处，均已固化）：
- `CMakeLists.txt`：增加"0 字节占位文件"检测，命中即删除以便重建软链（幂等，对所有自定义板生效）
- defconfig 显式声明 `CONFIG_ARCH_BOARD_CUSTOM_DIR` 指向本板目录

**连带发现**：`esp32p4-tab5` 参考板有同样缺陷 —— 它的 `CONFIG_ESP32P4_TAB5_LCD`
等选项在本仓库中同样不可达，即**参考实现其实是在"没有 LCD"的配置下构建的**。

**教训**：配置项的"沉默失败"比编译错误危险得多。凡是"加了选项没反应"，
先确认该 Kconfig 文件真的被 source 进来了。

### 缺陷 2：UART 控制台输出丢字节（影响所有 espressif 串口控制台）

**现象**：ai_agent 启动日志每次稳定丢失约 1.5KB（含 `P6`/`AI Agent ready` 行），
`vela>` 提示符从未出现。表现为"agent 卡在 P5 起不来"。

**根因**（`arch/risc-v/src/common/espressif/esp_lowputc.c`）：
```c
void esp_lowputc_send_byte(...) {
    uint32_t write_size;
    uart_hal_write_txfifo(priv->hal, (const uint8_t *)&byte, 1, &write_size);
}   /* 不等 FIFO 有空间，写不进去就直接丢弃该字节 */
```
`uart_hal_write_txfifo()` 在 FIFO 满时**不写、也不报错**（`write_size` 回 0），
而这是 `up_putc()` → syslog/printf 的控制台路径，所以输出突发超过 FIFO 深度即静默截断。

**定位过程**（值得记录的排除法）：
1. 先怀疑线程没启动 → 打点确认 `pthread_create` 返回 0
2. 再怀疑优先级 → 把 cron/heartbeat/CLI 调到 50 后，前两个开始运行，CLI 仍不行
3. 再怀疑线程创建顺序 → 把 CLI 提前创建，**提示符仍未出现**
4. 用 `fstat` 证明 stdin/stdout 就是 `/dev/console`（rdev/mode 一致）
5. 直接探针 `write(1)/write("/dev/console")/write("/dev/ttyS0")` 全部返回成功但**都到不了串口**
6. 反查 NuttX 侧：`CONFIG_UART0_TXBUFSIZE=256` + send_byte 不判空间 → **真因**
7. 修复后 `vela>` 提示符立刻出现

**修复**：等待 `uart_hal_get_txfifo_len()` 有空间再写（中断上下文只自旋不睡），
并把 `CONFIG_UART0_TXBUFSIZE` 提到 2048。

### 缺陷 3：GT911 驱动缺 ioctl 导致 LVGL 无法用触摸

**现象**：触摸即使初始化成功，LVGL 仍拒绝打开 `/dev/input0`。

**根因**（`drivers/input/gt9xx.c`）：file_operations 里 `ioctl = NULL`，
于是 `TSIOC_GETMAXPOINTS` 返回 `-ENOTTY`；而 LVGL 的
`lv_nuttx_touchscreen_create()` 在 `maxpoint == 0` 时直接放弃。

**修复**：补 `gt9xx_ioctl()` 返回 `maxpoint = 1`，并把 fileops 补全。

### 缺陷 4：V4L2 上层拒绝裸 Bayer 格式

**现象**：摄像头模块识别成功、设备节点正常，但 `VIDIOC_S_FMT` 恒返回 `EINVAL`。

**根因**（`drivers/video/v4l2_cap.c` `capture_try_fmt()`）：
`switch (pixelformat)` 的白名单只列了 NV12/YUV420/YUYV/UYVY/RGB565/JPEG 等，
**`default: return -EINVAL;`** —— 裸 Bayer（SBGGR8/10 等）全部被拒。
而没有 ISP 的 MIPI-CSI 传感器只能直接输出 Bayer。

**修复**：把 `V4L2_PIX_FMT_SBGGR8/SGBRG8/SGRBG8/SRGGB8/SBGGR10/...SRGGB10`
纳入白名单（直通 `imgdata` 下半部，不改变语义）。

## 22.3 硬件实测结论（诚实记录）

| 项 | 现象 | 判断 |
|---|---|---|
| 摄像头 | `SC2336 chip ID: 0xcb3a`（I2C0 @0x30 应答） | ✅ **模块识别、供电、24MHz 晶振、SCCB 帧格式全部正确** |

> 在 DSI 时序/初始化表上耗费大量时间。

## 22.4 烧录脚本的 SIGPIPE 竞态（差点造成"烧录成功但启动失败"）

**现象**：`tools/build_flash/usb_stable.sh`（改造成两镜像后）报"烧录 OK"，
但 MCUboot 报 `Image in the primary slot is not valid!`。

**根因**：脚本写成 `esptool ... | tee log | grep -q "Hash of data verified"`。
`grep -q` 在匹配到**第一个镜像**（引导）的校验行后立即退出 →
`tee` 收到 SIGPIPE 退出 → **正在写第二个镜像（应用）的 esptool 被连带杀掉** →
应用槽只写了一半，而流水线整体返回码仍是 0。

**修复**：先落盘再检查 —— `esp_run()` 把输出写文件并返回真实退出码，
`verify_log()` 要求日志里出现**两次** `Hash of data verified` + 一次 `Hard resetting`。

**教训**：`cmd | grep -q` 是经典陷阱 —— 早退的消费者会杀死生产者。
凡是"必须在乎命令是否真的跑完"的场景，都不能用管道短路。

## 22.5 并行开发的两个协作教训

1. **同一个构建目录不能并发跑 ninja**：本轮两个并行工作流同时在同一
   `cmake_out/` 构建，导致 `include/nuttx/config.h: unterminated #ifndef`、
   ccache `.d` 文件丢失、LVGL 静态库 `ar` 失败等**看似代码错误的假故障**。
   解法：每个工作流用独立构建目录（`--cmake -b <dir>`）。
2. **共享 defconfig 要用"只追加"策略**：多个工作流同时改
   `configs/nsh/defconfig` 时，全量重写会互相覆盖（本轮出现过
   `CONFIG_UART0_TXBUFSIZE=2048` 被重新配置冲掉）。约定：各自只在文件末尾
   追加自己的块，并在每次全量重配后逐行核对关键开关。

本节记录 9/14 后半程的定位与修复。**显示与 DNS 两项已真机闭环**，其余为精确定位后的新阻塞。

### 23.1 ✅ 显示点亮（`/dev/fb0`）——又一个平台级缺陷

**症状**：`EK79007 DCS 0xb2 failed: -110`，`esp_mipi_dsi_read_short: read FIFO empty timeout`，
`failed to register /dev/fb0`。现象极像"面板没供电 / 没接好"。

**根因**：`nuttx/drivers/video/mipidsi/mipi_dsi_device.c` 的 `mipi_dsi_dcs_write_buffer()`
**没有初始化 `struct mipi_dsi_msg` 里的 `rx_len` / `rx_buf`**（只逐字段赋了
channel/tx_buf/tx_len/flags/type）。而 DSI host 正是靠这两个字段判断读写方向：

```c
/* esp_mipi_dsi.c:899 */
is_read = (msg->rx_len > 0 && msg->rx_buf != NULL);
```

栈残留值一旦满足条件，一条本该 fire-and-forget 的 **DCS 写**会被当成 **读** 发出去 →
`esp_mipi_dsi_read_short()` → 等 BTA 应答 → 没人应答 → `-110`。

**影响面**：本文件 8 处 `struct mipi_dsi_msg` 声明全部中招（6 处写路径没赋 rx，
2 处读路径显式赋了）。任何在这块板子上接 MIPI-DSI 屏的驱动都会随机踩到。

**修复**：8 处统一改为 `= { 0 }`，并在 `mipi_dsi_dcs_write_buffer()` 留了带解析的注释。

**真机验证**：
```
EK79007: panel initialized (2 lanes, 900 Mbps/lane)
Starting DSI video...
/dev/fb0 ready 1024x600 RGB565 @ 0x48000040 (1228800 bytes)
/dev/fb0 registered (EK79007)
```

> 教训：`-110` + "读 FIFO 超时" 很容易被读成"面板硬件问题"，从而去查跳线 / 供电。
> 这次真正的突破口是**日志里出现的是 read 路径** —— 可一条 DCS **写**为什么会走读路径？
> 顺着这个矛盾才找到未初始化变量。

### 23.2 ✅ DNS 打通（且开机全自动）——三个叠加原因

| # | 原因 | 证据 | 修复 |
|---|---|---|---|
| 1 | `CONFIG_NET_UDP` 未开 | `dns_*` 符号数 = 0 | `CONFIG_NET_UDP=y` |
| 2 | **`CONFIG_NETINIT_DHCPC` 未开** | `.config` 里 `NETINIT_IPADDR=0x0a000002`（NuttX 出厂默认）把网卡刷成 `10.0.0.2/24`，而现场网段是 `192.168.1.0/24` | `CONFIG_NETINIT_DHCPC=y` |
| 3 | **netinit 不等链路就发 DHCP** | `ifup` 只启动 PHY 状态机，链路异步协商；DISCOVER 打进未 up 的链路被静默丢弃 → 开机停在 `0.0.0.0` | 新增 `CONFIG_NETINIT_DHCPC_LINK_WAIT_MS`（默认 5000），等 `IFF_RUNNING` |

关键点：`CONFIG_NETUTILS_DHCPC` 只是**把客户端编进来**，`CONFIG_NETINIT_DHCPC` 才是
**有人去跑它**。只开前者时 netinit 走 `else` 分支用静态默认值 —— 这是最容易漏的一对符号。

`IFF_RUNNING` 只由 `netdev_carrier_on()` 置位、`netdev_carrier_off()` 清除
（**不是** `ifup` 设的），所以它是真正的 carrier 指示，可安全用作"链路已 up"的判据。

**真机验证（无需任何手工命令）**：
```
eth0  inet addr:192.168.1.105  DRaddr:192.168.1.1  Mask:255.255.255.0  mtu 1500
nslookup api.xiaomimimo.com → 202.69.4.22
主机侧 ping 192.168.1.105 → 通
```

### 23.4 🔶 摄像头：拿到真实失败原因，修复已就位

打开 `CONFIG_DEBUG_VIDEO_ERROR` 后终于看到人话（此前只有 `errno=22`）：

```
SC2336: only 30 fps is supported
Failed to VIDIOC_S_FMT: errno = 22
```

**根因**：`v4l2_cap.c` 的 `initialize_frame_setting()` 在驱动**没有声明 `frmintervals`** 时，

### 23.5 🔴 两个仍未解决（均已精确定位）

**(a) 摄像头 DW_GDMA 中断分配失败**

```
E intr_alloc: No free interrupt inputs for DW_GDMA interrupt (flags 0x10E)
E dw-gdma: dw_gdma_install_channel_interrupt(641): alloc interrupt failed
esp_csi_data_init: ERROR: esp_cam_new_csi_ctlr failed: 261
```

**这是显示修好之后才出现的**：DSI 未通时它提前返回、不占中断；DSI 一通，
`esp_mipi_dsi.c:339-354` 就调用 `esp_setup_irq(DW_GDMA_INTR_SOURCE, ...)` 装上 ISR，
而 CSI 侧走 ESP-IDF 的 `esp_intr_alloc()` 要同一个 source 的 CPU 中断 → 拿不到。
方向：让其中一方以 `ESP_INTR_FLAG_SHARED` 申请，或让二者共用同一 ISR 分发。

**(b) 🔴 ai_agent 在网络服务真正启动后整板冻结（当前最大阻塞）**

现象：`All network services started!` 之后约 15–27s，**整板冻死**（串口无输出、ping 不通），
但**未复位**（`/dev/ttyACM0` 上 0 字节 ROM 输出，排除重启）。

已做的排除（全部真机）：

| 变量 | 结果 |
|---|---|
| 只空闲、不跑 ai_agent | **稳定**（235s 仍在线） |
| 只压网络（反复 nslookup + ping）、不跑 ai_agent | **稳定** |
| 跑 ai_agent 但 `ifdown eth0` | **稳定 90s+** |
| 关闭显示（`LCD`/`MIPI_DSI`/`LCD_BL`=n）后跑 ai_agent | **仍冻结**（显示被排除） |
| MTU 改 1500 后跑 ai_agent | **仍冻结**（MTU 被排除） |

关键推论：`ifdown eth0` 时 `network_wait_connected()` 会**超时**，于是走
`agent_main.c:191` 的 "Network timeout — net services not started" 分支，
**WS 服务 / cron / heartbeat / agent loop 全部没启动**。所以"稳定"证明的不是"没流量"，
而是**这些服务没起来**。嫌疑因此收窄到这几个服务，其中 **cron 的 10s tick 与观测到的
~15–27s 冻结时间高度吻合**（服务 ~13s 起好 + 10s ≈ 23s）。

> 副产物：此前 `docs/09` §七 记的"agent 启动后 console 输入无响应"，
> 与本冻结现象**是同一个问题** —— 不是输入通道问题，是整板冻死。

**(c) GT911 触摸仍无应答** —— 摄像头在**同一条 I2C0** 的 `0x30` 能正常应答芯片 ID，
说明总线本身没问题；同挂在 LCD 模组 FPC 上的 GT911(`0x5D`) 与 EK79007 此前一起失效。
显示现已修好，需重新确认触摸是否随之恢复（待测）。

### 23.6 操作教训：`/dev/ttyACM0` 被占 = 板子"假死"

排查中一度出现"板子冻死"的**假象**，真因是 **Tabby 的串口会话占着 `/dev/ttyACM0`**。
该口是 ESP32-P4 的原生 USB-Serial/**JTAG**，其 **DTR/RTS 直接控制芯片复位 / 下载模式**；
被占时 `esptool` 连 `chip_id` 都打不开（`Errno 11 Resource temporarily unavailable`），
**我发出的"reset"其实一次都没生效**，于是看到的是"复位后 0 字节输出"。

解决：用 **Tabby MCP**（`http://localhost:3001/mcp`）列出并关闭串口标签页以释放端口：

```bash
python3 tools/engineering/tabby_mcp.py text list_tabs
python3 tools/engineering/tabby_mcp.py text close_tab '{"tabId":"tab-97e0b64d","force":true}'
```

**结论：排查真机问题前，先 `fuser -v /dev/ttyACM0 /dev/ttyUSB0` 确认没人占口。**

### 23.8 ✅ 触摸（GT911）——控制器一直都在，是**我们的判据**把它丢掉了

**症状**：板上长期报
```
ERROR: GT911 not detected at 0x5d or 0x14 (check I2C0 GPIO7/GPIO8 and the panel FPC)
```
这条日志把排查方向直接引向"硬件没接好 / 总线不对"，此前几轮也确实去查了 FPC 方向、
J1→J6 跳线、模组供电。

**关键一步：先别猜，把 I2C0 全地址扫一遍。** 新增 `board_i2c_scan()`（1 字节读作为
探测，不会写任何器件寄存器），实测：

```
I2C0 @400000 Hz: ACK from 0x18   ← ES8311 codec
I2C0 @400000 Hz: ACK from 0x30   ← SC2336 camera
I2C0 @400000 Hz: ACK from 0x5d   ← GT911，一直在！
I2C0 @100000 Hz: 同样三个
```

**总线是好的，控制器也在。** 于是问题收窄到"读到了什么、我们怎么判断"。

**根因**：产品 ID 寄存器 `0x8140` 返回 4 字节 ASCII，GT911 实际回 `"911" + 0x00`
（NUL 补齐）。而原校验要求**四个字节全部**可打印：

```c
for (i = 0; i < GT911_ID_LEN; i++)      /* GT911_ID_LEN = 4 */
  if (id[i] < 0x20 || id[i] > 0x7e)
      return false;
```

第 4 字节的 `0x00` 必然 `return false` —— **I2C 读明明成功了，答案被校验器扔了**。

**修复**：按 GT9xx 产品 ID 的真实格式校验（首字节为数字、前 3 字节可打印、第 4 字节
允许 NUL 补齐），并**无条件打印原始 ID 字节**：

```
GT911: raw ID at 0x5d = 39 31 31 00
GT911: product ID "911" at 0x5d
GT911 touchscreen registered at /dev/input0 (0x5d)
```
`39 31 31 00` = `"911"` + NUL，与被拒的那个字节对上，根因闭环。

**一个被自己推翻的假设（诚实记录）**：排查中我发现摄像头跑 100 kHz 而 GT911 探针跑
400 kHz，且触摸通路比摄像头多两个连接器 + 两条 FPC，于是判断"400 kHz 超出上升时间
预算"。**扫描结果直接证伪了它**——GT911 在 400 kHz 下照样应答。最终把频率改成
100 kHz 只是**余量选择**（与已在 100 kHz 运行的摄像头统一），`board.h` 注释里写明了
"这不是根因"，避免后人误读。

**方法论教训**：
> "设备不应答"在共享总线上是**有歧义**的。一条静默的失败探针无法区分
> "器件不在/没供电" 与 "器件在、但我们读/判的方式不对"。
> **花 10 行代码做一次全地址 × 多速率扫描**，就把这个歧义彻底消掉了 ——
> 这比继续换着法子怀疑硬件便宜得多。这次证据也在**日志本身**：
> 加了 `raw ID = 39 31 31 00` 之后，一眼就能看出第 4 字节是 0x00。

**真机验证**：`/dev/input0` 正常注册；`lvgldemo`（LVGL widget demo）前台运行期间
`/dev/fb0` + `/dev/input0` 同时打开成功、系统稳定（ping 2–4 ms）。
⚠️ `lvgldemo` 必须**前台**运行：`lvgldemo &`（后台）会触发一次任务栈 dump 并把系统
搞死，这是另一个待查问题（见下）。

### 23.10 ✅ `cmd &` 必崩 —— 是 openvela 自己引入的回归，不是 LVGL 的问题

#### 现象：**任何**后台命令都崩，前台全正常

```text
nsh> free &
riscv_exception: EXCEPTION: Load access fault. MCAUSE: 00000005, EPC: 4fc1b674, MTVAL: 00000000
riscv_exception: PANIC!!! Exception = 00000005
dump_assert_info: ... task: nsh_main process: nsh_main
up_dump_register: PC: 4001fdca  SP: 4ff4b108  ...
dump_tasks:   ----   --- --- -------- ------- --- ------- ---------- ---------------- 0x4ff4aa30      2048   irq
```

原先记的是"`lvgldemo &` 会崩、前台正常"，看着像 LVGL 的线程/栈问题。
**先做了一次对照实验**：把 `lvgldemo &` 换成最简的 `free &` —— **同样崩，寄存器现场一模一样**。
于是问题定义立刻从"LVGL 后台运行"纠正为"**NSH 的后台路径整体坏了**"，后面所有定位都建立在这一点上。

#### 定位链（每一步都有证据）

1. **panic 现场**：`EPC=0x4fc1b674`（ROM 区）、`MTVAL=0`（**空指针解引用**）。
   ⚠️ 一开始我把 "SP 落在 `irq` 栈上" 误读成"故障发生在中断上下文"。
   后来读 `_interrupt_handler` 汇编才发现它的入口逻辑是：
   `addi sp,sp,-132` 先压帧 → 再用 `blt sp,g_intstackalloc` / `blt t0,sp` 判断，
   **只要当前栈不在 irq 栈区间就 `mv sp,t0` 切到 irq 栈再分发**。
   所以**普通任务异常也会显示 irq 栈** —— 结论修正为「任务上下文异常」。

2. **反汇编 ROM**（该地址不在任何 ROM 符号表里，用 OpenOCD 读回字节后本地反汇编）：
   ```asm
   4fc1b658:  addi sp,sp,-16 ; ...
   4fc1b65e:  add  a3,a0,a2          # end = a0 + n
   4fc1b664:  bne  a5,a3,scan        # 在 a0..a0+n 里扫 0 字节
   4fc1b670:  mv   a4,a1             # a4 = src
   4fc1b672:  li   a0,1
   4fc1b674:  lbu  a3,0(a4)          # ← 崩溃点：a4 = NULL
   ```
   是 ROM 里的字符串处理例程，**被用 `src = NULL` 调用**。

3. **栈上返回地址回溯**：`0x4ff40182` = `_interrupt_handler`、`0x4ff41238` = `riscv_doirq`、
   `0x40028dea` = **`nsh_execute`**。反汇编 `0x40028dd4` 附近：
   ```asm
   40028dda: lw   a1,0(a5)               # a1 = argv[i]
   40028ddc: li   a2,80                  # == CONFIG_NSH_LINELEN
   40028de0: mv   a0,s2
   40028de2: jalr -> 4fc00300 <strlcat>  # strlcat(dst, argv[i], 80)
   40028dea: bge  s4,s6, ...             # ← 与栈上的 ra 完全吻合
   ```
   → **崩溃就是 `strlcat(dst, NULL, 80)`**。

4. **源码对上**：`apps/nshlib/nsh_parse.c` 的 `nsh_execute()` 后台分支
   （`#ifndef CONFIG_NSH_DISABLEBG`）：
   ```c
   if (vtbl->np.np_bg)
     {
       sh_arg2 = lib_get_tempbuffer(CONFIG_NSH_LINELEN);
       sh_arg2[0] = '\0';
       for (ret = 0; ret < argc; ret++)                 /* ← 循环到 argc，含 argv[argc] */
         strlcat(sh_arg2, argv[ret], CONFIG_NSH_LINELEN);
       ...
       sh_argv[0] = "sh"; sh_argv[1] = "-c"; sh_argv[2] = sh_arg2; sh_argv[3] = NULL;
       /* np.np_bg still there ... */
       ret = nsh_execute(vtbl, 4, sh_argv, param);      /* ← np_bg 仍为 true，递归 */
     }
   ```
   它把命令包成 `sh -c "<cmdline>"` 再**递归**调用 `nsh_execute`，
   并依赖**它上面那段 builtin 派发**（`nsh_fileapp()`）在递归里提前 `return` 来终止递归。

5. **回归来源**：openvela commit **`7d54946ab`**（2025-09-09，"Add support to run builtin
   dirrectly as command"）恰好把那段派发改成了条件编译：
   ```diff
   -#ifdef CONFIG_NSH_BUILTIN_APPS
   +#if defined(CONFIG_NSH_BUILTIN_APPS) && !defined(CONFIG_NSH_BUILTIN_AS_COMMAND)
      ret = nsh_builtin(...) / ret = nsh_fileapp(...);
   ```
   → `CONFIG_NSH_BUILTIN_AS_COMMAND=y` 时**整段派发被编译掉**，递归回来的 `sh -c` 又落进后台分支，
   这次 `argc=4`，循环走到 `ret=3` 取 `argv[3]=NULL` → `strlcat(dst, NULL, 80)` → ROM 空指针。

#### 因果链（一句话）

> 我们为了让 `ai_agent` 能从 NSH 直接启动而打开 `CONFIG_NSH_BUILTIN_AS_COMMAND=y`
> → openvela `7d54946ab` 让该选项把 builtin 派发整段编译掉
> → `nsh_execute()` 后台包装的递归失去终止条件
> → 递归第二次进来时 `strlcat()` 拿到 `argv[3] == NULL`
> → ROM 里 `lbu a3,0(a4)` 空指针 → Load access fault。

**同一个选项还造成了另一个后果**：`nsh_command()` 在 `CONFIG_NSH_BUILTIN_AS_COMMAND` 下是
`return (builtin->main)(argc, argv);` —— **就地进程内调用**（Kconfig 帮助原文：
"run builtin application directly without creating a separate thread"）。
这正是 `ai_agent` 跑在 `nsh_main` 栈上、逼我们把 `CONFIG_DEFAULT_TASK_STACKSIZE`
从 2048 提到 16384 的原因。

#### 修复：换回 NuttX 的标准派发路径

```diff
- CONFIG_NSH_BUILTIN_AS_COMMAND=y
+ # CONFIG_NSH_BUILTIN_AS_COMMAND is not set
+ CONFIG_LIBC_EXECFUNCS=y
```

`nsh_fileapp()` 内部本来就处理 builtin（`builtin_isavail()` → `task_spawn(name, main,
..., attr(stacksize = builtin->stacksize))`），并遵守 `np_bg`（后台不 `waitpid`）。
一处改动同时解决两个问题：

| | 修复前 | 修复后 |
|---|---|---|
| `cmd &` | 递归进后台分支 → NULL 解引用 → panic | 递归被 `nsh_fileapp()` 提前 `return` **根本到不了后台分支** |
| `ai_agent` 栈 | 借用 `nsh_main` 的栈（需把默认栈提到 16 KB） | 拿 `.bdat` 里注册的 **32 KB 独立任务栈** |

#### 方法论教训

> **"看似 app 专属"的崩溃，先用最简命令做一次对照实验。**
> `lvgldemo &` → `free &` 只花了一分钟，却把问题定义从"LVGL 线程模型"
> 纠正到"NSH 后台包装递归"，避免在错误的问题上继续深挖。
>
> 第二条：**RISC-V 的陷阱入口会切到 irq 栈**，"SP 在 irq 栈上"≠"中断上下文出错"。
> 应先读 `_interrupt_handler` 汇编确认栈切换规则，再下结论。
>
> 第三条：遇到"某个开关一打开就崩"，**先看这个开关在上游是怎么被引入的**。
> 这次 `git log -S` 一眼就找到 `7d54946ab`，看清了它砍掉的正是递归的终止条件 ——
> 比在寄存器层面继续猜快得多。

#### 验证状态（诚实记录）

| 步骤 | 状态 |
|---|---|
| 根因定位（反汇编 + 栈回溯 + 源码 + `git log -S`） | ✅ 证据链完整 |
| "修复 A"落地（`NSH_BUILTIN_AS_COMMAND=n` + `LIBC_EXECFUNCS=y`） | ✅ 编译通过、**真机可启动并联网**（`ping` 通） |
| **"修复 A" 真机跑 `cmd &`** | ❌ **失败：会把系统卡死**（见下） |
| **已回退到原配置** | ✅ 真机复验：启动 + 联网正常（`ping` 3/4，4–10 ms） |

##### 🔴 "修复 A"为什么被回退 —— 一个更危险的副作用

因为 console 的 CP2102 掉线（§23.11），没法手敲 `free &`，于是做了一个
**不依赖串口**的自检：在 `esp_bringup()` 里起一个任务，自动驱动 NSH，
用一个**全局状态字**（`g_bgselftest_state`，OpenOCD 直接读内存）记录进度，
并用 **`g_system_ticks` 是否推进 + `ping` 是否回包** 作为"系统是否还活着"的判据。
（这招很好用 —— 能精确区分"没输出"和"没起来"。）

结果：

| 自检步骤 | 结果 |
|---|---|
| `system("free")`（前台对照） | ❌ 系统卡死（ticks 冻结） |
| 直接 `task_spawn("sh", sh_main, "-c free")` | ❌ 系统卡死 |
| 直接 `task_spawn("lvgldemo", lvgldemo_main)`（**非 NSH 的普通应用**） | ❌ 系统卡死（~5.3 s，正好在 spawn 处） |
| 对照：改回原配置后启动 | ✅ `ping` 正常 |

**结论**：在这套移植上，`nsh_fileapp()` → `task_spawn()` 派发 builtin 会**卡死整个系统**。
而 `CONFIG_NSH_BUILTIN_AS_COMMAND=n` 之后，**所有 builtin 都走这条路**——
`ai_agent` / `lvgldemo` / `camera`（演示的全部 app）都会起不来。
**这比原来的 `&` 崩溃严重得多**，所以果断回退。

顺带确认了两个独立事实（都值得记）：
- **`apps/system/system/system.c` 的 `system()` 在 openvela 下不可用**：
  它走 `task_spawn("system", nsh_system, ...)`，同样卡死。
  之前所有"用 `system()` 做个自检"的想法都不成立。
- 串口不可用时，**`g_system_ticks` + `ping` 是一对很好的"活体探针"**：
  前者能证明调度器还在跑，后者能证明系统走完了启动。

**下一步（需要可用 console 才能安全推进）**：
1. 恢复 CP2102，手敲 `free &` 复验"修复 A"是否真的卡死还是在别处；
2. 若确认 `task_spawn` 在 NSH 上下文可用（而在 bring-up 上下文不可用），
   则"修复 A"仍可成立；
3. 否则改用**外科式补丁**：保留 `BUILTIN_AS_COMMAND=y`，只在
   `nsh_execute()` 的后台分支加"只包装一次"的保护，彻底消掉递归，
   代价是 `cmd &` 变成同步执行（但至少不崩）。


### 23.11 🔴 尝试把 console 换到 USB-JTAG —— 失败，但换来一条重要结论

**动机**：本轮 `cmd &` 定位做到一半，**板载 CP2102（UART0 ↔ `/dev/ttyUSB0` 的桥）突然从
USB 总线上消失**（`lsusb` 里 `10c4:ea60` 直接没了，是 VMware 直通层面的掉线）。
UART0 的 console 就再也没有 host 侧读者了 —— 整个交互式调试被一根线卡死。

于是想到：**USB-Serial/JTAG（`/dev/ttyACM0`）和 esptool 烧录用的是同一根线**，
如果让它当 console，就只剩一根线，彻底去掉这个单点。

**做法**：`CONFIG_ESPRESSIF_USBSERIAL=y`（并修掉 `esp_serial.c` 里 `CONSOLE_DEV` 被
UART 分支与 USBSERIAL 分支**重复定义**的问题 —— 那条重复定义会以 warning 的形式
把"console 其实已经不是 UART 了"这件事藏起来）。

**结果：失败，而且是硬失败。**

```text
[esp32p4] [INF] start=0x4ff47de8
I (10185) esp_psram: Found 32MB PSRAM device
I (10188) hex_psram: psram CS IO is dedicated
        ← 到此为止，之后什么都没有
```

- 串口读不到任何 NuttX 输出；
- **板子不再响应 ping**（说明不是"只是没输出"，而是根本没起来）；
- OpenOCD 读回 `Halt cause (5) - (PMP Load access fault)`，PC 停在 `_interrupt_handler`
  里 —— 卡在 panic 循环。

**结论**：在这套 **MCUboot 二级引导 + flash XIP** 的配置下，USB-Serial/JTAG
**不能**当 console，它会挂在 console bring-up 那一步（正好是 PSRAM 初始化之后）。
已回退到 UART0 console，并把这次尝试的结论写进 `defconfig` 注释，
免得后人再花一轮去试。

**顺带留下的东西**：`esp_serial.c` 里的 `CONSOLE_DEV` 重复定义防护保留了 ——
`CONFIG_ESPRESSIF_USBSERIAL` 未启用时它**零行为变化**，但下次谁再打开这个开关，
会立刻编译报错/告警而不是被静默遮蔽。

**方法论教训**：
> 一个"看起来只是换个通道"的改动，可能直接让板子起不来。
> 好在 `ping` 就是一个**零成本、不依赖串口**的"系统是否走完启动"探针 ——
> 这次正是它把"没输出"和"没起来"区分开的。

### 23.12 🟡 摄像头 DW_GDMA 中断：根因确认 + 修复已就位（待复验）

开机日志里摄像头一直是这条：

```text
SC2336 chip ID: 0xcb3a
E intr_alloc: No free interrupt inputs for DW_GDMA interrupt (flags 0x10E)
E dw-gdma: dw_gdma_install_channel_interrupt(641): alloc interrupt failed
E dw-gdma: dw_gdma_channel_register_event_callbacks(676): install interrupt service failed
E CSI: esp_cam_new_csi_ctlr(238): failed to register dwgdma callback
ERROR: esp_csi_imgdata_initialize failed: -5
ERROR: failed to initialize the camera: -5
```

**根因链**：

1. `flags 0x10E` = `ESP_INTR_FLAG_SHARED(0x100) | LOWMED(0x0E)`
   —— 摄像头**本来就是在申请共享中断**，不是它没申请。
2. `get_available_int()` 先按 source 找已有向量，再用 `is_vect_desc_usable()` 判断能否复用；
   其中有一条：
   ```c
   if (vd->flags & VECDESC_FL_NONSHARED) {   /* 已被"非共享"占用 */ return false; }
   ```
3. 而 **我们的 DSI 驱动**（`esp_mipi_dsi.c`）是这样占的：
   ```c
   ret = esp_setup_irq(DW_GDMA_INTR_SOURCE, ESP_IRQ_PRIORITY_DEFAULT,
                       ESP_IRQ_TRIGGER_LEVEL, esp_mipi_dsi_dma_isr, priv);
   ```
   走的是 **非共享** 路径（`esp_setup_irq` → `esp_intr_alloc_intrstatus` 不带 `SHARED`），
   于是这条 CLIC 线被打上 `NONSHARED`。
4. 摄像头随后对**同一个** `DW_GDMA_INTR_SOURCE` 申请**共享** → 被上面那条判据拒绝 →
   退回去遍历 32 条 CLIC 线 → 其余线也都不可用 → `ESP_ERR_NOT_FOUND` → 摄像头初始化失败。

**而 DW_GDMA 本来就是共享外设** —— ESP-IDF HAL 自己写得很清楚
（`upper_hal_dma/src/dw_gdma.c`）：

```c
    // DW_GDMA multiple channels share the same interrupt source, so we use a shared interrupt handle
    int isr_flags = DW_GDMA_INTR_ALLOC_FLAGS | ESP_INTR_FLAG_SHARED;
    esp_intr_alloc_intrstatus(ETS_DW_GDMA_INTR_SOURCE, isr_flags,
                              dw_gdma_ll_get_intr_status_reg(hal->dev),
                              DW_GDMA_LL_CHANNEL_EVENT_MASK(chan_id),
                              dw_gdma_channel_default_isr, chan, &intr);
```

HAL 用「共享 handle + **每通道 status mask**」解复用；**我们的 DSI 驱动是这套模型里唯一的例外**。

**修复**（`arch/risc-v/src/common/espressif/esp_mipi_dsi.c`）：让 DSI 也按共享方式注册，
并复用 HAL 同一套 status 寄存器 + 通道掩码：

```c
ret = esp_setup_irq_with_flags_intrstatus(
        DW_GDMA_INTR_SOURCE,
        ESP_INTR_FLAG_SHARED | ESP_INTR_FLAG_LOWMED,
        (uint32_t)(uintptr_t)dw_gdma_ll_get_intr_status_reg(dev),
        DW_GDMA_LL_CHANNEL_EVENT_MASK(ESP_MIPI_DSI_DMA_CHAN),
        esp_mipi_dsi_dma_isr, priv);
```

要点：
- **IRAM 位必须保持不设**，与 HAL 的 `0x10E` 一致 ——
  `is_vect_desc_usable()` 会拒绝"共享但 IRAM 属性不匹配"的线；
- 共享分发（`shared_intr_isr`）在 `statusreg`/`statusmask` 命中时才会调用对应 ISR，
  所以 DSI 与摄像头各自的 ISR 互不打扰；
- DSI 的 ISR 只读/清自己的通道状态（`ESP_MIPI_DSI_DMA_CHAN = 0`），本来就安全。

**验证状态**：修复已进源码并编译通过；开机日志复验同样被 §23.11 的串口问题阻塞，待补。

### 23.13 🛠 运维经验：改了 `.config` 之后，mcuboot 的 ExternalProject 会来咬你

本轮为了改配置反复 reconfigure，**连续被 CMake 的 mcuboot ExternalProject 拦住**，
每次都要重来一遍。踩过的坑按顺序记下来（这条以后一定会再遇到）：

1. **reconfigure 会让 ExternalProject 的 stamp 全部失效。**
   `nuttx/CMakeLists.txt` 里 `.config` 的重新生成条件是
   `NOT EXISTS ${CMAKE_BINARY_DIR}/.config OR 路径变了` ——
   **光改 defconfig 不会触发**，必须删掉 `.config` 再跑 cmake。
   而 cmake 一跑，`bootloader-gitinfo.txt` / `bootloader-gitclone.cmake` 等被重新生成，
   **mtime 变新 → ninja 判定整条 bootloader 链脏** → 去 `git clone` mcuboot。

2. **`git clone` 会失败两次**：
   - 用户 `~/.gitconfig` 里有 `url.https://gh-proxy.com/https://github.com/.insteadof`，
     把所有 github clone 劫持到 gh-proxy，而它当前返回 **403**；
   - mcuboot 的 `--recursive` 子模块里有 **cypress PSoC6 那一堆**（`mtb-pdl-cat1` 等），
     与 ESP32-P4 毫无关系，实测 **~58 KB/s**，全拉要一小时。
   → 解决：构建时 `GIT_CONFIG_GLOBAL=/dev/null` 绕开代理直连 github。

3. **`bootloader-gitclone.cmake` 有短路开关**（省掉整个 clone）：
   ```cmake
   if(NOT "<gitinfo.txt>" IS_NEWER_THAN "<gitclone-lastrun.txt>")
     message(STATUS "Avoiding repeated git clone, stamp file is up to date")
     return()
   endif()
   ```
   把 `gitinfo.txt` 的 mtime 设旧、`gitclone-lastrun.txt` 设新，clone 直接跳过。

4. **`bootloader-gitupdate.cmake` 也会短路**：源码已经在 pinned commit 上时，
   它打印 "Already at requested ref" 并 `return()`，不联网。

5. **`bootloader-patch` 这一步真的需要 `ext/mbedtls-3.6.0` 子模块**，
   而 mbedtls 全历史克隆同样很慢。做法：取 gitlink 记录的 SHA 后**浅克隆精确 commit**：
   ```bash
   git -C "$MC" ls-tree HEAD ext/mbedtls-3.6.0     # -> 2ca6c285...
   mkdir -p "$MC/ext/mbedtls-3.6.0" && cd "$MC/ext/mbedtls-3.6.0"
   git init -q && git remote add origin https://github.com/ARMmbed/mbedtls
   GIT_CONFIG_GLOBAL=/dev/null git fetch --depth 1 origin 2ca6c285...
   git checkout -q FETCH_HEAD
   git -C "$MC" config submodule.sim/mbedtls.url https://github.com/ARMmbed/mbedtls
   git -C "$MC" config submodule.sim/mbedtls.active true
   ```
   再把它自己的 `framework`（mbedtls 测试框架，与构建无关）标成不更新：
   ```bash
   git -C "$MC/ext/mbedtls-3.6.0" config submodule.framework.update none
   git -C "$MC/ext/mbedtls-3.6.0" config submodule.framework.active false
   ```

6. **ninja 的 `.ninja_log` 还会记"命令行哈希"**：只要这一步**从未成功执行过**，
   它永远判脏（`ninja explain: command line changed`），改 mtime 没用。
   所以最终还是要让它**成功跑一次**，之后才能靠 mtime 短路。

**一句话**：改 `.config` 的代价不只是重编，还包括**把 mcuboot 的 ExternalProject 重新拖一遍**。
做完配置改动后，构建前先按上面 3/4/5 把环境铺好，可以省掉十几分钟和大量无谓下载。




### 23.14 ✅ 摄像头修好了（真机验证）+ 三个新根因

CP2102 恢复后，终于能读 console 了。这一轮把之前被串口阻塞的事全部补做，
**结果是：一个修复确认有效，同时又挖出三个新问题**。

#### ✅ 1. 摄像头 DW_GDMA 修复 —— 真机验证通过

`§23.12` 的 DSI 共享中断改动，烧录后启动日志：

```text
SC2336 chip ID: 0xcb3a
esp_csi_data_init: CSI: 1920x1080, 2 lane(s) @ 405 Mbps, fb=2592000 bytes (align 64), ...
Camera registered on /dev/video0          ← 之前这里是 5 行 ERROR + 初始化失败
```

`ls /dev` 里出现了 **`video0`**。**摄像头正式打通**（V4L2 设备已注册）。
修复要点（`esp_mipi_dsi.c`）：DSI 改用 `ESP_INTR_FLAG_SHARED | ESP_INTR_FLAG_LOWMED`
注册 DW_GDMA 中断，不再独占那条 CLIC 线。

#### ⚠️ 2. 中途踩的坑：共享注册时**不能**传 status 寄存器

第一版我照 HAL 的写法传了 `dw_gdma_ll_get_intr_status_reg(dev)` +
`DW_GDMA_LL_CHANNEL_EVENT_MASK(chan)`。结果：

- 启动日志一切正常、`/dev/fb0` 照常注册；
- 但**屏幕永远停在第一帧**（往帧缓冲里改内容，面板毫无反应）；
- 在 `esp_mipi_dsi_dma_isr` 下断点 —— **从不命中**；`wait_halt` 超时。

原因：`shared_intr_isr()` 只在 `*statusreg & statusmask` 成立时才调用该 ISR，
而这套掩码在 DSI 这条路径上没有命中，于是 `esp_mipi_dsi_dma_restart()` 再也不被调用，
DW-GDMA 传完第一帧就停了。

**修法**：改用 `esp_setup_irq_with_flags()`（内部 `intrstatusreg = 0`），
让共享分发器**无条件调用** DSI 的 ISR —— 等价于改动前的非共享行为，
同时仍然允许摄像头共用同一条线。DSI 的 ISR 本来就只读写自己的通道状态，安全。

#### 🔴 3. 新根因（P1）：面板只显示第一帧 —— 和我的改动无关

把 `esp_mipi_dsi.c` **还原成原始版本**再测，`esp_mipi_dsi_dma_isr` 断点**同样不命中**。

为了排除"断点机制本身不灵"，加了阳性对照：在 `riscv_doirq`（每次中断都经过）下断点 ——
**立刻命中**（`pc = 0x4ff411b0`）✓。所以结论是硬的：

> **DW_GDMA 的完成中断从来没有到达过 CPU。**
> DSI 不靠中断重载 DMA → 面板只显示第一帧 → 永远"纯蓝"。

而"纯蓝"的成因也查清了：帧缓冲里是 `0xF800`，正是 LVGL 默认主题的蓝色 `0x001F`
做了 **R/B 字段交换**。也就是说**画面通路本身是好的**，只是内容不再更新。

**这一条和摄像头的问题其实是同一个根源家族**：DW_GDMA 的中断在这套移植上没有被正确送达。
摄像头当初就是"申请不到中断线"，DSI 是"申请到了但中断不来"。

### 23.15 🔴 又一个真根因：`up_enable_irq()` 从不置位 CLIC IE（影响面很大）

追显示问题时，顺着 `up_enable_irq()` 读下去，发现一个**独立的真 bug**：

```c
/* esp_irq.c, 修复前 */
void up_enable_irq(int irq)
{
  intr_handle_t intr_handle = esp_get_handle(this_cpu(), irq);
  if (intr_handle == IRQ_UNMAPPED) { irqwarn(...); return; }
  ret = esp_intr_enable(intr_handle);        /* ← 只有这一句 */
  ...
  /* 注释写着："CLIC IE 位已由 esp_intr_alloc() 置好，无需再写" */
}
```

**但这个前提是错的**，链条如下（都能在源码里逐行核对）：

1. `esp_setup_irq_intrstatus()`（由 `esp_setup_irq()` 调用）**总是**带上
   `ESP_INTR_FLAG_INTRDISABLED`；
2. `esp_intr_alloc_intrstatus()` 先 `ESP_INTR_ENABLE(intr)`（置 CLIC IE），
   末尾又因为 `INTRDISABLED` 调用 `esp_intr_disable(ret)` → **把 IE 清掉**
   （`intr_alloc.c:675-677`）；
3. `esp_intr_enable(handle)` 在 **source >= 0** 时只做
   `esp_rom_route_intr_matrix(...)` —— **重连路由矩阵，不写 CLIC IE**
   （`intr_alloc.c:888`，`ESP_INTR_ENABLE()` 那个分支只走 `source < 0`）；
4. 真正置 IE 的是 `esp_intr_enable_source(inum)` → `esp_cpu_intr_enable(1 << inum)`
   （`intr_alloc.c:1016`）—— **没人调用它**。

> **结论：凡是走 `esp_setup_irq()` + `up_enable_irq()` 这条路的驱动，
> 它的 CLIC 线永远是 disabled，中断永远送不到 CPU。**

**修复**（`esp_irq.c`）：在 `up_enable_irq()` 里补上
`esp_intr_enable_source(esp_intr_get_intno(intr_handle));`
—— 用**真实分配的 intno**，而不是外设 source 号。

**顺带纠正上一轮的一个判断**：之前审查时发现过一行
`esp_intr_enable_source(ESP_IRQ2SOURCE(irq))`，判定"source 不是 intno，参数错了"
于是**整行删掉**。参数确实错了（`1 << source` 对 ETH_MAC=92 还是 UB），
但**删除的同时把一个必需的动作也删掉了** —— 正确的做法是**用对的参数把它加回来**，
而不是删掉。这条教训值得记：*"这行参数错了" 不等于 "这行不该存在"*。

**验证状态**：
- 修复已编进固件（反汇编 `up_enable_irq` 可见 `j esp_intr_enable_source`）✓；
- 板子启动 / 联网 / 摄像头注册 **均无回归** ✓；
- ⚠️ **但显示问题没有因此解决**：DSI 的 `esp_mipi_dsi_dma_isr` 断点**仍然不命中**，
  说明 DW-GDMA 的中断还有一层原因（外设侧没有拉起来，或另一处使能缺失），
  这一条留给下一步。

### 23.17 显示问题的寄存器级定位（外设侧正常，卡在"送达 CPU"这一段）

用 OpenOCD 读 DW-GDMA（基址 **`0x500a0000`**，用 `g_esp_mipi_dsi.dw_hal.dev` 反查得到）：

| 寄存器 | 值 | 含义 |
|---|---|---|
| `id0` (+0x00) | `0x3134312a` | DW-GDMA 控制器识别正常 |
| `compver0` (+0x08) | `0x00000b06` | 版本寄存器可读 |
| **`int_st0` (+0x30)** | **`0x00000019`** | **通道 0 中断状态位已置起（bit0）** |
| `chen0` (+0x18) | `0` | 通道已停（只传了一帧） |

**结论：外设侧没问题 —— 中断确实被拉起来了，只是送不到 CPU。**
所以 DSI 的 `esp_mipi_dsi_dma_isr` 永远不会执行，`esp_mipi_dsi_dma_restart()` 永远不被调用，
DMA 传完第一帧就停 → **面板永远停在第一帧**。

**一条重要的测量教训**：
`0x20801000` 这段 CLIC 控制寄存器经 **JTAG 读出来全是 0**，但中断明明工作正常
（UART / EMAC / timer 都在跑）。这与之前会话的发现一致：
> "tick 中断能触发（intctl 全 0 也触发）—— P4 的中断触发不完全依赖 intctl，
> 使能位图另有其位。"

**所以 CLIC 寄存器不能作为"中断有没有被使能"的判据**，用它会得出错误结论。
判断"中断有没有送达"目前最可靠的办法是 **在该 ISR 上下断点**（并配一个阳性对照，
比如在 `riscv_doirq` 下断点确认机制本身可用）。

**下一步的确定方向**（外设已确认拉中断，所以只剩送达链路）：
1. DW-GDMA 的中断**信号使能**（per-channel `int_sig_ena` / 全局 `int_sig_ena0` @ +0x48）是否打开
   —— `int_st0` 只表示"状态位"，不等于"信号已输出到中断矩阵"；
2. `esp_rom_route_intr_matrix(cpu, DW_GDMA_INTR_SOURCE, intno)` 是否真的把这根 source
   接到了 CLIC 线上（可读 intr matrix 寄存器核对）；
3. CLIC 线的 IE / level 配置（但注意上面那条测量教训，别只看 intctl 读回值）。

## 摄像头（MIPI-CSI / SC2336）接收链路排查结论

**结论：驱动软件链路已逐级证伪，故障在摄像头模组 / 其 MIPI 高速链路上（硬件）。**

### 已逐项验证为正确的部分

| 环节 | 验证证据 |
| --- | --- |
| 传感器身份 | 上电读回 chip ID `0xcb3a`，与 `SC2336_PID` 完全一致 |
| 传感器寄存器表 | 与 Espressif 官方 `sc2336_mipi_2lane_24Minput_1920x1080_raw10_30fps` **逐条一致**（149/149，无缺失/多余/取值差异） |
| 开流时序 | 与官方驱动一致（`0x0100=0x01`，回读 `0x01`） |
| CSI Host | 总线时钟已开、`csi2_resetn=1`、`phy_shutdownz=1`、`dphy_rstz=1`、2 lane、PHY 参考时钟 `PLL_F20M` 已使能 |
| CSI Bridge | 模块时钟已开、桥时钟 `host_ctrl=0x3`、`csi_en=1`、1920x1080、RAW10 (0x12–0x2f)、burst 512 |
| DW-GDMA | `dmac_en=1`、通道已武装（`sar`=桥 FIFO、`dar`=帧缓冲、`block_ts`=324000 恰好一帧 RAW10）；**同一控制器被 DSI 通道证明可用**（其 `sar` 在逐帧轮转） |
| 资源冲突 | DSI 改用 ch1、摄像头 ch0，冲突已解 |

### 关键判据

打开传感器**内部测试图案**（`0x4501` bit3）后，D-PHY 状态显示
`phy_rx=0x00030000`（bit17 `rxclkactivehs=1`，clock lane 处于 HS）、
`stopstate=0`（各 lane 均未停），即**传感器确实在发送**；
但 CSI Host 既**不产生任何 packet**、也**不报任何错误**（`int_st_main` 清零后持续为 0），
桥 FIFO 为空、DMA 从不触发。

「模拟状态正常 + 数字侧零 packet 零错误」= **D-PHY 收到的数据没有送达 Host 的包解析器**，
属于物理层问题，而非寄存器配置问题。

### 重要教训（避免再次误判）

- **`bridge int_raw` 不是"收到数据"标志**，其位定义全是错误位
  （`vadr_num_gt/lt`、`discard`、`buf_overrun`、`async_fifo_ovf`），
  全 0 只代表"无错误/无丢弃"，**不能**据此判断"没有数据"。
- **`n_lanes` 是被编码过的**：`mipi_csi_host_ll_set_active_lanes_num()` 写入的是 `lanes_num - 1`，
  读到 1 表示 **2 lane**（正确），不是 1 lane。
- **`phy_rxclkactivehs` 才是"时钟 lane 是否在 HS"的判据**；
  `rxulpsclknot` 默认即为 1，不携带信息。
- **寄存器偏移必须用 host 编译的 `offsetof()` 核实**：
  bridge `clk_en`@0x00、`host_ctrl`(csi_enableclk)@**0x40**；
  曾误把 0x00 的 `clk_en`（默认 0，含义仅为"时钟门控使能"）当成"桥时钟没开"。
- **严禁用 CPU 直接读桥数据 FIFO `0x50104000`**：该地址只能由 DW-GDMA 访问，
  CPU load 会挂死总线（实测直接 task dump + 板子失联）。

### 现场可复现的诊断开关

- `nuttx/arch/risc-v/src/common/espressif/esp_csi.c`：`#define ESP_CSI_CAPTURE_DIAG 1`
  开启后，首帧启动 3 秒后连续打印 4 组 host/bridge/DW-GDMA 寄存器快照。
- `nuttx/drivers/video/sc2336.c`：`#define SC2336_TEST_PATTERN 1`
  开启传感器内部测试图案，用于区分"采集链路坏"与"传感器不发送"。

### 下一步（需硬件动作）

上游 `espressif/esp-video-components` issue #53 记录了**同一块板 + 同一颗 SC2336 的完全相同症状**，
其最终处理结果是**更换摄像头模组后恢复正常**（原模组硬件故障）。
本板建议同样先重插/更换摄像头排线与模组，再用上面的诊断开关复测。

### 复测更新（重插摄像头模组后）

用户重插摄像头模组后复测，**结论不变**，并又排除两条假设：

| 假设 | 实验 | 结果 |
| --- | --- | --- |
| 控制器在传感器未开流时被武装，桥锁死错误态 | 在传感器确认在流后 `stop`+`start` 重新武装，之后 2 秒内 4 次采样 `dar` | **静止 → 证伪** |
| PHY 的 `hs_freq_sel` 与实际 lane rate 不匹配 | 单次烧录内自动扫 `0x25/06/14/15/22/19/16/0a/04`（覆盖 90–1099 Mbps），逐个写 PHY 寄存器 0x44 后采样 | **9 个值全部零数据 → 证伪** |

**判据教训**：重新武装本身会用新缓冲区重写 `dar`，因此「武装前后各采一次 `dar`」是无效判据
（我据此一度误报 MOVING）。正确做法是**武装之后**连续多次采样，看 `dar` 在采样之间是否移动。

复测后仍为：`ch0 dar` 完全静止、`brg int_raw=0`、`buf_depth=0`、Host 零 packet 零错误，
而 D-PHY 报告 `rxclkactivehs=1`、`stopstate=0`（传感器确实在发）。

**最终判断：软件侧已无剩余可调项（Host 全部 42 个寄存器已覆盖），故障在摄像头模组/其 MIPI 高速链路，
需更换模组验证。**

# 二十四、消除部署步骤：交付物做到「repo sync 即可构建」（9/17）

> 📌 **本阶段核心**：评审复现路径里最后一步手工操作 —— `deploy.sh <工作区>`
> （rsync 覆盖 + 按 `.deleted-files` 删除 8 个上游文件）—— 是唯一的"非 manifest 环节"。
> 本节把它彻底省掉：**交付物只用 `<copyfile>` 表达，评审 init → sync → build 三步到底。**

## 24.1 那 8 个删除从哪来（旧方案的由来）

移植对齐的是较新的 NuttX 公版，公版早已把一批旧驱动删掉/改名，于是旧方案直接把这 8 个文件
从文件树里"删除"：

| 被删的上游文件 | 现在的替代 |
|---|---|
| `esp_timer.c` / `esp_timer.h` | `esp_timer_adapter.c` ＋ ESP-IDF HAL `components/esp_timer` |
| `esp_hr_timer.c` | 同上（`esp_hr_timer.h` 保留，作为对外 HR timer API 头）|
| `esp_wlan.c` / `esp_wlan.h` / `esp_wifi_init.c` | `esp_wlan_netdev.c`（netdev 路径）|
| `esp_dma.c` / `esp_dma.h` | 改由 esp-hal-3rdparty 的 DMA 组件提供 |

**为什么删除只能用脚本做**（`repo` 源码级结论）：

| 机制 | 能否表达"删除" | 依据 |
|---|---|---|
| `<copyfile>` | ❌ 只能复制/覆盖（还会把目标 chmod 去掉写位） | `project.py::_CopyFile._Copy()` |
| `<linkfile>` | ❌ 对已存在的**真实文件**不生效 | `_LinkFile.__linkIt()` → `platform_utils.removedirs()` 明确"不删用户内容"，随后 `symlink()` EEXIST 报错 |

→ 于是复现路径里多出第 2 步 `deploy.sh`：**rsync 覆盖（copyfile 已能覆盖）＋ 按清单删除（唯一不可替代的能力）**。

## 24.2 解法：不删除，让移植源码自己消化冲突

先逐个验证这 8 个文件"留在原地"到底有没有害：

| 检查 | 方法 | 结论 |
|---|---|---|
| 是否会被编译 | `grep` `CMakeLists.txt` / `Make.defs`（本目录） | ✅ 8 个文件名 **0 引用** |
| 是否会被自动收编 | `grep` `build.ninja`；risc-v arch 的 `CMakeLists` 是否有 `file(GLOB …)` | ✅ 0 命中、**无 GLOB** |
| 头文件是否被包含 | 全树 `grep` `#include "esp_dma.h" / "esp_wlan.h" / "esp_timer.h"` | ⚠️ 只有 `esp_timer_adapter.c` 的 `esp_timer.h` 一处（其余 = 其它芯片架构自己的同名头）|
| 唯一真实冲突 | 旧 `esp_timer.h` 是 `esp_timer_initialize()` 老 API，会**遮蔽** ESP-IDF HAL 的同名头 | 🔴 必须处理 |

**修复只有一行** —— `esp_timer_adapter.c`：

```c
- #include "esp_timer.h"      /* 引号：优先搜"包含者所在目录" → 命中上游遗留旧头 */
+ #include <esp_timer.h>      /* 尖括号：跳过该规则 → 命中 HAL 头 */
```

原因（`compile_commands.json` 实测的 `-I` 顺序）：HAL 的 `components/esp_timer/include`
在 **index 116**，而 arch 目录 `…/common/espressif` 在 **index 155** —— 尖括号形式天然命中 HAL。
其余 7 个文件保持上游原样（不编译、不被包含）→ 无影响。

## 24.3 第二处只能靠 rsync 表达的东西：目录软链 `common/board`

顺着"交付物必须能被 manifest 完整表达"再查一遍文件树，发现另一处 deploy-only 依赖：

```
board/esp32p4/common/board -> ../esp32p4-function-ev-board/src     # 指向**目录**的软链
<copyfile src="board/esp32p4/common/board" dest="vendor/espressif/boards/esp32p4/common/board"/>
```

- `rsync -a` 会把它原样重建（软链）→ 旧方案能工作；
- `<copyfile>` **对任何软链都直接失败**：src 经 repo 的 `_SafeExpandPath()` 逐段校验，
  任一段是软链（含最后一个组件）即抛
  `ManifestInvalidPathError: "<path>: traversing symlinks not allow"`，
  评审端 `repo sync` 后该路径根本不存在；
- `<linkfile>` 也救不了：它只能把 dest 链到**作品仓里**的路径（repo 自算相对路径），
  无法得到"链到工作区内的 `../esp32p4-function-ev-board/src`"这个目标。

> ⚠️ **实测纠错**：本小节初稿按"只有指向目录的软链会出事"写（依据 `_CopyFile._Copy()` 里的
> `isdir(src)` 检查），随后直接 import repo 源码跑真实调用，结果是**目录软链与普通文件软链
> 都报 `traversing symlinks not allow`**（`_SafeExpandPath()` 逐段 `islink` 校验）：
>
> | 传入 src | 实测结果 |
> |---|---|
> | `link_to_dir`（指向目录） | `ManifestInvalidPathError: … traversing symlinks not allow` |
> | `link_to_file.h`（指向普通文件） | 同上（**一样失败**，不是"落成普通文件"）|
>
> 因此校验改为**树内不得有任何软链**（`tools/engineering/gen_manifest_copyfiles.py` 第 4 条），
> 交付树当前 0 软链。

**是否真的需要它？** 逐处查引用：

| 引用者 | 是否使用 `board/` | 说明 |
|---|---|---|
| `common/CMakeLists.txt` | ❌ | 只有 `add_subdirectory(src)` + `target_include_directories(board PRIVATE include)` |
| `common/src/CMakeLists.txt`、`esp32p4-function-ev-board/CMakeLists.txt` | ❌ | 无 `common/board` 引用（全 vendor 树 grep 0 命中）|
| `common/Makefile`（**make** 路径） | ✅ `include board/Make.defs` / `--dep-path board` | 该路径**已经是坏的**：`esp32p4-function-ev-board/` 下没有 `Make.defs` |

→ 结论：**只有 make 路径用它，而 make 路径本就不通，且评审走的是 `--cmake`**。
故直接从交付物删除：删软链 + 删 manifest 条目（清单 326 → 325）；顺带清掉一处误入树的构建产物
`board/esp32p4/common/Make.dep`（`*.dep/.depend/.built` 已列入 `export.py` 跳过名单）→ 清单定稿 **324 条**
（2026-09-17 晚修 WS 服务端时改动 `app/ai_agent/src/channels/ws_server.c`，它首次进入改动集 → **325 条**）。
（若将来要恢复 make 路径，正解是在 `common/Makefile` 里直接写 `../esp32p4-function-ev-board`
而不是依赖一个 manifest 表达不了的软链。）

## 24.6 教训

- **交付物必须"能用 manifest 表达"**：任何依赖部署脚本的动作，都会在评审环节丢失或走偏；
  "能一条 `repo sync` 复现"应当是可校验的不变量（已由 §24.4-2 的校验强制）。
- 上游遗留文件冲突，优先在**源码层**消化（include 形式 / 符号命名 / 条件编译），
  而不是在**交付层**要求手工删除 —— 后者不可复现、不可校验、也无法被 CI 发现。
- 顺带暴露的文档腐化：`build.sh` 参数写法、`board/esp32p4_vela/` 旧路径在多处文档里残留 ——
  结构变动后要同步"复现路径"类文档，否则评审照抄就失败。
- **结论只能靠"删掉重来"来验证**：文档里的复现命令只有在**清空构建产物后的干净树**上跑过
  才算数。本节 §24.5-6 的短名写法就是因为只在缓存齐全的树上试过而蒙混过关（见 §24.7）。

## 24.7 干净树复现复验（2026-09-18，删构建 + 重建）

> 目的：回答"评审照 README 从零来一遍，到底能不能出双镜像？"——把构建产物全删掉重来。

做法与结果：

| 步骤 | 命令 / 判据 | 结果 |

| 1. 删除构建产物 | `rm -rf cmake_out out nuttx/build-esp32p4-bootloader nuttx/mcuboot-esp32p4.bin` | 释放约 2.4 GB |
| 2. 干净构建 | `./build.sh vendor/espressif/boards/esp32p4/esp32p4-function-ev-board/configs/nsh --cmake -j8` | ✅ `build completed successfully (06:32)`，2,426 步 |
| 3. 双镜像 | `cmake_out/…/nuttx.bin` + `nuttx/mcuboot-esp32p4.bin` | ✅ **1,835,008 B** + **24,672 B**，与文档一致 |
| 4. SRAM 判据 | `sram_seg` 区间段求和（方法见 `docs/04` §3.2） | ✅ **123,190 B ≈ 120.3 KB / 512 KB（23.5%）** |

## 24.8 `repo sync` 会**删掉**清单里已移除的落位文件（9/18 踩到，已修）

强制同步复验时发现工作区少了 5 个 `.gitignore`，后果很重：`arch/…/esp32p4/esp-hal-3rdparty/`（≈594MB）
与 `arch/…/espressif/bootloader/`（≈1.6GB）**不再被忽略**，于是在 `git status` 里变成"未跟踪改动" ——
下一次 `tools/engineering/export.py --apply` 会把这两棵依赖树当成改动导出。

**机制**（repo 源码 `subcmds/sync.py`）：repo 在 `.repo/manifests/copy-link-files.json` 里记录
**上一次投递过的 copyfile/linkfile 目标**，每次 sync 执行

```python
need_remove_files = set(old["copyfile"]) - set(new_copyfile_paths)
for f in need_remove_files: platform_utils.remove(topdir/f)   # ← 静默删除
```

即：**manifest 里"去掉"一条 copyfile，等价于"从工作区删掉那个文件"**。旧布局（`board/esp32p4_vela/`）
曾把移植自带的 5 个 `.gitignore` 当 copyfile 投递（旧 manifest 可查：5 条 `dest="…/.gitignore"`），
9/17 的 A 方案重构把它们从清单里丢了 → 第一次 sync 就把它们从工作区删除了。

**影响面**：只影响作者工作区（评审是全新 clone，没有历史投递记录 → 不会被删）。
但作者的 `git status` / 导出工具会因此看到 GB 级"改动"，属高风险。

**已修**：

1. 按重构前历史逐字恢复 5 个 ignore 文件（内容取自 `594b719:board/esp32p4_vela/…`）：
   `nuttx/arch/risc-v/src/esp32p4/.gitignore`（`/bootloader`、`/esp-hal-3rdparty`、`/ulp`…）、
   `nuttx/arch/risc-v/src/common/espressif/.gitignore`、`nuttx/arch/risc-v/include/esp32p4/.gitignore`
   （生成头 `gpio_sig_map.h`/`irq.h`）、`vendor/espressif/boards/esp32p4/common{,/scripts}/.gitignore`。
   复核：`nuttx` 仓库 `git status` 回到 164 项，导出预览回到 **325**。
2. `tools/engineering/export.py` 加**兜底守卫**：`git status` 里凡是"目录条目"（= 嵌套 git 仓/依赖树）一律跳过并提示，
   即便 ignore 规则再次缺失，也不可能把依赖树灌进作品仓。

**教训**：`repo sync` 不是"只加不减"的；manifest 里删条目 = 工作区删文件。
交付形态里**任何一条 copyfile 的增删都要当成一次"工作区变更"来评估**。

# 二十六、ai_agent 一启动就"整机失聪"：JTAG 现场取证与定论

这是本届最"反直觉"的一个问题：agent 自己**跑得好好的**（P0→P6 全 rc=0、12 skills、
WebSocket 监听 28789、`All network services started!`），但它一跑完，**整板对外全部失联**。
9/17 用 JTAG 把现场读出来，结论是：**不是 agent 逻辑的问题，是 CPU 侧中断投递（CLIC/共享线）掉了**。

## 26.1 症状与复现（100% 稳定，当日 3/3）

```
nsh> ai_agent
[agent] ... P0/P1/P3/P5 全部 rc=0
[netmgr] Found iface eth0 addr 192.168.1.105 → [agent] Network connected: 192.168.1.105
[agent] All network services started!          ← 最后一行日志，之后彻底安静
```
* 主机 `ping`：启动前 3/4 通（RTT ≈3ms）→ 启动后 **0/5 通（100% 丢包）**；
* 主机 `TCP 28789`：连接超时（板端明明已 listen）；
* 串口：**输入无回显**（不是"输出被截断"，`UART0 STATUS` 里 txfifo=0、rxfifo 也被读空）；
* **不会自愈**：等 60s 依旧，必须复位。

## 26.2 取证方法（可复现：`tools/test/wedge_diag.sh`）

| 手段 | 关键点 |
|---|---|
| JTAG 直读 | `openocd -f board/esp32p4-builtin.cfg`，`halt` 后读 CSR / 内存 / 外设寄存器，`resume` 后 CPU 继续跑（**不打断复现**，两次采样间隔 4s 即可判"涨不涨"） |
| 读 CSR | openocd 默认只暴露了 `mintthresh/mclicbase` 等少数 CSR；`riscv expose_csrs` **必须在 `init` 之前**执行，否则报 `must be used before init`。本脚本补暴露 `mstatus/mie/mip/mtvec/mtvt/mepc/mcause/mcycle/minstret` |
| 读"现场"而非"结果" | 只读 `g_system_ticks`/外设 pending 位只能看到症状；**能定性的是对照**：同一套读数在"健康态"和"wedge 态"各采一遍 |
| 处理器表 | `g_irqvector[18]`（NuttX 向量表）+ `s_intr_handlers[core0][32]`（HAL 的 `intr_handler_item_t{fn,arg}`）+ 每个 adapter 的 `{func,irq,ctx,arg}`，用 `System.map` 反查符号 |

## 26.3 现场数据与判读

| 观测量 | 健康态（复位后、未启 agent） | wedge 态（启动后） | 判读 |
|---|---|---|---|
| `pc` | `0x4ff412fe` = `esp_cpu_wait_for_intr`（WFI 空闲） | `exception_common` / `riscv_dispatch_irq` / `return_from_exception` | wedge 态 CPU **一直在中断进出路径上**（风暴），不是空闲 |
| `mcycle` / `minstret` | 前进 | **同样前进**（两次采样差 ~4.4e8 / ~3.3e8） | CPU 真的在跑，**不是停机/死等** |
| `g_system_ticks` | 4s 内 +410（≈102.5Hz） | 两次采样**完全相同**（0x157d） | **100Hz 节拍中断不再执行** |
| `SYSTIMER INT_ENA/INT_RAW/INT_ST` | `5 / 0 / 0`（每 tick 都被 ISR 清） | `5 / 5 / 5`（TARGET0 节拍闹钟 + TARGET2 都在请求，**没人清**） | 外设侧在正常请求中断，**CPU 侧没跑完** |
| `SYSTIMER TARGET0_CONF` | `0xc0027100`（work_en=1，period=160000＝10ms@16MHz） | 同 | 节拍闹钟配置没被改 |
| `mintthresh / mtvec / mtvt / mie / mip` | `0x1f / 0x4ff40003 / 0x4ff40040 / 0 / 0` | **完全一致** | 不是阈值抬高、不是向量表被改、不是"CLIC IE 全灭" |
| halt 伪迹 `mstatus` | `0x89`（MIE=1） | `0x1801`（MIE=0/MPIE=1/MPP=3，即"在 trap 里"） | 进 trap **之前** CPU 中断是开着的 |
| `s_intr_handlers[core0]` | intno0=`isr_adapter_func`→`systimer_irq_handler`(0x4002f672)、intno3=`shared_intr_isr`… | **逐字节相同** | 节拍 ISR **仍然注册着**，却没有被进入 |
| `g_irqvector` | 16×`0x40001eba` + `0x40002032` + `esp_isr_demultiplexing` | 同 | 向量表没被改 |

**判别实验**：halt 后手动写 `SYSTIMER_INT_CLR=0x5` → `INT_RAW` 立刻 5→0，`resume` 3s 后
又回到 `0x1`（周期闹钟照常再来），但系统**仍然不恢复**（`g_system_ticks` 不动、ping 仍 100% 丢）。
⇒ **挂起位是症状不是病因**：外设在请求、CPU 没有把它跑完。

## 26.4 已排除项（都是真机 A/B，不是推断）

| 假设 | 否证方式 |
|---|---|
| CPU 忙等/死循环在某个任务 | `mcycle/minstret` 在两态都前进；且 wedge 态 PC 在 trap 进出路径而非某个自旋函数 |
| UART 硬件/输入通道坏了 | wedge 态 `UART0 INT_RAW` 无 RX 位、RX FIFO 已读空；DSI/CSI 那些曾经打印的通道也都正常 |
| 包缓冲耗尽（IOB/EMAC 描述符太少） | 把 `IOB_NBUFFERS 8→128`、`IOB_NCHAINS 4→32`、`EMAC NRXDESC/NTXDESC 2→8` 恢复后重编重烧，**现象完全不变** |
| 中断阈值/向量表/全局中断开关被改 | 见上表：四项 CSR 两态逐字一致 |
| tick ISR 被"注销"了 | `s_intr_handlers` 两态逐字一致，intno0 仍指向 `systimer_irq_handler` |

## 26.5 结论与下一步

**结论**：agent 启动网络服务之后，**NuttX 节拍所依赖的 systimer 中断在 CPU 侧不再被服务**
（外设 pending 位常驻、CPU 反复进出 trap、`g_system_ticks` 冻死），于是所有依赖时间/超时的
东西（socket 超时、NSH 输入、心跳）一起"哑掉" —— 这与"输入通道坏了"是两个不同的结论，
也解释了为什么 ICMP/TCP/串口会**同时**失联。

**代码线索（下一步的着手点）**：

```
board_emac_init()                    vendor/espressif/.../src/esp32p4_ethernet.c:64
  └─ esp_hr_timer_init()             nuttx/arch/risc-v/src/common/espressif/esp_timer_adapter.c
       └─ esp_timer_early_init() + esp_timer_init()      ← ROM 里的 IDF esp_timer
            └─ SYSTIMER_ALARM_ESPTIMER + ETS_SYSTIMER_TARGET2_INTR_SOURCE
NuttX 节拍                            nuttx/.../esp_timerisr.c
  └─ SYSTIMER_ALARM_OS_TICK_CORE0 + SYSTIMER_TARGET0_INTR_SOURCE
  两者由 port 的 esp_irq.c（CLIC + 共享线记账）统一分配 CPU 中断线
```
现场同时看到 TARGET0 与 TARGET2 的 pending 位，正是这两路。建议的定位手段（按性价比排序）：
1. 在 `esp_irq.c` 的 `up_disable_irq()` / `esp_intr_enable_source()` / `esp_clear_handle()`
   打点（记录 irq + 返回地址到全局环缓冲），复现后 JTAG 读回环缓冲 → 直接看到"谁最后动了这条线"；
2. 让节拍与 IDF esp_timer 不再共用 systimer（例如节拍改用 GPTimer，或让 EMAC 走
   NuttX 原生 `esp_hr_timer.c` 实现而不是 IDF esp_timer）；
3. 用 `gdb + target remote :3333` 在 wedge 态读调度器状态（本 ELF 无 DWARF，需要手工 struct
   offset，成本较高，优先级低于 1）。

**影响面（诚实记录）**：不阻碍"agent 能在板上完整跑起来"的演示（启动链路的每条断言都能复现），
阻碍"与 agent 交互"（`ask`、WebSocket 对话）——这一条在提交说明里必须写明。

## 26.6 方法学教训

1. **先做对照组**。第一次读到 `mintthresh=0x1f` 时我几乎写下了"阈值被抬高"的结论；再在
   健康态读一次，发现**两态都是 0x1f**（CLIC 编码里它就是"阈值 0"）——省下一次错误结论。
2. **halt 会留下伪迹**。`mstatus.MIE=0 + MPP=3 + mcause=ECALL` 是调试器 halt 自身造成的
   （`mepc` 指向 ROM 的 ECALL 桩）；把它当"中断被关了"会得出完全错误的结论——用
   `MPIE=1`（进 trap 前的状态）才对。
3. **区分"症状"和"病因"**。`INT_RAW=5` 看着像原因；手动清掉后系统不恢复，才证明它只是症状。
4. **可复现的现场 = 资产**。把整条取证路径固化成 `tools/test/wedge_diag.sh`（含判读文本），
   下次（或评审/队友）一条命令即可复现这段 JTAG 现场，而不是重读一遍我的聊天记录。

## 26.7 根因与修复（2026-09-17 傍晚，当天闭环）

一轮就抓到了元凶。

### 现场数据（修复前）

| 观测量 | 读数 | 含义 |
|---|---|---|
| `g_dbg_irq_cnt[0..5]` | 两次采样**完全相同** | 一条中断都没被派发 |
| `g_dbg_tick_cnt` / `g_system_ticks` | 冻在同一值 | 节拍 ISR 没进过 |
| `g_dbg_exc_cnt` | `0x013efbdd → 0x0160c58b`（+220 万 / 5s） | **≈49 万次/秒的异常风暴** |
| `g_dbg_exc_mcause` | `0x3000000b` | ECALL from M-mode（异常 11） |
| `g_dbg_exc_mepc` | `0x4002fa64` | 落在 **`up_exit()` 的 `ecall` 指令**上 |
| 调度器 | `g_running_tasks[0] = NULL`，就绪队列只剩 idle | 任务已退出、没有上下文可切 |

反汇编对上了（`riscv-none-elf-objdump`）：

```asm
4002fa56: jal  nxtask_exit
4002fa5e: sw   zero,188(a5)   # g_running_tasks = NULL   ← up_exit 故意置空
4002fa62: li   a0,1           # SYS_restore_context
4002fa64: ecall               # ★ 陷入点（mepc 指这里）
4002fa6a: j    4002fa62       # ★ 原地重发 → 死循环
```

### 根因（一行）

`nuttx/arch/risc-v/src/common/riscv_doirq.c` 里那段"早期引导保护"：

```c
  if (g_running_task == NULL)
    {
      return regs;          /* ← 本意：忽略 ROM 在调度器起来前打来的中断 */
    }
```

它把**所有** trap 都吞了 —— 而 `up_exit()` 恰恰是**故意**先把 `g_running_task` 置 NULL，
再发 `ECALL(SYS_restore_context)` 让 `riscv_swint()` 去切到下一个就绪任务。
被这段保护拦下后，ECALL 进不到 `riscv_swint()`，`.S` 里那条 `j` 就把它无限重发：
CPU 100% 卡在 trap 进出路径 → 节拍/网络/串口全部"失聪"。

**所以这不是 agent 的问题：任何任务退出都会触发。** 判别实验：在子 shell 里敲 `exit`
（与 agent 毫无关系的普通任务退出），现象一模一样 —— `ping` 100% 丢、`mepc` 同样
`0x4002fa64`、异常计数同样爆炸。

### 修复

保护只对**硬件中断**生效；异常/系统调用必须继续派发：

```c
  if (g_running_task == NULL && irq > RISCV_MAX_EXCEPTION)
    {
      return regs;
    }
```

（异常 irq 为 0..15；外设中断 irq 为中断源号，如 48/61/70/109，两者不会混淆。）

### 修复后验证（生产固件，埋点开关已关回 0）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 子 shell `exit` | 整机死（ping 100% 丢，需复位） | **ping 4/4 收，系统照常** |
| `ai_agent` 启动完成 | ping **0/5（100% 丢）**、TCP 28789 超时、串口无回显 | ping **5/6（16.7%，与空闲基线一致）**、**TCP 28789 连接成功** |
| 启动 60s 后再测 | 依旧死 | ping 4/5，稳定 |
| `mepc` | `0x4002fa64`（up_exit 的 ecall） | `0x4002fcd6`（`up_switch_context`，正常换上下文） |

证据：`logs/verify-2026-09-17/wedge_fix.txt`；复测工具：`tools/test/wedge_diag.sh`。

### 仍未闭环的两件（独立问题，与本次修复无关）

1. 对 28789 发起 WebSocket / HTTP 请求会在 ~10ms 内被 RST（收到 0 字节）：TCP 握手正常、
   端口在监听，REST 接口未编入（`CONFIG_AI_AGENT_REST_API` 未开），所有连接走
   `ws_server.c` 的握手分支 —— 待查。
2. MiMo API key 经主机直连仍为 **HTTP 401 Invalid API Key**，LLM 真实对话未验证。

### 26.8 教训（补）

1. **"保护性提前返回"最危险的地方是它同时吞掉了正常路径。** 这段 guard 的注释写得
   很清楚（针对 ROM 早期中断），但没写"不得吞异常/系统调用"，于是把 `up_exit` 的
   上下文切换机制一起吞了。改完之后我把这个约束写进了注释与文档。
2. **埋点要打在"分发入口"而不是"业务函数"里。** 一个 `g_dbg_irq_cnt[cpuint]++` 加
   一个异常分支里的 `mepc/ra` 快照，就把 3 小时的猜测变成了一次读数。
3. **判别实验比推理便宜。** "任意任务退出都会死"这条结论来自子 shell 里敲一个 `exit`，
   比继续读调度器代码快得多，也更有说服力。

# 二十七、ai_agent 端到端对话打通（2026-09-17 晚，三个独立缺陷）

§26 修掉"整机失聪"之后，WebSocket 能连上、消息能进去，但回答仍然出不来。
当晚把这条链路从上到下走通，一共是**三个互不相干**的缺陷，全部实测定位：

## 27.1 端点不对：key 属于 Token Plan 网关（HTTP 401）

`agent_config.h` 里默认 `AGENT_LLM_API_HOST = api.xiaomimimo.com`，而手里的 key 只能在
Token Plan 网关 `token-plan-cn.xiaomimimo.com` 下使用，于是每次请求都是 401。

做法（**部署相关信息不写进仓**）：

```c
/* agent_config.h：默认值改成可覆盖（保留上游默认） */
#ifndef AGENT_LLM_API_HOST
#define AGENT_LLM_API_HOST "api.xiaomimimo.com"
#endif

/* packages/ai_agent/include/agent_secrets.h（.gitignore 忽略，本地） */
#define AGENT_LLM_API_HOST "token-plan-cn.xiaomimimo.com"
#define AGENT_LLM_API_PATH "/v1/chat/completions"
```

真机日志确认生效：`[llm] LLM proxy initialized (model: mimo-v2.5, host: token-plan-cn.xiaomimimo.com)`；
主机直连同样确认 key 有效（`/v1/models` 200 + `chat/completions` 200）。

## 27.2 连接被 RST：`CONFIG_NET_TCPBACKLOG` 没开

现象：TCP 三次握手正常、端口在监听，但一发数据就被 RST（收到 0 字节）。

定位：在 `ws_server.c` 的**静默路径**补日志（`recv` 失败/accept 失败/线程创建失败——此前
这些分支什么都不打，看上去就像"服务端坏了"），发现连 `client connected` 都不打 ⇒
**`accept()` 从来没被调用**。对照 NuttX 源码：

* `net/tcp/tcp_netpoll.c`：监听 socket 的 `POLLIN` 依赖 `TCP_BACKLOG` 事件；
* `net/tcp/tcp_accept.c`：backlog 未开启时只能**阻塞 accept**，不能靠 poll 先探；
* `net/tcp/Kconfig`：`NET_TCPBACKLOG` 默认 **n**。

ai_agent 的 `accept_thread` 恰好是"先 poll 再 accept"，于是永远 poll 不到可读 —— 连接
堆在栈里直到被对端/协议栈复位。

修复（板级 defconfig）：

```
CONFIG_NET_TCPBACKLOG=y
CONFIG_NET_TCPBACKLOG_CONNS=8
```

修复后握手成功：

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket / Connection: Upgrade
Sec-WebSocket-Accept: r0TrHkmdTpTfiD/0Yp3vjFG6h7c=
```

## 27.3 好答案被丢掉：计时用了会被 TLS 改写的墙上时钟

握手通了之后，回答仍然是"请求超时"。串口日志给出的关键三行：

```
[llm] Response: 6 bytes text, 0 tool calls, finish=end_turn          ← 请求其实成功了
[agent] LLM watchdog: call took 2748619798 ms (limit 60s)           ← 却判成超时
[trace] END status=timeout iters=1 tools=0 llm_ms=2748619798
```

2.7e9 ms ≈ 31 天，明显不是真时延。根因在 `infra/vela_tls.c`：为了让证书校验通过，
它在发现系统时间早于 2024 年时会把 **`CLOCK_REALTIME` 强推到 2026**
（`clock_settime(CLOCK_REALTIME, 1772275200)`）——这件事恰好发生在**首次 HTTPS 握手期间**，
而 `agent_loop.c` 用 `gettimeofday()` 前后取样算时延 ⇒ 一次调用里跨了 1.7e9 秒的跳变。

修复：

```c
/* agent_loop.c：时延一律用单调时钟 */
static inline uint32_t mono_ms(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return (uint32_t)((uint64_t)ts.tv_sec * 1000u + (uint64_t)ts.tv_nsec / 1000000u);
}
uint32_t t0_ms = mono_ms();
int err = llm_chat_tools(...);
uint32_t latency_ms = mono_ms() - t0_ms;
```

顺带把看门狗预算调到与实际相符（推理模型 + 15KB 工具 schema 的实测时延）：
`AGENT_LLM_TIMEOUT_SEC 60 → 180`、`AGENT_LLM_SOCKET_TIMEOUT_SEC 120 → 240`。

## 27.6 教训

1. **静默的失败路径 = 假的"服务端坏了"**。`recv<=0 → close` 这种什么都不打的写法，
   让"客户端没发数据"和"服务端没工作"看起来一模一样；补上一行日志，问题当场收敛。
2. **NuttX 的服务端语义要查源码**：`poll` 对监听 socket 报可读依赖 `TCP_BACKLOG`，
   默认关闭的 Kconfig 会让一个"标准写法"的 TCP 服务端永远收不到连接。
3. **墙上时钟随时可能被改**。任何"耗时/超时"判断都必须用单调时钟——这个 bug 的代价是
   把已经拿到的正确答案扔掉，而且日志里的数字（2.7e9 ms）看着像"设备太慢"。
