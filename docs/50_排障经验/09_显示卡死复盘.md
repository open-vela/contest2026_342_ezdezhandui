# 09_显示卡死（相机抢带宽）复盘

> 写于 2026-11-04。结论先行 + 复现命令。**屏幕出现"卡死/花屏且只能复位"时先读这篇。**

## 一句话结论

**相机与面板共用 DW-GDMA/PSRAM 带宽。相机连续流把带宽抢死后，DSI 扫描被饿死，
面板画面冻住；而项目里原本没有"显示重建"入口，所以只能复位整机。**
现在的解法是三层：**默认路径不抢**（关掉流量翻倍的 ISP 路径）、**抢的时候让路**
（占空比限流）、**真停摆了能自救**（看门狗 + 重建入口）。

## 现象与定位

| 现象 | 证据 |
|---|---|
| 面板画面冻住、要复位才恢复 | 用户现场；`g_disp_commits`（驱动维护的显示提交计数）停止增长 |
| 只出现在"相机页 + ISP 路径" | ISP 出 RGB565 时相机 DMA 每帧 **1,843,200 B**；RAW8 是 921,600 B（**翻倍**） |
| 代码里早有伏笔 | `dm_camera.c` 注释：*相机与面板共用同一个 DW-GDMA 控制器，连续流会把 DSI 的显示打停* |
| 没有退路 | 全仓库只有启动时的 `boardctl(BOARDIOC_INIT)`，**没有显示重建入口** ⇒ 只能复位 |

**三条路径实测（同一相机页，25~30 秒窗口，JTAG 读 `g_disp_commits`）**：

| 配置 | 显示提交 | 相机 fps |
|---|---|---|
| ISP **连续流** | **3.2/s** ❌（就是卡死那版） | 13.6 |
| RAW8 连续（默认） | 5.6 ~ 7.7/s | 13.8 |
| **ISP + 让路（12 帧 / 80ms）** | **11.4/s** ✅ | 13.7 |

## 三层解法

1. **不让路就别用**：ISP 路径（`DM_CSI_ISP_RGB565`）默认**关**；要用就必须配让路。
2. **让路（占空比限流）**：`dm_config.h` 里 ISP 打开时默认
   `DM_CAMERA_BURST_FRAMES=12` / `DM_CAMERA_BURST_PAUSE_MS=80`；
   采集循环每采 N 帧 `usleep(M)`，把带宽定期让回给扫描。
   —— 实测**既不卡死、相机也不掉帧**，显示提交反而比 RAW8 更顺（11.4 vs 5.6~7.7/s）。
3. **自救**：
   - 板级 `esp32p4_display_reinit()`：**停流 → 重新绑定帧缓冲（重新武装 DW-GDMA）→ 开流**，
     幂等可重复调用（真机 `reinit OK`，之后提交继续增长）；
   - 应用侧看门狗线程：`g_disp_commits` 连续 **3 秒**不增长即判停摆，
     调用重建入口（最多 3 次）——人为停摆 8 秒实测 `stalls=6` / `reinits=3`。

## 复现与验证命令

```bash
# 看显示是否还活着（JTAG 单次读，别用循环）
riscv-none-elf-nm cmake_out/<board>/nuttx | grep g_disp_commits
openocd ... -c "set _ONLYCPU 0x1" -f board/esp32p4-builtin.cfg -c init -c halt \
  -c "mdw 0x<addr> 1" -c resume -c shutdown

# 人为制造停摆，验证看门狗
deskmate --agent mock --disp-stall 8 --camera --soak 10
# 直接验证重建入口可安全调用
deskmate --agent mock --disp-reinit --camera --soak 10
```

## 教训

- **共享 DMA/带宽的外设必须成对考虑**：给相机提性能（ISP 出 RGB565 让流量翻倍）
  会直接打到显示上；**任何"提流量"的改动都要先问"面板还吃得上饭吗"**。
- **可自愈 > 只能复位**：一个"提交计数 + 重建入口 + 看门狗"的小闭环，
  比事后反复复位省事得多；计数必须由**驱动**维护（别拿帧缓冲内容猜）。
