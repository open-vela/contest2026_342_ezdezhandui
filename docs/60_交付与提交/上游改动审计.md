# 上游树改动审计

> 目标里有一条明确约束：**"少改上游树"**。这份文档交代我们到底改了什么、
> 为什么非改不可、以及哪些地方刻意选择了"不动上游"的做法。
>
> **2026-11-02 重写**：Espressif 共享层整体从 `arch/risc-v/src/common/espressif/`
> 搬进 `arch/risc-v/src/esp32p4/espressif/`，通用层（RISC-V generic）从此只被
> **1 个**文件覆盖。上一版（2026-10-28）的"11 个上游文件 + 45 个共享层条目"
> 已经不适用。

## 一、结论

| 类别 | 数量 | 说明 |
|---|---|---|
| **覆盖上游基线**（nuttx 树，逐文件 `<copyfile>`） | **18** | 其中落在**通用 RISC-V 层**（`arch/risc-v/src/common/`）的只有 **1** 个 |
| nuttx 新增文件（逐文件 `<copyfile>`） | 14 | `arch/risc-v/include/esp32p4/*`、视频驱动、`tools/espressif/*` |
| Espressif 层（整层） | 121 | 搬到 `arch/risc-v/src/esp32p4/espressif/`，随 **1 条 `<linkfile>`** 交付（该子树合计 528 文件） |
| 交付总条目 | 116 copyfile + 3 linkfile | 逐文件条目里 `nuttx/` 只占 32 条 |
| 落到 `arch/risc-v/src/common/` 的交付条目 | **1** | 仅 `common/CMakeLists.txt` |

搬迁前后的对照：

| | 迁移前 | 迁移后（2026-11-02） |
|---|---|---|
| Espressif 层位置 | `nuttx/arch/risc-v/src/common/espressif/` | `nuttx/arch/risc-v/src/esp32p4/espressif/` |
| 交付方式 | 45 条 `<copyfile>`（**写在通用层**） | 随 `esp32p4` 的 1 条 `<linkfile>` |
| 通用层交付条目 | 48 | **1** |
| P4 构建读的是哪一份 | 通用层里我们覆盖的那份 | 芯片目录里的整层 |

## 二、这次搬迁做了什么

### 2.1 整层搬走

`nuttx/arch/risc-v/src/common/espressif/**`（121 文件：`Kconfig`、`Make.defs`、
`CMakeLists.txt`、`Bootloader.*`、`Wireless.*`、`esp_ulp.*`、`chip.h`、被编译的
19 个 `.c/.S`、头闭包，以及其余上游驱动）→ `nuttx/arch/risc-v/src/esp32p4/espressif/**`。

跟随改动（全部在**我们自己的文件**里）：

| 文件 | 改动 |
|---|---|
| `esp32p4/CMakeLists.txt` | `add_subdirectory(../common/espressif)` → `add_subdirectory(espressif)` |
| `esp32p4/Make.defs` | `include common/espressif/Make.defs` → `include chip/espressif/Make.defs`；新增 `CMN_CSRCS := $(filter-out riscv_mtimer.c,…)` |
| `esp32p4/Kconfig` | `source "…/common/espressif/Kconfig"` → `source "…/esp32p4/espressif/Kconfig"` |
| `esp32p4/hal_esp32p4.mk` | `freertos_compat` 的 include 路径 |
| `espressif/CMakeLists.txt` | HAL 补丁路径 `../../esp32p4/patches/` → `../patches/` |
| `espressif/Make.defs` | `Bootloader.mk`/`Wireless.mk` 的 include、`INCLUDES`、`VPATH` |
| `espressif/ulp.cmake`、`board/…/common/src/{CMakeLists.txt,Make.defs}` | `ulp.cmake`/`ulp_makefile` 的路径 |
| `tools/build_flash/ensure_psram_guard.sh` | MCUboot 工作树的新位置 |

HAL 克隆目录（`${NUTTX_BINARY_DIR}/arch/risc-v/src/common/espressif/esp-hal-3rdparty`）
**故意保持原名**：它是构建目录里的缓存路径，改它会连带作废评审端/本机已下载的 700 MB 树。
`espressif/CMakeLists.txt` 里对此有注释说明。

### 2.2 另外两处通用层改动的去向

| 原改动 | 去向 |
|---|---|
| `common/riscv_doirq.c`：早启动 `g_running_task == NULL` 守卫（提交 8510a00，"任务退出 → 整机失聪"） | **下沉**到 `esp32p4/espressif/esp_irq.c` 的 `riscv_dispatch_irq()`。P4 全部 trap 只从这条路进来（`esp_vectors.S → exception_common → riscv_dispatch_irq → riscv_doirq`），全树 `riscv_doirq()` 的调用者也**只有** `esp_irq.c`，所以在调用点拦一层与在原函数里拦一层等价。通用文件已回到基线（`git -C nuttx diff --stat arch/risc-v/src/common/riscv_doirq.c` 为空） |
| `common/Make.defs`：`riscv_mtimer.c` 条件编译 | 由 `esp32p4/Make.defs` 的 `filter-out` 取代，`common/Make.defs` 不再交付 |

### 2.3 MCUboot 工作树移出交付子树

`Bootloader.cmake`/`Bootloader.mk` 的 `BOOTLOADER_SRCDIR` 原本是
`<源目录>/bootloader`。搬迁后它会变成 `esp32p4/espressif/bootloader` —— 而
`esp32p4` 是**作品仓的符号链接**，那棵 1.6 GB 的 MCUboot 工作树（`mcuboot/` +
`esp-hal-3rdparty-mcuboot/` + 打过 PSRAM 守卫补丁的 `mmu_hal.c`）会直接落进交付树。
所以改成：

```cmake
set(BOOTLOADER_SRCDIR ${NUTTX_DIR}/bootloader-${CHIP_SERIES})   # Bootloader.cmake
BOOTLOADER_SRCDIR = $(TOPDIR)/bootloader-$(CHIP_SERIES)         # Bootloader.mk
```

与既有的 `build-${CHIP_SERIES}-bootloader/`、`mcuboot-${CHIP_SERIES}.bin` 同级，
都属于构建产物。`tools/build_flash/ensure_psram_guard.sh` 同步指向新位置。

## 三、为什么 `common/CMakeLists.txt` 删不掉（可复现）

它做的是把 `riscv_mtimer.c` 改成 `if(CONFIG_ONESHOT)` 条件编译。基线（`76354c6`）
是**无条件**编译，而本板配置 `CONFIG_ONESHOT=n` / `CONFIG_ONESHOT_COUNT=n`：

```bash
# 用工程真实 flag 复现（flag 取自 <build>/build.ninja 里 riscv_doirq.c.o 的规则）
riscv-none-elf-gcc <DEFINES/FLAGS/INCLUDES> -c \
    nuttx/arch/risc-v/src/common/riscv_mtimer.c -o /tmp/riscv_mtimer.o
# → error: 'const struct oneshot_operations_s' has no member named 'start_absolute'
```

（成员被 `include/nuttx/timers/oneshot.h` 里的 `CONFIG_ONESHOT_COUNT` 包住；对象虽然
不会被链接进去——`libarch.a` 不带 `--whole-archive`——但**编译**必然失败。）

那能不能从芯片目录把它摘掉？实测不能（CMake 3.22，最小工程复现）：

| 手段 | 结果 |
|---|---|
| `set_source_files_properties(<abs>/riscv_mtimer.c PROPERTIES HEADER_FILE_ONLY TRUE)` | 无效（源文件属性按目录隔离） |
| 同上 + `TARGET_DIRECTORY arch` | 无效 |
| 同上 + `DIRECTORY <common 目录>` | 无效 |
| `set_property(TARGET arch PROPERTY SOURCES …)` 过滤掉该文件 | 无效（CMake 3.22 忽略 SOURCES 写入） |
| `cmake_language(DEFER DIRECTORY … CALL …)` | 需要 CMake 3.25（本机 3.22.1） |

再加上顺序问题：`arch/risc-v/src/CMakeLists.txt` 是
`add_subdirectory(chip) → add_subdirectory(common)`，芯片目录先被处理，改不到后加进来的源。
**Make 路径**倒是有现成套路（同层已有 `CMN_ASRCS := $(filter-out riscv_vectors.S,…)`），
所以 `common/Make.defs` 已经不交付了。

结论：这 1 个文件是"基线真 BUG + CMake 机制受限"的显式例外，并由
`gen_manifest_copyfiles.py --assert-shared-max 1` 与 `check_consistency.py` 的
"通用层交付条目 ≤ 1" 两个断言钉住。

## 六、常见疑问

**评审端 `common/espressif/**` 还在，会不会被编译？**
不会。全部引用点都在
`esp32p4/{CMakeLists.txt,Make.defs,Kconfig,hal_esp32p4.mk}` 里，已全部改到新路径；
`arch/risc-v/src/CMakeLists.txt` 也不会主动加它。构建图自检：
`grep -c "src/common/espressif/esp_" <build>/build.ninja` = 0。

**别的 ESP 芯片（esp32c3/c6/h2…）会不会坏？**
不会。它们的 `Kconfig`/`Make.defs`/`CMakeLists.txt` 仍指向基线的
`common/espressif/*`（manifest 不能删文件，基线那份还在），本次只改 P4 一侧。

**为什么不干脆把基线那 121 个文件也删掉？**
manifest 只能新增/覆盖，无法表达删除；强行删会给评审加一步部署脚本，得不偿失。
现在的状态是"基线文件闲置 + 我们整层交付"，语义上等价于"通用层零改动"。

**为什么搬过来的是工作区那份（比基线新）而不是基线那份？**
搬迁要的是**一层自洽的 espressif 实现**：19 个被编译的 `.c/.S` + 16 个头闭包 +
构建文件必须同源。工作区那份正是本板一直编译并已通过真机验证的内容（与迁移前
交付的 45 个文件逐字节相同），其余文件同属一批上游内容；混用"新 45 + 旧 76"才是
真正的隐患（头与实现不同源）。

**这一层自洽性有构建证据**：驱动更全的 `verify-drivers` 配置在新位置跑 `arch` 目标，
313 个 edge 全部编过，`libarch.a` 374 个成员里含
`esp_adc/esp_csi/esp_dedic_gpio/esp_emac/esp_i2s/esp_lirc/esp_mipi_dsi/esp_touch/esp_rmt`
（其中 `esp_rmt.c` 只有这个配置会编、4 个驱动连 nsh 都不编），以及搬迁后的
`esp_irq.c`/`esp_vectors.S`；同一次构建里 MCUboot 也走完了 configure/build/install。
证据：`logs/20261102-124236_espressif-move/verify_drivers_arch_build.txt`。
