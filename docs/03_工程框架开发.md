## 一、工程形态：一个工作区、四个源仓、一个作品仓

openvela 用 `repo` + manifest 管多仓。我们的**交付物只占一个仓**（作品仓），
其余上游仓只提供"基线"，靠 manifest 的 `<copyfile>` 把我们的**改动集**映射进作品仓。
好处很直接：评审看到的是"改了哪些文件、为什么改"，而不是 4 个 fork 的 12 万行全量 diff。

```
/opt/openvela（工作区，repo 管）
├── nuttx/            ← 上游基线（NuttX 内核 / arch / 驱动）
├── apps/             ← 上游基线（apps）
├── packages/ai_agent ← 上游基线（ai_agent）
├── vendor/espressif  ← 上游基线（vendor 板级）
├── .repo/            ← repo 元数据（manifest 在这里）
└── contest2026_342_ezdezhandui/    ★ 作品仓（唯一交付物）
```

| 作品仓目录 | ⇄ 工作区路径 | 内容 |
|---|---|---|
| `nuttx/` | `nuttx/` | 内核/arch/驱动的适配改动 |
| `board/esp32p4/` | `vendor/espressif/boards/esp32p4/` | 板级源码 + `defconfig` |
| `app/apps/` | `apps/` | camera / lvgl / netinit 等应用侧改动 |
| `app/ai_agent/` | `packages/ai_agent/` | ai_agent 应用 + 自定义 Skill |
| `tools/` `docs/` `logs/` | （作品仓自有，不映射） | 工具、文档、真机证据、AI 会话日志 |

> 归一化后的**上游基线是干净的**：`board/esp32p4` 与 `nuttx/arch/risc-v/src/esp32p4`
> 在上游一个文件都没有，esp32p4 移植 100% 是我们自己的代码（`git ls-files` 实证）。

## 二、manifest 机制（`contest2026_342_ezdezhandui.xml`）

### 2.1 只用 `<copyfile>`

```xml
<project name="contest2026_342_ezdezhandui"
         path="contest2026_342_ezdezhandui"
         revision="5e41cb6b7a1a6814bfbf1a5604d6b2d7285ea355">
  <copyfile src="nuttx/arch/risc-v/src/esp32p4/esp_start.c"
            dest="contest2026_342_ezdezhandui/nuttx/arch/risc-v/src/esp32p4/esp_start.c"/>
  …324 条…
</project>
```

`repo sync` 时按 `src → dest` 自动落位，**因此不需要任何部署脚本**（历史上那步
`deploy.sh` 已删除，见 `docs/06` §24）。

### 2.2 两条不能碰的红线（都是 repo 自身的限制，实测确认）

| 限制 | 含义 | 我们的做法 |
|---|---|---|
| `<copyfile>` **不能表达删除** | 上游文件只能被覆盖，不能被删掉 | 移植冲突在**源码层消化**（如把 `#include "esp_timer.h"` 改成 `<esp_timer.h>` 绕开旧头），不靠删文件 |
| **任何软链都不行** | repo 的 `_SafeExpandPath()` 逐段校验，遇软链报 `traversing symlinks not allow` | 树里 0 软链（`.git` 除外）；需要"目录别名"时改为真实文件/目录 |

另有 `<linkfile>` 不能指向工作区内部路径，所以也别打它的主意。

### 2.3 清单与文件树必须严格一致

| 脚本 | 作用 |
|---|---|
| `tools/gen_manifest_copyfiles.py` | 扫文件树 → 生成/校验 324 条 `<copyfile>`；发现软链或 `.deleted-files` 直接报错 |
| `tools/export.py [--apply] [--manifest]` | 工作区改动 → 作品仓文件树；`--apply` 才写盘，`--manifest` 顺带刷新清单 |
| `tools/lock-revision.sh` | 把 manifest 里**自锁**的 `revision` 推进到最新 HEAD，并同步 `.repo/manifests` 副本 |

> `revision` 必须锁 **SHA**（不能用分支名）：评审环境 `repo sync` 只认 SHA。

## 三、构建与烧录：一条命令、两个镜像

```bash
# 1) 同步（copyfile 自动落位；无部署步骤）
repo init -u <contest-manifests> -m contest2026_342_ezdezhandui.xml && repo sync

# 2) 构建（注意配置名是 <board>:<config>）
./build.sh esp32p4-function-ev-board:nsh --cmake -j8

# 3) 烧录（两镜像 + hash 校验；0x2000 引导 / 0x20000 应用）
contest2026_342_ezdezhandui/tools/usb_stable.sh

# 4) 看 console（UART0 → /dev/ttyUSB0，115200，须 assert DTR/RTS）
python3 contest2026_342_ezdezhandui/tools/board.py login
```

| 产物 | 路径 | 说明 |
|---|---|---|
| 应用 | `cmake_out/esp32p4-function-ev-board_nsh/nuttx.bin` | MCUboot 兼容，烧 `0x20000`（OTA_0） |
| 引导 | `nuttx/mcuboot-esp32p4.bin` | 烧 `0x2000` |

**Boot 链**：ROM → MCUboot（memcpy SRAM 段 + MMU 映射 IROM/XIP）→ 应用入口 →
`nx_start` → NSH。细节与"为什么要二级引导"见 `docs/04` §3.1。

### 3.1 两个必须记住的构建坑

1. **改了 `.config` / `defconfig` 之后必须 `touch nuttx/CMakeLists.txt`** —— `config.h`
   只在 CMake configure 阶段再生成，不 touch 就会"改了配置但没生效"（ninja 显示
   `no work to do`）。
2. **配置写法**：`./build.sh esp32p4-function-ev-board:nsh`；写成
   `nuttx/boards/.../configs/nsh/` 会被解析成 `nuttx/boards` 并报 `No config file found`。

## 四、工具链（`tools/`）

| 工具 | 一句话 | 典型用法 |
|---|---|---|
| `export.py` | 工作区改动 → 作品仓文件树（可同时刷新 manifest） | `python3 tools/export.py`（预览）→ `--apply --manifest` |
| `gen_manifest_copyfiles.py` | 生成/校验 copyfile 清单 | `python3 tools/gen_manifest_copyfiles.py --check` |
| `lock-revision.sh` | 推进 manifest 自锁 revision + 同步 `.repo/manifests` | `tools/lock-revision.sh` |
| `usb_stable.sh` | 两镜像烧录（带重试 + hash 校验） | `tools/usb_stable.sh` |
| `board.py` | 串口 harness：reset / run / script / watch / login（内置 DTR/RTS） | `python3 tools/board.py run "free"` |
| `verify_aiagent.sh` | ai_agent 启动里程碑断言（多轮容错采集） | `tools/verify_aiagent.sh 3` |
| `camera_diag.sh` | 摄像头链路一次性判定（读 CSI/DMA/PHY 寄存器） | `tools/camera_diag.sh 35` |

| `dsh_session_to_contest_log.py` | AI 会话日志 → `logs/<login>/<date>/` | 见脚本头注释 |

## 五、日常开发流程

### 5.1 先判断"这个改动属于哪棵树"

| 改动性质 | 改哪里（工作区） | 会落到作品仓 |
|---|---|---|
| 内核/驱动/arch | `nuttx/…` | `nuttx/…` |
| 板级（引脚、defconfig、板级初始化） | `vendor/espressif/boards/esp32p4/…` | `board/esp32p4/…` |
| 应用（camera/lvgl/netinit…） | `apps/…` | `app/apps/…` |
| ai_agent / Skill | `packages/ai_agent/…` | `app/ai_agent/…` |
| 工具/文档/证据 | 直接改作品仓 | 不进 copyfile |

### 5.2 标准循环（改 → 建 → 烧 → 验 → 导 → 提）

```bash
W=/home/ez/share/openvela                     # 工作区
D=$W/contest2026_342_ezdezhandui              # 作品仓

# ① 改代码（工作区）
$EDITOR $W/nuttx/drivers/video/sc2336.c

# ② 构建（必要时先 touch 触发 config 再生成）
cd $W && ./build.sh esp32p4-function-ev-board:nsh --cmake -j8

# ③ 烧录 + 真机验证（每个结论都要有证据）
$D/tools/usb_stable.sh
python3 $D/tools/board.py run "camera 3" --timeout 30 --save /tmp/cam.log

# ④ 导出到作品仓（**确认没有临时调试代码**！）
cd $D && python3 tools/export.py            # 先看 dry-run
python3 tools/export.py --apply --manifest

# ⑤ 提交 + 锁 revision + 推送
git add -A && git commit -F -               # 见 §5.3 提交信息规范
tools/lock-revision.sh
git push fork dev-ai-contest-2026:dev-ai-contest-2026
```

### 5.3 提交信息规范

- 一行主题：`<类型>(<范围>): <做了什么>`，类型用 `fix/feat/docs/tools/chore/refactor`
- 正文写**根因 + 证据 + 影响面**，不写"优化了一下"
- 例：`fix(mcuboot): TCM(LP_IRAM) 校验放行改由 patch 脚本承载 —— 修板子启动循环`

### 5.4 提交前自检清单

```bash
cd $D
python3 tools/export.py            # 应只剩预期改动
grep -c "<copyfile" contest2026_342_ezdezhandui.xml     # 应为 324
find . -type l -not -path "./.git/*" | wc -l            # 应为 0
ls .deleted-files 2>/dev/null                           # 应不存在
git status --porcelain                                  # 干净
```

## 六、约定与不变量（都是踩过的坑）

1. **带临时调试开关时不要跑 `export.py`** —— 会把调试代码带进树。
   正确做法：调试代码用宏开关（如 `ESP_CSI_CAPTURE_DIAG`、`ESP_WEDGE_DIAG`），
   默认 0 进树，需要时 `sed` 改 1 单独编一版诊断固件。
2. **JTAG 脚本里的符号地址会随固件变化** —— 每次重新构建后从
   `cmake_out/.../System.map` 取地址，别把上一版的地址写死。
3. **证据归档**：真机结论一律留证据文件到 `logs/verify-<date>/`
   （串口实录 / JTAG 转储 / 帧缓冲截图），文档里引用它，不口说无凭。
4. **密钥不进仓**：`packages/ai_agent/include/agent_secrets.h` 由 `.gitignore` 忽略，
   本地注入；文档里只写变量名不写值。
5. **`logs/` 目录契约**：`logs/<login>/<date>/<tool>__<sid>.jsonl`（AI 会话日志）；
   截图/实录放 `docs/` 或 `logs/verify-<date>/`。
6. **别 `pkill -f openocd`** —— 模式会匹配到自己这条命令，把当前 shell 一起杀掉；
   用 `ps -eo pid,args | grep bin/openocd` 再按 PID kill。
7. **串口**：打开 `/dev/ttyUSB0` 必须 assert DTR/RTS，否则读到 0 字节；
   `CONFIG_TTY_SIGINT` 未开时 **Ctrl+C 杀不掉前台长驻应用**（如 `lvgldemo`），只能复位。
8. **`/dev/ttyUSB0` 与 Tabby**：Tabby 占用串口时 `board.py` 会 `device reports readiness
   to read but returned no data`；要么关掉 Tabby 的串口页，要么走 `tools/tabby_mcp.py`。
