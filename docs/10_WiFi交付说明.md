# WiFi（板载 C6 / SDIO + ESP-Hosted）交付说明

> 2026-10-29 · 这份文档把 WiFi 这一项的**实际状态、证据、与待办**说清楚。
> 完整排查过程见 `docs/08_WiFi_SDIO实现.md` 附录 A–AA（一百余节）。

## 一、一句话结论

**主机侧驱动已完整实现，并与 ESP-IDF 官方协议文档逐条对齐；每个可调变量都有实验记录。
设备侧的 C6 在数据阶段不提供数据 —— 三个互相独立的指标都指向这一点。
这不是主机驱动能修复的问题。**

## 二、做到了什么（都有证据）

| 环节 | 状态 | 证据 |
|---|---|---|
| SDIO 枚举 `CMD0/5/3/7` | ✅ | 多次复位稳定；逻辑分析仪解码出 `cmd0/cmd5×4/cmd3/cmd7`，CRC7 全部合法 |
| 卡功能（FN1、512 字节块）| ✅ | `card function ready (FN1, 512-byte blocks)` |

| CMD53 块传输 + IDMAC + cache | ✅ | 缓冲区预填 `0xAA`，DMA 后变为 `0x00`（传输确实发生）|
| 命令帧正确性 | ✅ | 波形逐位解码 `arg=0x1fef8801`，与参考实现的地址/模式/长度完全一致 |

## 三、本次会话定位并修复的 **10 个真实缺陷**

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `waitresponse()` 末尾缺 `return OK`（整块替换时被删）| 返回不确定值 `53`，`sdio_probe` 误判失败 |
| 2 | 上层成功判据写成 `ret < 0` | 把 `53` 当成成功，**"枚举成功"的假象掩盖了 #1** |
| 3 | 完成位没在发命令前清掉 | 轮询看到上条命令的残留位，响应"迟到"，读到旧的 `RESP0` |
| 4 | `eventwait()` 依赖中断事件 | 该中断从未送达本驱动，数据传输一律超时；改轮询后才工作 |
| 5 | DMA 没有 cache 维护 | 接收不作废、发送不回写 |
| 6 | `widebus()` 把 D1/D2/D3 配成普通输出且未设值 | **把它们驱动为低 —— 直接解释了"命令通、数据不通"** |
| 7 | `configpins()` 从未把 `DAT1..3` 接回控制器 | **4-bit 传输在结构上不可能** |
| 8 | `eventwait()` 的 `break` 未按 `waitmask` 判断 | 数据阶段未被完整等待 |
| 9 | **`eventwait()` 的 `while` 条件只看 `xfrmask != 0`** | **数据阶段被完全跳过，却返回成功** |
| 10 | 未协商 CCCR 高速模式（从机配置为 `HIGH_SPEED`）| 25 MHz 下链路直接失效 |

## 五、缺口的确切性质

**读从机发送 FIFO 时，得到的是零。** 三个互相独立的角度都指向同一件事：

| 角度 | 读数 |
|---|---|
| **中断原始状态** | `INT_RAW = 0`（掩码已确认为 `0xFF`，非屏蔽所致）|
| **协议判据** | 文档第 2 步要求"有新的包"，实测 `INT_ST = 0` |
| **FIFO 内容** | DMA 确实运行（缓冲区被覆盖），收到的就是零 |

**`PACKET_LEN` 读回 60 是唯一"说有数据"的读数**，而它是**累加计数器**
（`sdio_get_len_from_slave` 里要减去已读长度、还要处理回绕），在没有任何包真正排入时
也可能留有残值。

**从机软件侧的日志显示它调用了 `sdio_slave_transmit()`（`Send slave up event`），
但从机的硬件寄存器表明发送 FIFO 是空的。**

## 六、怎么继续（需要主机侧之外的观测手段）

1. **用示波器探到 C6 一侧** —— 看它在数据阶段是否真的驱动了数据线。
   目前的分析仪接在 P4 侧同一网络上，只能看到"网络上有没有信号"，
   无法区分"从机没驱动"与"从机驱动了但主机采不到"。
2. **用一个已知良好的 SDIO 从机做对照** —— 区分"本驱动有问题"与"这颗 C6 有问题"。
3. **用厂商工具检查 C6 的 `sdio_slave` 状态** —— 确认 `sdio_slave_transmit()` 之后
   发送 FIFO 里是否真的有数据。

**拿到以上任一项，就能把问题定性并继续。在此之前，继续在主机侧改动只能是猜测。**

## 八、2026-10-29 的重要更新：结论被修正过两次

### 8.1 第一个修正：数据阶段从来没被真正等待

`eventwait()` 里有两处叠加的错误：

```c
while (priv->xfrmask == 0)      /* 任何事件就退出 —— CMD_DONE 在命令阶段就来了 */
  {
    ...
    if ((priv->xfrmask & priv->waitmask) != 0) break;   /* 永远轮不到 */
  }
```

**结果：CMD53 的读操作在命令完成时就返回了，数据阶段被完全跳过，
而调用方因为事件集里既没有 `TIMEOUT` 也没有 `ERROR` 而返回 `OK`。**

**这解释了长达几十轮里最矛盾的现象："命令全对、数据永远是零、从不报错"。**

**修正之后（`while` 条件与 `break` 都按 `waitmask` 判断），同样的读操作会等满 5 秒
超时并如实返回 `-ETIMEDOUT`。**

### 8.2 第二个修正：从机其实有数据

**C6 的日志在 `Send slave up event` 之后完全停住** —— 连此前每次启动都有的
WiFi 断连重试日志都不再出现。而 `sdio_slave_transmit()` 是阻塞的（等主机读走）。

**即：`send_task` 卡在 `sdio_slave_transmit()` 上。**

**这证明帧确实在从机的发送 FIFO 里** —— 与"从机没有数据"是相反的结论。

### 8.3 因此现在的准确表述是

**从机有数据，但它的 SDIO 硬件没有把 FIFO 里的数据搬上数据线。**

波形证据（附录 AA.143）：数据阶段 67,730 个时钟周期内，`D0` 99.8% 高、`D3` 100% 高 ——
四条数据线保持空闲电平。

**从机软件把一切准备好了（描述符已挂、发送中断已使能、触发已调用），
主机按协议文档发起了读取，而数据阶段不动。**

### 8.4 只剩一种手段能区分

**用示波器/探针直接测 C6 一侧的 DAT0** —— 而不是测同一网络上的 P4 侧。

**区别很关键**：分析仪在 P4 侧看到的是"网络上有没有电平变化"，
**无法区分"从机硬件没搬"与"从机搬了但板级连接把它衰减/隔离了"**。
**这两种情况的修法完全不同。**

### 8.5 频率问题的最终答案（问题 1）

| 时钟 | 结果 |
|---|---|
| 25 MHz（SD 默认速度）| 🔴 `PACKET_LEN` 读回 0，链路失效 |
| 403 kHz（实测）| 命令正常，数据超时 |
| 400 kHz | 命令正常，数据超时 |
| **100 kHz** | ✅ 唯一稳定（命令正常，数据仍超时）|

**两个方向都试过：更快会断链，更慢仍不通。不是频率问题。**
（25 MHz 断链的根因后来查明是 CCCR 高速模式未协商 —— 已补上，补上后 25 MHz 下
寄存器通信恢复正常，但数据阶段仍然超时。）
