# 踩坑笔记 #03：ESP32-P4X 烧录与启动（0x25 根因 → NuttX 完整启动）

> 2026-08-18/21。目标：板卡（ESP32-P4X-C5-Function-EV-Board，rev3.2）烧录并启动 NuttX。
> **结论：NuttX 内核完整启动**（调度器 idle 运行）——4 个根因级修复（链接布局 / 烧录偏移 / XIP 污染 / CLIC 中断风暴）；**USB-Serial console 数据未达主机**（T2 第一项）。
>
> ⚠️ **本篇写于「RAM 执行」时代**（`CONFIG_ESPRESSIF_SIMPLE_BOOT`：镜像整段搬进 SRAM 后从 SRAM 取指）。
> 之后架构已切换为 **MCUboot 二级引导 + Flash XIP**（代码留在 flash 就地执行，SRAM 占用 451 KB → 96 KB），
> **烧录流程也从"单镜像写 0x2000"变成"双镜像 0x2000 + 0x20000"** —— 旧的单镜像做法已失效。
> 因此本篇里的"XIP"多指**要避开的**东西（链接误指 `0x40000000` → 执行空 flash），
> 与后来**主动启用**的 XIP 语义相反；完整迁移过程与 10 个新坑见 **`踩坑笔记_04_MCUboot与FlashXIP.md`**。

## 里程碑链路（按修复顺序）

| 阶段 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1. 链接布局 | 早期 crash `load access fault @0x25` | HAL sdkconfig.h 的 `CONFIG_APP_BUILD_USE_FLASH_SECTIONS=1` 劫持链接 → 代码链到 0x40000000（**flash XIP 映射区，非 RAM**）→ ram-only 加载后执行空 flash | `esp32p4_flat_memory.ld`：条件改 `CONFIG_ESPRESSIF_SIMPLE_BOOT` + rev3 的 `sram_seg`（上游 else 分支引用 sram_low 是 rev<3 专属——**rev3+SIMPLE_BOOT 组合上游从未跑通**） |
| 2. 烧录偏移 | ROM 报 `invalid header`（读到的不是烧的内容） | **P4 的 bootloader 偏移 = 0x2000**（`BL_OFFSET`，espressif_esptool_common.cmake 中 `CONFIG_ARCH_CHIP_ESP32P4` 专属）——烧 0x0 无效 | esptool **≥4.12.0**（2026-07-13 才支持 rev3.2/ECO7，5.3.1/4.10 stub 全崩）`write_flash 0x2000 nuttx.bin`；或官方 `cmake --build <dir> -t flash`（⚠️ 其 `write-flash` 参数名与 4.12 的 `write_flash` 不兼容） |
| 3. XIP 污染（**旧方案下的问题；新方案已主动启用 XIP，见 #04**） | bss 垃圾、CPU 跳飞（0x8C5B/0x8FF8 等垃圾地址） | `esp_start.c` SIMPLE_BOOT 分支调 `map_rom_segments`，用 `_image_irom_lma`（修复后 = **SRAM 地址**）当 flash 物理地址配置 MMU → 整片 SRAM 被无效映射污染 | SIMPLE_BOOT 跳过 `map_rom_segments`（只 MCUBOOT 需要 XIP） |
| 4. CLIC 风暴 | 早期中断风暴（irq_unexpected_isr → 反复） | ROM 遗留 CLIC 中断源在 NuttX IRQ 表就绪前触发；`up_disable_irq` 无 IRQ_UNMAPPED 检查（上游同 bug） | `__esp_start` 早期清全部 CLIC 中断控制字节（`0x20801003 + i*4` 置 0，128 个） |
| 5. console | NuttX 启动到 idle 但无输出 | `esp_usbserial_write` 被调用（输出路径活）但数据未达主机（TX 端点/主机侧） | ⏳ **T2 第一项**；备选 UART0 console（CP2102 在线） |

## 坑 1：esptool rev3.2 stub 崩溃

- 现象：5.3.1/4.10 均 stub 崩溃（`Entering download mode` 后 OHAI 不达）；ROM 模式（--no-stub）USB 断流；UART0 下载模式无响应
- 根因：**ESP32-P4 rev3.2/ECO7 支持仅存在于 esptool ≥ v4.12.0**（2026-07-13 发布）
- 解决：`pip3 install --user "esptool==4.12.0"`；烧录用 `~/.local/bin/esptool.py --chip esp32p4 --port /dev/ttyACM0 write_flash <addr> <bin>`
- ⚠️ pip 升降级后 **重建 esptool 软链**（`ln -sf ~/.local/bin/esptool.py ~/.local/bin/esptool`）——mkimage 依赖

## 坑 2：JTAG 烧录（OpenOCD）的坑

- OpenOCD：`/tmp/openocd-esp32/openocd-esp32/bin/openocd`（v0.12.0-esp32-20260703，ghfast 下载）；配置 `-f board/esp32p4-builtin.cfg`（esp_usb_jtag 303a:1001 + esp32p4 target，flash 支持齐全）
- **`esp32p4_soc_reset` 会断 USB**（P4 系统复位含 USB-JTAG 控制器）→ 复位后设备重枚举（VMware 直通下加剧抖动）
- **ROM 复位后总是进下载模式等待**（strap 引脚配置）——`boot:0xf` 从 flash 启动需要特殊触发；**RAM 加载调试绕开 ROM 启动**：
  ```bash
  openocd -f board/esp32p4-builtin.cfg -c "init" -c "halt" \
    -c "load_image <nuttx ELF>" -c "resume <entry>" -c "shutdown"
  # 入口：riscv-none-elf-readelf -h nuttx | awk '/Entry point/ {print $4}'（$4！不是 $3）
  ```
- **`reg pc <val>` 无效**（SMP 双核）——用 `resume <entry>`（设 PC+运行一步）
- **OpenOCD `break` 命令传函数名会报 "expected integer"**；`bp` 命令在 esp32p4 上 "Invalid command argument"——**用 gdb**（`target remote :3333`，gdb 12.1 支持 riscv32）但 VMware 抖动下协议不稳
- 软件断点调试注意：`-c "wait_halt 10000"` 不命中会一直等

## 坑 3：烧录"成功"但没落盘（JTAG stub vs esptool）

- **JTAG stub flasher（flash write_image）报 wrote 但 ROM 读到的还是旧内容**——写入未真正落盘（XMC 缓存）
- **esptool 烧录可靠**（走 ROM 下载模式驱动，hash verified）——验证：`esptool.py read_flash <addr> 0x40 | xxd` 应看到 `e9 04`（ESP 镜像 magic）
- 判断依据：JTAG read_bank 读 0x0 = e9 04（JTAG stub 写的），ROM 启动却报 `invalid header: 0xc6b7c290`（旧内容）——**两次写入一次有效**

## 坑 4：LP WDT 复位循环（连 JTAG 都不稳）

- 现象：`Reset cause (16) - (LP WDT resets chip)` 反复；USB 设备号每次枚举都变；OpenOCD "Debug Module is not active"
- 根因：镜像卡死（中断风暴）→ `bootloader_config_wdt` 未执行 → LP WDT 超时复位 → 循环
- 解：修掉卡死根因（坑 1-4 的修复）；`bootloader_super_wdt_auto_feed` 配置后不再复位
- 调试经验：**串口监听要用自动重连脚本**（设备复位循环/重枚举时 cat 会挂）：
  ```bash
  for i in $(seq 1 30); do [ -e /dev/ttyACM0 ] && timeout 6 cat /dev/ttyACM0; sleep 1; done
  ```

## 坑 5：调试工具链细节

- **pkill/pgrep -f 自误杀**：命令行含匹配串就杀自己（exit 144）——模式用字符类 `"[o]penocd-esp32/bin"`，且 heredoc/路径里出现完整串也会被匹配
- **串口被占**：esptool 前 `fuser -k /dev/ttyACM0`（cat 监听占着端口会 Write timeout）
- **读内存验证 bss/中断表**：OpenOCD `mdw <addr> <n>`（halt 后）——bss 垃圾 = 中断表 g_irqvector 被污染（之前靠这个定位 XIP 污染）
- **CLIC 寄存器**：基址 0x20800000；每中断使能/优先级控制字节 `0x20801003 + i*4`（1 字节，0=禁用）；`CLIC_INT_INFO` 0x20800004（当前中断号）
- **P4 flash 数据映射区 0x8FF8xxxx**（XIP）——halt PC 落在这里 = MMU 被错误映射（XIP 污染症状）

## 坑 6：烧录/启动环境

## 坑 8：console 中断使能调查记录（8/24，T2 专项）

**现象**：NuttX 完整启动 + nsh 提示符生成（txbuffer 有 `\r\nNuttShell (NSH)\r\nnsh> `）但数据卡缓冲（主机收不到）；banner（ets_printf/ROM 直写）能出（USB 通道工作）。

**调查结论**（已定位到最后一环）：
- 外设侧：USB-Serial 外设（基址 **0x500D2000**）INT_RAW=0xf30f（中断 pending）+ INT_ENA=0x0c（已使能）✓
- CPU 侧：**CLIC intctl（0x20801003+i*4）全 0**（含调用 enable_source 后——**esprv_int_enable（ROM）没写 intctl**）
- esp_intr_enable 返回 OK（route 分支——只配路由矩阵，不写 CLIC）；up_enable_irq 补 enable_source（幂等）实测仍无效
- **结论**：P4 的中断 CPU 侧使能寄存器**不是 intctl**（0x20801000 区域调用前后无变化）——**使能位图在别处**（intr_matrix 或 CLIC 扩展区）——**需对照 ESP-IDF 的 P4 中断系统（esp_cpu_intr_enable → rv_utils_intr_enable → esprv_int_enable（ROM）写哪个寄存器）**

**线索**：
- tick 中断能触发（intctl 0 也触发）——P4 中断触发不依赖 intctl
- 外设基址链：DR_REG_HPPERIPH1_BASE=0x500C0000 → USB2JTAG=+0x12000=0x500D2000
- CLIC 基址 0x20800000（INT_CONFIG/INFO/THRESH 三个寄存器）

## 坑 8 更新（8/24 深挖）：console 的真相是"异常循环"

**新证据**（halt 读）：
- **mcause=0x30000007（store/AMO access fault）**，mepc=0x4ff412ea（riscv_doirq 内）
- 异常点：`sw s0, 168(g_running_tasks)`（g_running_tasks=0x4ff4e2d0——store 到 0x4ff4e378——合法 SRAM 但 fault）
- **向量表**：0x4ff40008 `_panic_handler` → j `_interrupt_handler`（0x4ff40100）——**异常与中断共用入口**（异常走 riscv_doirq 路径——调度器操作（早期异常时 g_running_tasks 指向对象无效 → store fault → 递归异常循环）
- CLIC 全禁用（早期）+ 路由矩阵全 0（INTERRUPT_CORE0_BASE+4*source）——**中断不该触发**；PMP（REGION_PROTECTION）关闭实验无效——**不是 PMP**

**结论**：早期某次异常（来源待查）→ _panic_handler → riscv_doirq（异常当中断处理）→ 调度器 store fault → 循环。halt 的 riscv_doirq 是异常处理现场，不是正常中断。

**下次线索**：
- 断 _interrupt_handler（0x4ff40100）入口抓第一次异常号（gdb 或 halt 读 a0）
- 对照 NuttX 上游 esp32p4 的早期异常处理（_panic_handler 语义）
- 检查早期异常来源（bootloader_init 后各步骤：esp_rtc_init/esp_mspi_pin_init/spi_flash_init_chip_state/esp_mmu_map_init）

## 坑 8 更新 2（8/24）：0x8FF8 异常循环（CPU 在垃圾区执行）

**核心现象**：cpu0 持续在 **0x8FF80700 执行**（mcause=0x30000001，mepc=0x8FF80700）——JTAG 读 0x8FF8 全 0，但 CPU 能取指（cache？）——**异常循环的根源是 CPU 跳到了 0x8FF8 区域**（flash/cache 映射区——执行垃圾/全 0）

**已排除**：PMP（REGION_PROTECTION 关）、esp_mmu_map_init（SIMPLE_BOOT 跳过）、CLIC 使能（全禁用+路由全 0）、map_rom_segments（已修复跳过）

**待解**：
- 0x8FF00000 的物理含义（P4 的 flash dcache 映射区？L2 cache 窗口？——查 ext_mem_layout/g_mmu_mem_regions）
- CPU 跳到 0x8FF8 的**跳转源**（某函数指针/数据 = 0x8FF8xxxx——内存扫描或 gdb 断跳转）
- 对照 ESP-IDF 的 P4 启动（esp_cache/esp_mmu 初始化——0x8FF0 是否该被配置）

**影响**：异常循环占住 cpu0（中断处理），console 输出（txbuffer）无法 flush——**比中断使能更根本的障碍**

## 坑 8 更新 3（8/24）：0x8FF8 排除清单与跳转源分析

**地址语义全排除**（soc/ext_mem_defs.h）：
- flash 线性区 = 0x40000000（SOC_IRAM0_CACHE_ADDRESS_LOW）
- PSRAM 线性区 = 0x48000000（SOC_IRAM_PSRAM_ADDRESS_LOW）
- **0x8FF0 在 soc 定义中不存在**（无效地址）——CPU 跳到无效地址取指 fault

**dump 扫描**：SRAM 前 266KB 无 0x8FF8 前缀值——**跳转源不在静态数据**（动态计算/寄存器/cache 窗口）

**下一步候选**：
- P4 的 L2 cache 窗口（0x8FF0？——cache_ll/cache_hal 定义）
- 早期某 cache/MMU 操作返回/引用了 0x8FF8（对照 ESP-IDF P4 的 esp_cache/esp_mmu 初始化）
- 完整 SRAM dump（剩余 180KB）再扫

## 坑 8 更新 4（8/24）：0x8FF8 = SRAM 的 non-cacheable 别名（跳转源指向数据区）

**破案**（ESP-IDF cache_ll.h）：
- `CACHE_LL_L2MEM_NON_CACHE_ADDR(0x4FF00000) = 0x4FF00000 + SOC_NON_CACHEABLE_OFFSET_SRAM = 0x8FF00000`
- **0x8FF8xxxx = SRAM 0x4FF8xxxx 的 non-cacheable 别名**（DMA/外设写穿透用）
- CPU 执行 0x8FF80700 = 执行 SRAM 0x4FF80700（堆未使用区，内容全 0）——**某代码把 non-cacheable 数据地址当代码跳转**

**待查**（下一步）：
- 谁使用 `CACHE_LL_L2MEM_NON_CACHE_ADDR`（产生 0x8FF8 地址——esp_dma/esp_cache/缓冲分配——早期（bootloader_init 后）代码审查
- 设备稳定时 halt 读寄存器（找 0x8FF8 值的来源）+ gdb 断跳转
- heap 的 non-cacheable 访问（mm_heap 的 DMA 缓冲——某函数指针读自 non-cacheable 缓冲）

## 坑 10：console 攻坚（8/24 全天）——从"零输出"到 boot 深推进的根因链

> 状态：**boot 已推进到 esp_clk_init 时代（迟滞在 up_mdelay/_assert 区）**，console 输出仍不可见。

### 本轮确认的事实（含推翻旧结论）

| # | 结论 | 依据 |
|---|---|---|
| 1 | **flash 0x0-0x2000 = PADDING**（保留区，非 ROM 代码） | esptool memory map：0x0-0x10000 标 "PADDING"；web 确认 P4 ROM 在芯片内部，bootloader 在 0x2000 |
| 2 | **0x4FC00000-0x4FC1FFFF = 内部 ROM 的取指窗口**（memset=0x4FC00268 等 ROM API 在此） | esp32p4.rom.ld：全部 ROM 符号在 0x4FC0xxxx |
| 3 | **旧构建（cmake_out）镜像入口错误：0x4FF47FB2（spi_flash 尾部）≠ __start（0x4FF485A6）** | ELF e_entry 对比；新构建入口正确 |
| 4 | **CONFIG_ESP_SYSTEM_MEMPROT 在 sdkconfig.h 硬编码=1**——IRAM(RX)/DRAM(RW) 分割与 SIMPLE_BOOT 平铺布局冲突（.flash.text 在 _iram_text_end 之上 → 执行即 PMP fault） | 已修复：删硬编码 + 补丁 |
| 5 | **链接脚本 flash_rodata_dummy 的 ALIGN(0x10000)+0x20 把 .flash.rodata 推到 0x4FFC0020（物理 SRAM 之外）** | 已修复：SIMPLE_BOOT 下跳过页对齐 → 0x4FFB0350 |
| 6 | **早期中断在 g_running_task==NULL 时进 riscv_doirq_top → NULL 解引用 store fault** | 已加 guard：调度器未就绪时忽略 |
| 7 | **复位循环引擎 = ROM 武装的 LP WDT（Super WDT）**；bootloader_init 也重新武装（已注释） | Reset cause (16)/(18)；设备号持续递增 |
| 8 | 旧观察教训：**canonical 模式 cat 瞬间退出 = 0 字节假阴性**；抓串口必须 raw 模式或 pyserial | 多轮 0 字节都是假象 |
