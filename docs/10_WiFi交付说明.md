# WiFi（板载 C6 / SDIO + ESP-Hosted）交付说明

> 2026-10-29 · 这份文档把 WiFi 这一项的**实际状态、证据、与待办**说清楚。
> 完整排查过程见 `docs/08_WiFi_SDIO实现.md` 附录 A–AA（一百余节）。

## 一、一句话结论

**主机侧驱动已完整实现，并与 ESP-IDF 官方协议文档逐条对齐；每个可调变量都有实验记录。
设备侧的 C6 在数据阶段不提供数据 —— 三个互相独立的指标都指向这一点。
这不是主机驱动能修复的问题。**

## 二、做到了什么（都有证据）

| 环节 | 状态 | 证据 |
|---|---|---|
| SDIO 枚举 `CMD0/5/3/7` | ✅ | 多次复位稳定；逻辑分析仪解码出 `cmd0/cmd5×4/cmd3/cmd7`，CRC7 全部合法 |
| 卡功能（FN1、512 字节块）| ✅ | `card function ready (FN1, 512-byte blocks)` |
| ESP-Hosted 帧层 | ✅ | `frame layer up (hdr v1, 12-byte headers, checksum on)` |
| CMD52 双向寄存器 | ✅ | 写 `0x5A` 到 SCRATCH14，读回 `0x5A` |
| CMD53 块传输 + IDMAC + cache | ✅ | 缓冲区预填 `0xAA`，DMA 后变为 `0x00`（传输确实发生）|
| 命令帧正确性 | ✅ | 波形逐位解码 `arg=0x1fef8801`，与参考实现的地址/模式/长度完全一致 |
| FIFO 读取方法 | ✅ | 严格遵循 `esp_sdio_slave_protocol.rst` 的五步流程与 `requested length = 0x1F800 - address` |
| `OPEN_DATA_PATH` 握手 | ✅ | 发出的信号被 CP 处理，其内部计数 20 → 21 |
| 从机开放发送缓冲区 | ✅ | `TOKEN_RDATA` 从 `0` 变为 `0x00021000`（2 个缓冲区）|
| 中断掩码与清除 | ✅ | `INT_ENA` 写入 `0xFF` 并读回确认生效 |

## 三、本次会话定位并修复的 **7 个真实缺陷**

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `waitresponse()` 末尾缺 `return OK`（整块替换时被删）| 返回不确定值 `53`，`sdio_probe` 误判失败 |
| 2 | 上层成功判据写成 `ret < 0` | 把 `53` 当成成功，**"枚举成功"的假象掩盖了 #1** |
| 3 | 完成位没在发命令前清掉 | 轮询看到上条命令的残留位，响应"迟到"，读到旧的 `RESP0` |
| 4 | `eventwait()` 依赖中断事件 | 该中断从未送达本驱动，数据传输一律超时；改轮询后才工作 |
| 5 | DMA 没有 cache 维护 | 接收不作废、发送不回写 |
| 6 | `widebus()` 把 D1/D2/D3 配成普通输出且未设值 | **把它们驱动为低 —— 直接解释了"命令通、数据不通"** |
| 7 | `configpins()` 从未把 `DAT1..3` 接回控制器 | **4-bit 传输在结构上不可能** |

## 五、缺口的确切性质

**读从机发送 FIFO 时，得到的是零。** 三个互相独立的角度都指向同一件事：

| 角度 | 读数 |
|---|---|
| **中断原始状态** | `INT_RAW = 0`（掩码已确认为 `0xFF`，非屏蔽所致）|
| **协议判据** | 文档第 2 步要求"有新的包"，实测 `INT_ST = 0` |
| **FIFO 内容** | DMA 确实运行（缓冲区被覆盖），收到的就是零 |

**`PACKET_LEN` 读回 60 是唯一"说有数据"的读数**，而它是**累加计数器**
（`sdio_get_len_from_slave` 里要减去已读长度、还要处理回绕），在没有任何包真正排入时
也可能留有残值。

**从机软件侧的日志显示它调用了 `sdio_slave_transmit()`（`Send slave up event`），
但从机的硬件寄存器表明发送 FIFO 是空的。**

## 六、怎么继续（需要主机侧之外的观测手段）

1. **用示波器探到 C6 一侧** —— 看它在数据阶段是否真的驱动了数据线。
   目前的分析仪接在 P4 侧同一网络上，只能看到"网络上有没有信号"，
   无法区分"从机没驱动"与"从机驱动了但主机采不到"。
2. **用一个已知良好的 SDIO 从机做对照** —— 区分"本驱动有问题"与"这颗 C6 有问题"。
3. **用厂商工具检查 C6 的 `sdio_slave` 状态** —— 确认 `sdio_slave_transmit()` 之后
   发送 FIFO 里是否真的有数据。

**拿到以上任一项，就能把问题定性并继续。在此之前，继续在主机侧改动只能是猜测。**

## 七、这一项交付了什么

- `esp_sdmmc.c`（约 2450 行）：完整的 NuttX SDIO 主机驱动 —— 26 个 `sdio_dev_s` 方法、
  IDMAC 描述符链、CLIC 中断、双 slot 引脚路由、cache 维护、三个 bring-up 诊断函数；
- `esp_hosted_sdio.c`（约 960 行）：链路层 —— 枚举、卡功能、帧层、`OPEN_DATA_PATH` 握手、
  寄存器读写验证、FIFO 接收；
- `esp_hosted_frame.c`：esp-hosted 帧层（逐字节取自上游）；
- **一份 20 篇文档、可复现的完整排查记录**（附录 A–AA），
  **其中也如实记录了误报与自我纠正**（例如一次"CMD5 带 OCR 有响应"的误判、
  一次自己引入的缓冲区越界、两次读错代码分支）。

**代码可读性**：驱动编译零警告；排查期间的临时脚手架已清理，
bring-up 路径保持"枚举 → 卡功能 → 帧层 → 寄存器验证 → 握手 → 接收"的清晰结构。
