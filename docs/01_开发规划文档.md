## 一、项目概述

**作品名称**：桌伴（DeskMate）—— 基于 openvela + ai_agent 的 ESP32-P4X 智能视觉中控屏
**一句话**：一块 7 英寸的 AI 视觉中控屏——它「能看见、会主动、会执行」：摄像头看到你进门就主动问候，早上 8 点自动播报天气和日程，说"记一下明早 9 点开会"就记下并到点提醒，家里设备异常它主动告警。全程离线也能响应本地指令，联网后 LLM 加持。
**运行方式**：编译 `nuttx/boards/risc-v/esp32p4/esp32p4-function-ev-board/configs/nsh/` → **两镜像烧录（MCUboot 二级引导，9/11 起）**：`0x2000 mcuboot-esp32p4.bin` + `0x20000 nuttx.bin` → NSH → `ai_agent` → `router_set mimo <key>` → 对话/主动任务。（旧 SIMPLE_BOOT 单镜像「`0x2000 nuttx.bin`」自 9/11 起失效；烧录流程落地见 §十 P0-2、证据见 `05_开发过程复盘与改进清单.md` §21.5）

### 3.1 用户故事

> 独居的上班族小林回家：门口的「桌伴」摄像头认出他，屏幕亮起"欢迎回家，今天 24℃，晚间有雨"。他说"帮我记一下明早 9 点项目评审"——桌伴记下并到点提醒。深夜摄像头检测到阳台异常人影，桌伴立即屏显+TTS 告警并推送到手机。他全程动嘴不动手。

### 3.3 技术实现要点

- **移植路径（技术难度主攻）**：NuttX 上游 `arch/risc-v/src/esp32p4` + `boards/risc-v/esp32p4/esp32-p4-function-ev-board` → openvela（`vendor_espressif/boards/esp32p4/` 板级 + nuttx 侧同步）；参考同仓 esp32s3 的 vendor 化模式；外设按「串口→ETH→屏/触摸→摄像头→codec」渐进
- **P4X 与 P4 差异**：P4X-Function-EV-Board = ESP32-P4 芯片 rev v3.1+ 变体，NuttX 上游板目录（esp32-p4-function-ev-board）为移植基线，P4X 差异点（芯片 rev/个别引脚）移植时核对 user_guide 修正
- **ai_agent 集成**：参照官方 esp32s3-eye 模式（`defconfigs/<板>/` + `fix_<板>.sh` 处理 mbedtls 冲突/兼容性问题）——esp32s3 先例经验直接复用（同 vendor 仓、同工具链生态）
- **联网**：**以太网（RMII 10/100）为保底**（ai_agent/LLM 依赖）；ESP32-C6 WiFi6 为无线演示增强（NuttX esp32p4 WiFi 支持状态待验证）
- **摄像头**：MIPI-CSI 2MP；NuttX 上游 esp32p4 有 camera 驱动参考；本地视觉用轻量模型（CPU），避免 NPU 依赖
- **内存**：32MB PSRAM 充裕（ai_agent 最小 256KB + LVGL + 视觉缓存）
- **「基于 openvela」判定对齐**：图形（LVGL）+ AI（ai_agent）+ 多媒体（TTS/摄像头/H264）全落地

### 9.6 关键技术路径（恢复被裁剪能力）—— 9/10 晚实测修正

**根因**：模块被桩掉的名义理由是「省 512KB SRAM」（`stubs.c` 注释）。实测**代码空间**才是真瓶颈，且 **512KB 在 SIMPLE_BOOT 模式下是硬限制，无法扩容**（推翻了「扩到 768KB」的初判）。

**证据链（决定性）**：
| 证据 | 来源 | 结论 |
|---|---|---|
| `SOC_DIRAM_ROM_RESERVE_HIGH = 0x4ff40000` | `soc/soc.h:183` | 低 **256KB 是 ROM 保留区**（ROM data/bss + L2 cache 存储） |
| 「ROM bootloader arms (locked) PMP entries covering [0x4FF40000, 0x4FFC0000) (RW)；低区是 L2 cache storage 且**复位被擦除**, cannot hold image content」 | `esp32p4_flat_memory.ld:37-43` | 窗口起点/终点由 **ROM 锁定 PMP** 决定,不可改 |
| `CONFIG_SPIRAM_XIP_FROM_PSRAM` 仅在 ld 中被引用,**Kconfig 未定义** | 全局搜索 | 「PSRAM 代码执行」是**死代码**（恒 false） |
| L2 cache 可选项 128/256/512KB,当前 256KB | `esp32p4/Kconfig:95` | 改 cache 大小**不移动 ROM 保留边界** → 不增加可用窗口 |

**当前实测占用（512KB 窗口内）**：
```
.flash.text    337 KB   ← 代码（SIMPLE_BOOT 下放 SRAM）
.flash.rodata   67 KB
.dram0.bss      53 KB
.dram0.data      6 KB
──────────────────────
合计 ≈ 463 KB / 512 KB  → 仅余 ~49 KB
```

**真正的解锁路径：切到 MCUboot 二级引导（非 SIMPLE_BOOT）—— ✅ 已实施（9/11，见 `05_开发过程复盘与改进清单.md` §二十一）**
- `CONFIG_ESPRESSIF_BOOTLOADER_MCUBOOT=y` → 取消 SIMPLE_BOOT → `text_seg = irom_seg`(0x40000000 flash XIP)、`rodata_seg = drom_seg`（可配 `CONFIG_SPIRAM_RODATA` 落 PSRAM）
- 收益：**text 337KB + rodata 67KB 移出 SRAM**，SRAM 仅剩 data+bss(~60KB) → **释放约 400KB**
- **LVGL 基本必须走这条路**（LVGL 库本身数百 KB）
- 代价：工作区**无 esp32p4 MCUboot 范例**（仅 esp32c6/c3/h2 有 `mcuboot_nsh`）→ 需移植：OTA 分区表 + MCUboot 镜像构建/烧录 + 新烧录流程（会改动 README 复现步骤）

**过渡方案（留在 SIMPLE_BOOT，挤出 50–100KB）—— ✅ 已实施（9/10）**：
- **已验证有效**：把大静态缓冲改成堆分配（堆＝PSRAM）即可把 SRAM 让给代码
  - `vela_tls.c` 8KB TLS 原始缓冲 → `malloc`（释放 8KB）
  - `cron_service.c` 11.4KB 作业表 → `calloc`（释放 11.1KB）
  - 结果：SRAM 静态占用 **463KB → 460.6KB**，且**顺带把 cron 真实启用**（只加 cron 时链接溢出 4496B，正是靠这两处腾挪放下）
- 后续可继续搬：`s_pool`(2KB, agent_main.c)、`s_backends`(2KB, llm_router.c)、消息队列(~5KB)

**实施结果（9/11，真机验证）**：
- ✅ MCUboot 引导构建成功（24.6KB），五道集成障碍全部做成持久化补丁 `mcuboot_p4_fixup.sh`
- ✅ **text+rodata（409KB）迁入 flash XIP 执行**；SRAM 占用 **460KB → 83KB**（*9/11 首测；2026-09-17 干净树复测为 **120.3KB / 512KB**，方法见 `docs/04` §3.2*）
- ✅ 真机：MCUboot → `Mapped IROM vaddr=0x40000000` → NuttShell → ai_agent P0→P3（cron 真实）
- ✅ 分区（16MB 物理 / MCUboot 管前 4MB）：引导 0x2000 ｜ OTA_0 0x20000 ｜ OTA_1 0x1E0000 ｜ scratch 0x3A0000
- ✅ 空间释放后启用：`web_search`、`llm_vision`/`tool_vision`（weather/briefing/news 三个 Skill 由"必失败"转可用）
- ⏳ LVGL/摄像头/语音仍需各自硬件驱动（不再是代码空间瓶颈）

- **交付物**：**修改已入树的** `board/esp32p4_vela/ai_agent/src/tools/skill_loader.c`（manifest 第 307 行已有 `<copyfile>`，**无需新增文件/条目**；流程：工作区改 → 编译验证 → `export.sh` 回树）+ 人读副本 `docs/skills/*.md`（评审可直接阅读 Skill 文本，对应 §六 规划的 `skills/`）
