# 08_驱动层调优与"多副本陷阱"

> 写于 2026-11-04（驱动层性能优化那一轮）。结论先行，附复现命令。
> 适用：改 openvela/ESP32-P4 的**驱动层**（I2C / CSI / PPA / 触摸）时先读这一篇。

## 一句话结论

**这个仓库里同名驱动常常有多份副本，`ninja` 编译的和链接进镜像的未必是你改的那一份。
改驱动前必须先确认"到底哪一份进了镜像"，否则改了等于没改。**

## 坑 1：改了驱动却毫无效果（浪费了两轮）

### 现象

给 `esp_i2c.c` 的 I2C 传输加"总线锁有界等待"，重新烧录后**指标几乎没变**；
把自己加的诊断全局拿去 `nm` 查最终 ELF，**根本不存在**。

### 根因

树里至少有 **3 份** `esp_i2c.c`：

```
nuttx/arch/risc-v/src/common/espressif/esp_i2c.c                 ← 第一次改的（没被编译）
nuttx/arch/risc-v/src/esp32p4/espressif/esp_i2c.c                ← ninja 说"编译的是它"
contest2026_342_ezdezhandui/nuttx/.../esp_i2c.c                  ← 仓库副本
```

更隐蔽的是：**`arch/libarch.a` 里有两个同名的 `esp_i2c.c.o` 成员**，
链接器取的是另一份的 `.text.esp_i2c_transfer`，而我们那份的
`.bss.g_dbg_i2c_xfer_ms` 被 `-ffunction-sections/-fdata-sections` + gc-sections **丢弃**。

`nuttx.map` 里能直接看到：

```
 .bss.g_dbg_i2c_xfer_ms_max   0x00000000   0x4   arch/libarch.a(esp_i2c.c.o)
 .bss.g_dbg_i2c_xfer_ms       0x00000000   0x4   arch/libarch.a(esp_i2c.c.o)
                                        ↑ 在"丢弃段"列表里
```

### 正确姿势（两条命令）

```bash
# 1) 谁被编译？（看实际源文件路径，不是猜）
ninja -C cmake_out/<board> -t commands | grep -oE "[^ ]*esp_i2c\.c"

# 2) 谁被链接？符号到底在不在最终 ELF？
riscv-none-elf-nm cmake_out/<board>/nuttx | grep g_dbg_i2c_xfer
# 或看 map：既能看到"废弃段"，也能看到某个地址属于哪个 .o
grep -nE "0x40048[4-6]|esp_i2c\.c\.o" cmake_out/<board>/nuttx.map | head
```

**判据：自己加的符号必须能在 `nm nuttx` 里查到**，否则这次改动就是空转。

## 坑 2：I2C0 是共享总线，触摸读最坏能到 800ms

- 板级事实（`esp32p4_touch_gt911.c` 注释写明）：**GT911 的 INT 引脚没引到 SoC**，
  只能**轮询**；而 I2C0 由 **触摸 + 相机 SCCB + ES8311** 共用。
- 实测：触摸单次 I2C 读最坏 **1539ms →（改 devlock trylock 后）419ms → 310ms → 800ms**（随负载波动）。
- 有效手段（按收益排序）：
  1. `nuttx/drivers/input/gt9xx.c` 的 `gt9xx_read()` 把 `nxmutex_lock(&priv->devlock)`
     换成 `nxmutex_trylock()`，锁忙返回 `-EAGAIN`（= 这次没有新样本）——**1539ms → 419ms**，最有效；
  2. I2C 传输处加**有界等待**（`nxmutex_timedlock`，注意坑 1 的多副本问题）；
  3. 在**确定会被链接**的文件里做计时（我们最终放在 `gt9xx.c`：
     `g_dbg_touch_i2c_us(_max)`）。
- **无效手段**：把 LVGL 输入读周期 30ms 调到 50ms —— 实测反而撞上 800ms 的停顿，
  说明瓶颈是"传输本身"而不是"读得太频繁"。
- 结论：这部分残留是**驱动/硬件层**的，应用层只能减轻。

## 坑 3：PPA（2D 硬件加速）编进构建的完整清单

1. **HAL 源列表在** `nuttx/arch/risc-v/src/esp32p4/hal_esp32p4.cmake` 的 `HAL_SRCS`
   （由 `espressif/CMakeLists.txt` 的 `include(.../hal_${CHIP_SERIES}.cmake)` 引入）。
   默认**只编 `upper_hal_dma`**，PPA 完全没进构建。
2. 需要补的源（缺一个就 `undefined reference`）：
   `upper_hal_ppa/src/ppa_{core,srm,blend,fill}.c`、`esp_hal_ppa/ppa_hal.c`、
   `esp_hal_dma/dma2d_hal.c`、`esp_hal_dma/<chip>/dma2d_periph.c`、`upper_hal_dma/src/dma2d.c`。
3. **FreeRTOS/IDF 兼容缺口**：`freertos/portmacro.h`（转包含 `FreeRTOS.h` 即可，
   `portMUX/CRITICAL` 已映射到 `esp_os_*`）+ `freertos/semphr.h`
   （`xSemaphoreCreateBinaryWithCaps` / `vSemaphoreDeleteWithCaps` / `xSemaphoreTake/Give(FromISR)`
   → 用容量 1 的 `esp_os_queue_*` 实现）+ IDF 的 `__containerof`
   （部分源看不到，用 `target_compile_options(arch PRIVATE -include .../ppa_compat.h)` 注入）。
4. **cache 一致性**：PPA 是 DMA 主设备，CPU 写完要 `esp_cache_msync(C2M)`，
   PPA 写完读回要 `esp_cache_msync(M2C)`；缓冲按 **128B（L1+L2 line）** 对齐。
5. 颜色坑：`fill_color_val` 按 **ARGB8888** 解释再转 RGB565 落盘
   （传 `0xf800` 得到 `0x07c0`），断言别直接比原始值。
6. 验证方式：`deskmate --ppa-test` → `PPA: fill selftest OK`，结果写
   `g_esp_ppa_test_rc`（JTAG 可读，0=通过）。

## 坑 4：ISP 能出 RGB565，但接不进去

- 结论：**ISP 支持 CSI 输入 → RGB565 输出，且 `demosaic_en=1`（硬件去马赛克）**，
  见 `components/esp_hal_cam/esp32p4/include/hal/isp_ll.h` 的
  `isp_ll_set_output_data_color_format(ISP_COLOR_RGB565)`。
- 但把 `esp_csi.c` 的 bypass 换成真 ISP 管道后，控制器报
  `esp_cam_new_csi_ctlr(): failed to configure format conversion`（262）——
  **格式转换要求通过官方 `esp_isp_new_processor()` 创建的 ISP 处理器对象**，
  直接写 LL 寄存器不够。要做得把 `esp_csi.c` 迁到
  `esp_isp_new_processor + esp_cam_new_csi_ctlr` 组合（一次较大的驱动重构）。

## 坑 5：长跑取证在本机不可靠

- **JTAG 单次读**可以，但**循环里反复 halt/resume 会卡住**（脚本里读到一半就没下文）。
- **串口在长跑场景会停止输出**（`heartbeat:` 一行都没有、`cat /tmp/xxx.txt` 读不回来）——
  与之前遇到过的 `nsh_consolewrite` 问题同源。
- 可靠做法：**只在开始/结束各读一次** JTAG 计数器，或用**自检的 4 秒窗口指标**
  多次采样取统计；长跑只用于**定性**结论（无 panic、计数单调增长、应用存活）。
