# 触摸采样率改造：前后对比（2026-11-06）

> 判据全部来自**硬件实测**，不来自观感：
> - 采样率/总线时间：PXView 逻辑分析仪（1 MS/s，ch0=SDA，ch1=SCL，解码器 `0:i2c`）
> - 应用与驱动计数：JTAG 读全局符号（`tools/test/hw_var_read.sh` 同款做法）
> - 端到端：`deskmate --selftest --camera` 的 28 项判据

## 一、结论

| 指标 | 改造前 | 改造后 | 倍数 |
|---|---|---|---|
| **触摸采样率** | **7.1 Hz** | **79.4 Hz**（三次独立复测 78.5 / 78.9 / 79.4） | **11×** |
| 采样间隔 p50 | 120 ms | **9.0 ms** | 13× |
| 采样间隔 p90 | 268 ms | 9.0 ms | 30× |
| 采样间隔 max | 405 ms | 66.6 ms | 6× |
| 单次 `read()` 端到端 p50 | 17.7 ms | **≈ 0**（不再做 I²C） | — |
| 单次 `read()` 端到端 max | 204.6 ms | ≈ 0 | — |
| 单周期总线时间 | 0.99 ms | 1.50 ms | 1.5×（读 8 字节替代 3 笔） |
| 总线占用率 | 0.71 % | 12.6 % | 18×（仍远低于饱和） |
| 事件语义 | 只有 `TOUCH_DOWN` | `DOWN` → `MOVE`×n → 恰好 1 次 `UP` | — |
| `ui:responsive` max_busy | 620 ms | **34 ms** | 18× |
| `cam:fps`（4 s 窗口） | 2 fps（prio 90 时） | **6 fps** | 3× |
| `deskmate --selftest --camera` | — | **28/28 PASS** | — |

## 二、采样率与总线（PXView，20 s 窗口）

| 指标 | 前 | 后 |
|---|---|---|
| 完整读周期数 | 141 / 20 s | 1571 / 20 s |
| 事务形状 | `Wdd / Rd / Wddd` | `Wdd / Rddddddd / Wddd` |
| 纯总线时间 p50 | 0.988 ms | 1.50 ms |
| 组内事务间隙 p90 | 55 ms | 无长间隙 |
| 总线占用 | 0.71 % | 11.8 % |

**判读**：改造只是把"3 笔小事务"换成"1 笔 8 字节读 + 1 笔清状态"，
单周期总线时间从 0.99 → 1.59 ms；但因为不再有 50 ms 的 `poll()` 空等和
20 ms 的 tick 量化，**采样率提升了 11 倍而总线仍只用 12.6 %**。

最终形态的事务形状是 `9 / 21 / 11` 条注释（读 8 字节那笔注释更多），
采样间隔分布已经收敛成"几乎恒为 9.01 ms"，p90 与 p50 相同 —— 说明定时器链
稳定，不再有随机长尾。

## 三、tick 粒度 A/B

| `CONFIG_USEC_PER_TICK` | 定时器触发 / 5 s | 实际采样 / 5 s | 采样率 |
|---|---|---|---|
| 10 000 µs（默认） | 251 | 179 | 35.2 Hz |
| **1 000 µs（现用）** | 557 | 394 | **78.5 Hz** |

⇒ `wd_start(MSEC2TICK(8))` 在 10 ms tick 下只能取 1 tick，且每次重挂对齐到
下一个 tick 边界，8 ms 的周期被量化成 20 ms。**传输搬进 worker 之后，
tick 粒度成为限制项** —— 已写入板级 defconfig。

> 注意：`docs/30_实现/应用层_DeskMate_UI.md` §「否证 1」记录的
> "tick 10ms→1ms 没收益"是在**读仍在 read() 里同步做 I²C** 时测的，
> 那时瓶颈是抢占。两个结论不矛盾，前提不同。

## 四、线程优先级 A/B（相机采集线程）

| 优先级 | `cam:fps` | `ui:responsive` max_busy |
|---|---|---|
| 100（与 UI 同权，**现用**） | 4 fps | 70 ms |
| 90（低于 UI） | 2 fps | 219 ms |

⇒ **降优先级两边都变差**：线程只是在 poll/mutex 上等更久，一旦拿到 CPU
仍要一次性做完整帧转换。解法是降低单帧转换成本，不是调优先级。
（`DM_CAMERA_THREAD_PRIORITY` 宏保留为 100，注释里写清了这次实验。）

## 五、A/B 之外修掉的三个真 bug（都是这一轮才暴露的）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 注入 (512,300) 却报 (432,551) 之类错坐标 | 合并读后坐标偏移没跟着改：GT9xx 从 0x814E 顺序排布是 `status, track_id, x_lo, x_hi, y_lo, y_hi`，按老的 `buf[1..4]` 解会把 track_id 当 x 低字节 | 改成 `buf[2..5]` |
| 2 | 相机起来几十毫秒后 `Load access fault`，EPC 落在 `lv_obj_get_screen`，MTVAL 是 `0x7d` | 采集线程栈被压到 4096（默认 16384），栈溢出冲掉相邻堆对象 | 恢复默认栈；显示看门狗同样恢复默认 |
| 3 | 同一 NSH 会话里第二次跑 `deskmate` 必崩，崩溃点同上 | `lv_deinit()` 释放了 LVGL 对象，但 `dm_ui.c` 与 5 个页面模块的 `static lv_obj_t *` 没清零；只修 `dm_ui.c` 不够（试过，仍崩） | 在 `deskmate_main()` 加进程内静态标志**明确拒绝第二轮**并打印原因（复位即可重跑）—— 用拒绝代替一个涉及 6 个文件的修复 |

## 六、复现方法

```bash
# 1) 构建并烧录
cd /home/ez/share/openvela
./build.sh vendor/espressif/boards/esp32p4/esp32p4-function-ev-board/configs/nsh --cmake -j8
cd contest2026_342_ezdezhandui && bash tools/build_flash/usb_stable.sh

# 2) 串口（Tabby 会话 c9cba921-...）跑自检
deskmate --selftest --camera
#   → DM-SELFTEST RESULT: PASS (28/28)

# 3) 采样率：PXView 抓 20 s，按"每 3 笔事务一组"求组首间隔均值
#    详见 docs/50_排障经验/13_用逻辑分析仪定位触摸延迟.md

# 4) 驱动侧分段计数（串口每 5 s 一行）
#    [dm] touch: ticks=.. xfers=.. err=.. events=.. lock=../..ms xfer_max=..us hist=..
#    ticks 涨 xfers 不涨 => LPWORK 被饿死
#    xfers 涨 hist 高   => 总线/控制器慢
#    两者都涨 events 少 => 两次采样之间丢了动作
```
