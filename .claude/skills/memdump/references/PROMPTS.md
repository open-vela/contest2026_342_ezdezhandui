# Prompt 模板集合

本文档提供各种memdump分析场景的AI Prompt模板，可直接使用或修改。

---

## 基础分析

### 单核系统分析
```
请根据 {日志文件} 中的 memdump 信息，配合 {ELF文件}，
分析 {线程名} 线程的 heap 占用情况。

要求：
- 统计总内存、分配次数、开销比例
- 列出 Top 10 最大分配并解析完整 backtrace
- 按功能模块分类统计内存占用
- 给出优化建议
```

**示例**：
```
请根据 startup.log 中的 memdump 信息，配合 vela_audio.elf，
分析 mediad 和 media_trigger 线程的 heap 占用情况。

要求：
- 统计每个线程的总内存占用、分配次数、平均分配大小
- 列出 Top 15 最大的内存分配
- 解析每个大分配的 8 层完整 backtrace
- 分析内存用途并给出优化建议
```

### 多核系统分析
```
请根据 {日志文件} 中的 memdump 信息分析 heap 占用情况。

系统配置：
- CPU0 ({架构}): {ELF文件}，运行 {任务列表}
- CPU1 ({架构}): {ELF文件}，运行 {任务列表}

要求：
1. 识别日志中哪些 memdump 来自 CPU0，哪些来自 CPU1
2. 使用对应的 ELF 文件解析 backtrace
3. 分别统计每个核心的内存占用情况
4. 列出每个核心的 Top 10 大分配
5. 分析跨核心的内存使用模式
```

**示例**：
```
请根据 startup.log 中的 memdump 信息分析 heap 占用情况。

系统配置：
- CPU0 (ARM): cpu0_vela.elf，运行 mediad, media_trigger
- CPU1 (Xtensa): cpu1_vela.elf，运行 audio_dsp, codec_task

要求：
1. 识别日志中哪些 memdump 来自 CPU0，哪些来自 CPU1
2. 使用对应的 ELF 文件解析 backtrace
3. 分别统计每个核心的内存占用情况
4. 列出每个核心的 Top 10 大分配
5. 分析跨核心的内存使用模式
```

## 差异对比

### 事件前后对比
```
请对比 {日志文件} 中 {事件} 前后的 heap 变化。

分析线程: {线程1}, {线程2}, {线程3}

要求：
- 找出被释放和新增的分配
- 解析有差异的 backtrace
- 统计内存变化的大小和分配数量
- 分析事件对内存的影响
```

**示例**：
```
请分析 tmp.log 中的 memdump 内容，对比在 L1 wakeup event 前后，
mediad、media_trigger、abufsink@soundtrigger 三个线程的 heap 占用变化。

要求：
1. 找出被释放和新增的内存分配
2. 解析差异部分的完整 backtrace
3. 分析事件对内存的影响
```

### 版本对比
```
请对比两个版本的内存使用情况。

- 版本A: {日志文件A}
- 版本B: {日志文件B}

要求：
1. 统计总内存变化（增加/减少了多少）
2. 找出新增和减少的分配点
3. 分析主要差异的原因
4. 评估版本B的内存优化效果
```

## 泄漏检测

### 初步泄漏检测
```
请分析 {日志文件} 中的 memdump 数据，检测是否存在内存泄漏。

分析维度：
1. 总分配数是否异常增长
2. 按 backtrace 分组后，哪些调用路径的分配在增长
3. 是否有分配只增不减的模式
4. 预估每次操作的平均内存增长
```

### 多时间点增量对比
```
请对比以下多个时间点的 memdump：
- T1: {file1} (操作 0 次)
- T2: {file2} (操作 10 次)
- T3: {file3} (操作 20 次)

计算：
1. 每次操作的平均内存增长
2. 增长最快的 backtrace 及其调用栈
3. 预估 N 次操作后的内存占用
4. 判断是否存在泄漏
```

**示例**：
```
请分析以下三个时间点的 memdump，检测内存泄漏：
- baseline.log: 系统启动稳定后
- mid.log: 执行播放/停止操作 10 次后
- final.log: 执行播放/停止操作 20 次后

重点关注：
1. 分配总数是否持续增长
2. 哪些 backtrace 的分配数量在增长
3. 增长速率是多少（每次操作增加多少分配）
```

### 泄漏深度分析
```
已发现以下可疑的泄漏点：
{backtrace 列表}

请：
1. 解析完整 8 层调用栈到源码位置
2. 分析每个分配的生命周期应该如何管理
3. 指出可能缺少释放的位置
4. 识别泄漏模式（事件处理/错误路径/循环引用/缓存增长）
5. 给出具体的修复建议
```

**示例**：
```
已确认以下 backtrace 存在泄漏：
0x115d114a → 0x115b62ba → 0x115fd67d → 0x115fdb92

每20次播放操作新增约150个分配，总计约60KB。

请：
1. 解析完整调用栈到源码位置
2. 分析哪个函数应该负责释放
3. 检查是否有对应的 free/release 调用
4. 给出修复建议（包括所有返回路径的检查）
```

## Backtrace 解析

### 单个Backtrace解析
```
请解析以下地址的调用栈：
{地址列表}

使用 ELF 文件: {ELF文件}

要求：
- 解析到函数名、源文件、行号
- 使用 c++filt 处理 C++ mangled 符号
- 按调用深度格式化输出
```

**示例**：
```
请解析以下地址的完整 backtrace：
0x115d114a 0x115b62ba 0x115fd67d 0x115fdb92

使用 ELF 文件: vela_audio.elf
工具链: xtensa-esp32-elf-addr2line

要求：
1. 解析为函数名和源文件:行号
2. 分析这个分配的可能用途
3. 指出应该在哪里释放
```

### 批量Backtrace解析
```
请解析 Top 10 大分配的 backtrace：

{分配列表，包含大小和backtrace}

使用 ELF 文件: {ELF文件}

对每个分配：
1. 解析完整调用栈
2. 分析分配用途
3. 评估是否合理
4. 给出优化建议
```

## 特定场景分析

### 启动阶段分析
```
请分析系统启动阶段的内存占用。

日志文件: {启动日志}
ELF文件: {ELF文件}

要求：
1. 统计启动完成后各线程的内存分配
2. 识别占用内存最大的模块
3. 分析是否有异常大的分配
4. 给出启动内存优化建议
```

### 播放场景分析
```
请分析播放过程中的内存使用。

- 播放前: {before.log}
- 播放中: {playing.log}
- 播放后: {after.log}

要求：
1. 对比播放前后的内存变化
2. 分析播放过程中的临时分配
3. 检查播放结束后是否完全释放
4. 评估播放的内存开销
```

### 录音场景分析
```
请分析录音过程中的内存使用。

- 录音前: {before.log}
- 录音中: {recording.log}
- 录音后: {after.log}

要求：
1. 对比录音前后的内存变化
2. 分析录音缓冲区的大小和数量
3. 检查录音结束后是否完全释放
4. 评估录音的内存开销
```

## Prompt 使用技巧

### 1. 明确目标
- ✅ "分析mediad线程的内存占用"
- ❌ "看看内存"

### 2. 提供完整上下文
- 指定具体的日志文件
- 提供ELF文件路径
- 说明系统配置（单核/多核、架构）
- 描述操作步骤和场景

### 3. 分步深入
- 先做整体统计
- 再分析Top分配
- 最后深入可疑点

### 4. 使用具体数值
- ✅ "Top 15 大分配"
- ❌ "主要分配"

### 5. 明确输出格式
- 需要表格还是列表
- 需要图表还是文本
- 需要代码还是分析

## 提示词模板变量

常用变量和占位符：

| 变量 | 说明 | 示例 |
|------|------|------|
| {日志文件} | 日志文件名 | startup.log, tmp.log |
| {ELF文件} | ELF调试文件 | vela_audio.elf |
| {线程名} | 目标线程名称 | mediad, media_trigger |
| {事件} | 关键事件 | L1 wakeup, 播放开始 |
| {架构} | CPU架构 | ARM, Xtensa, RISC-V |
| {任务列表} | 任务名称列表 | mediad, audio_dsp |
| {地址列表} | Backtrace地址 | 0x115d114a ... |
| {分配列表} | 分配记录列表 | PID Size Overhead... |
