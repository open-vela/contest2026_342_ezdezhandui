# ES8311 音频（I2S + GDMA）与语音播放 —— 实现说明

> 版本：2026-10-23 · 状态：**驱动链路已编入固件并通过构建验证**（板端出声待上板复测）
> 相关：`docs/STATUS.md` §五、`docs/08_WiFi_SDIO实现.md`（WiFi 部分另见该文）

## 一、目标与结论

把板载 ES8311 codec 打通成一条**标准 NuttX 音频设备**（`/dev/audio/pcm0`），
使上层（nvplayer / ai_agent 的 TTS 播报）无需知道 codec 如何接线。

**关键结论：音频不需要新写驱动。** 两半都已经在上游树里：

| 环节 | 已有实现 | 位置 |
|---|---|---|
| codec 寄存器序列（I2C 控制 + I2S 数据）| `es8311.c`（2273 行，完整 lower-half）| `nuttx/drivers/audio/es8311.c` |
| I2S 控制器 + **GDMA 搬运** | `esp_i2s.c`（3532 行）| `nuttx/arch/risc-v/src/common/espressif/esp_i2s.c` |
| WAV/PCM 前端 | `pcm_decode.c` | `nuttx/audio/pcm_decode.c` |

缺的**只是板级粘合**：告诉 codec「你在哪根 I2C、哪个地址」，告诉 I2S
「五根线接在哪」，再在 codec 配好之后打开功放。所以本次新增的板级代码只有
约 300 行，且**没有 fork 任何一个驱动**。

## 二、硬件接线（来源：官方原理图，非推测）

取自 `ESP32_P4X_C5_Function_EV_board-2.0-schematics.pdf`（Espressif 官方下载），
已与 `docs/ref_stock_boot_esp-idf_v5.5.2.log`（原厂 IDF 固件启动日志）交叉核对。

| 原理图网名 | ESP32-P4 | 方向 | 说明 |
|---|---|---|---|
| `I2S_MCLK`  | GPIO13 | P4 → codec | 主时钟 |
| `I2S_SCLK`  | GPIO12 | P4 → codec | 位时钟 BCLK |
| `I2S_LRCK`  | GPIO10 | P4 → codec | 帧/字选择 WS |
| `I2S_DSDIN` | **GPIO9**  | **P4 → codec** | 播放数据（进 codec DAC）|
| `I2S_ASDOUT`| **GPIO11** | **codec → P4** | 录音数据（出 codec ADC）|
| `PA_CTRL`   | GPIO53 | P4 → 功放 | NS4150B 使能，高有效 |
| `I2C0` SDA/SCL | GPIO7 / GPIO8 | — | **与 GT911 触摸、SC2336 摄像头共用**，codec 地址 `0x18` |

### ⚠️ 最容易踩的坑：两个数据脚是反的

原理图网名是**以 codec 为主语**命名的，与主机方向**相反**：

- `I2S_DSDIN` = codec 的 *D*igital *S*erial *D*ata *IN*（codec 的**输入**）
  → 对应 **主机输出** → `CONFIG_ESPRESSIF_I2S0_DOUTPIN=9`
- `I2S_ASDOUT` = codec 的 *A*DC *S*erial *D*ata *OUT*（codec 的**输出**）
  → 对应 **主机输入** → `CONFIG_ESPRESSIF_I2S0_DINPIN=11`

按字面把 DOUTPIN 填成 11、DINPIN 填成 9，现象就是**扬声器完全无声**且没有任何报错。
（同类现象在 Guition JC-ESP32P4-M3-DEV 上被独立记录过：该板原理图甚至把
GPIO48 的网名标成 `ES7210_SDOUT`，而板上根本没有 ES7210。）

### MCLK 不是可选项

`CONFIG_ESPRESSIF_I2S0_MCLK` 必须开。ES8311 用 `MCLK ÷ 采样率` 的比值查内部
分频表（`nuttx/drivers/audio/es8311.h` 的 `es8311_coeff_div[]`），表里只收录了
那些 256× 频点。`esp_i2s.c` 对 16bit 数据取 `mclk = rate × 256`，正好落在
`12.288 MHz / 24 kHz` 这一项上。因此：

- 可用采样率：8k / 12k / 16k / 24k / 32k / 48k（均按 256× 命中）
- **语音播报推荐 24 kHz**：比 48 kHz 少一半 APLL 频率与 PSRAM 带宽

## 三、代码结构（低耦合高内聚）

```
board/esp32p4/esp32p4-function-ev-board/
├── include/esp32p4_audio_es8311.h      # 对外只有 2 个函数
└── src/esp32p4_audio_es8311.c          # 全部板级知识集中在这一个文件
```

对外接口刻意收得很窄：

| 函数 | 作用 |
|---|---|
| `esp32p4_audio_es8311_initialize()` | 唯一入口，建立整条链路并注册 `/dev/audio/pcm0`；幂等 |
| `esp32p4_audio_pa_set(bool)` | 单独控制 NS4150B 使能（长空闲时省电用）|

`esp32p4_bringup.c` 里只有一处调用，且与通用路径**互斥**：

```c
#if defined(CONFIG_ESP32P4_FUNCTION_EV_BOARD_AUDIO_ES8311)
  ret = esp32p4_audio_es8311_initialize();
#elif defined(CONFIG_ESPRESSIF_I2S)
  ret = board_i2s_init();          /* 通用 I2S 音频设备 */
#endif
```

**为什么互斥**：两条路径都要占用 I2S0，同时注册会是两个音频设备抢一个端口，
后开流的一方会死锁。互斥保证「一个端口，一个设备」。

分层关系：

```
  应用 (nxplayer / TTS)
        │  open/write /dev/audio/pcm0
   ┌────▼─────────────────────┐
   │ pcm_decode.c  (WAV 解析) │  上游
   ├──────────────────────────┤
   │ drivers/audio/es8311.c   │  上游：codec 寄存器、音量、worker 线程
   ├──────────────────────────┤
   │ esp_i2s.c                │  上游：I2S 控制器 + GDMA
   ├──────────────────────────┤
   │ esp32p4_audio_es8311.c   │  ★ 本次新增：只管"接在哪"
   └──────────────────────────┘
```

## 四、构建期发现并修复的 4 个上游缺陷

这些都是**打开 I2S/音频开关才会暴露**的潜伏缺陷，此前从没被这个配置路径触发过。

### 4.1 `esp_i2s.c` 缺 3 个头文件（链接期 undefined reference）

`esp_i2s.c` 用到了 `struct work_s`/`HPWORK`、`kmm_free`、`nxmutex_*`，却一个头
都没包含。C 语言下这不会报编译错，只会生成"外部调用"，到链接期才炸：

```
undefined reference to `HPWORK` / `kmm_free` / `nxmutex_lock` / `nxmutex_unlock`
```

修复：补 `<nuttx/wqueue.h>`、`<nuttx/kmalloc.h>`、`<nuttx/mutex.h>`。

> 注：`nxmutex_*` 默认是 `nuttx/mutex.h` 里的 `static inline`，包含头即可内联展开；
> 不包含则退化成对**并不存在的**外部符号的调用。

### 4.2 `drivers/audio/es8311.c` 缺 `<nuttx/mutex.h>`

同上，`es8311.c` 用了 `nxmutex_*` 但没包含。同目录的 `es8388.c`、`cs43l22.c`
**都有**这一行 —— 属于 es8311 单独漏掉。

### 4.3 同名公私头文件的混淆风险（已排查，结论：当前不需改动）

`es8311.c` 写的是 `#include "es8311.h"`，期望拿到**私有**头
（`drivers/audio/es8311.h`，含 `struct es8311_dev_s`、寄存器地址、`es8311_coeff_div[]`），
而树里还有 `include/nuttx/audio/es8311.h`（**同一个 basename**、**不同的 include guard**、
只有公有声明）。

排查过程中的一个"假象"值得记录：中途编译报出 400+ 条
`invalid use of undefined type 'struct es8311_dev_s'`，一度被判断为"私有头没被找到"。
真实原因是**生成的 `include/nuttx/config.h` 陈旧**（不含 `CONFIG_AUDIO`），
导致私有头里的 `#ifdef CONFIG_AUDIO` 整段被跳过 —— 头其实找到了，只是内容被条件编译掉了。
重新生成 config.h 后这些错误全部消失。

**当前不需要任何 CMake 改动**：C 语言规定 `#include "x.h"` 先查**包含者所在目录**，
`drivers/audio/es8311.h` 因此必然优先命中，公有头只在私有头缺失时才会被误用。
（曾试过用 `target_include_directories(drivers PRIVATE .../drivers/audio)` 兜底，
验证后确认多余，已移除，保持改动面最小。）

> 顺带一提：`wm8994.c` / `cs43l22.c` / `vs1053.c` 用同样的写法，
> 目前也没有启用，若将来启用应留意同类条件编译问题。

### 4.4 板级 Kconfig：`select` 无法穿透 `menuconfig`

```kconfig
menuconfig DRIVERS_AUDIO      # 无依赖，但必须显式命名
if DRIVERS_AUDIO
config AUDIO_ES8311
    depends on AUDIO          # ← 直接依赖
```

`select AUDIO_ES8311` 会因 `depends on AUDIO && DRIVERS_AUDIO` 不满足而**静默失效**。
`olddefconfig` 的告警是：

```
warning: AUDIO_ES8311 ... has direct dependencies AUDIO && DRIVERS_AUDIO with
value n, but is currently being y-selected by ESP32P4_FUNCTION_EV_BOARD_AUDIO_ES8311
```

→ 必须在 defconfig 里显式写 `CONFIG_AUDIO=y` 与 `CONFIG_DRIVERS_AUDIO=y`。

# 附录：真机上板实录（2026-10-23，本轮新增）

本节记录**在真板上跑出来的**结果。上板前本文件的所有结论都是构建期的（编译、链接、
符号、反汇编）；上板后纠正了其中若干条，并把**只有真机才能暴露的 3 个驱动缺陷**定位出来。

## A.1 已经真机验证通过的

```
ES8311: speaker PA enabled (GPIO53)
ES8311 ready: I2S0 (MCLK=13 BCLK=12 WS=10 DOUT=9 DIN=11), I2C0 addr 0x18 -> /dev/audio/pcm0
```

- `/dev/audio/pcm0` 在 `ls /dev/audio` 中真实存在
- I2C0 在 400 kHz 与 100 kHz 下都由 `0x18` 应答（与 GT911 `0x5d`、SC2336 `0x30` 共存）
- I2S 时钟计算正确：`mdiv=26 → mclk=6144000 Hz`（= 24000 × 256），`bdiv=4 → bclk=1536000`
- `AUDIOIOC_CONFIGURE` 在 24000 Hz / 16bit / 立体声下成功
- 缓冲区分配、`AUDIOIOC_ENQUEUEBUFFER`、`AUDIOIOC_START` 全部成功
- ES8311 worker 线程真实运行，日志可见 `AUDIO_MSG_ENQUEUE`
- **DMA 传输完成、缓冲区被归还**：`AUDIO_MSG_COMPLETE` 与 `es8311_returnbuffers` 各出现多次

也就是说：**从应用到 codec 的数据通路是通的**。

## A.2 真机暴露的 3 个驱动缺陷（已修）

这三个都**不可能在构建期发现** —— 编译链接全部通过，只有真的往 I2S 送数据才崩。

### A.2.1 `es8311.c` 用 `ERANGE` 拒绝了合法配置

```c
ret = -ERANGE;                                          /* 悲观默认值 */
...
ret = es8311_setsamplerate(priv) == -ENOTTY ? OK : ret;  /* OK 被丢弃！ */
```

三元表达式的 `OK` 算出来就扔了，`ret` 仍是 `-ERANGE`。后果：**任何**合法的
输出配置都返回 `ERANGE`，播放器第一步 `AUDIOIOC_CONFIGURE` 就失败
（真机现象：`audiotest: AUDIOIOC_CONFIGURE failed: 34`）。
`AUDIO_TYPE_INPUT` 分支有一模一样的写法。

修复：直接取返回值，只有 `-ENOTTY`（"I2S 不支持运行时改速率"）才视为成功。

### A.2.2 `esp_i2s.c` 的 cache 对齐循环会下溢到 ~13 亿

```c
for (; bufsize % alignment != 0; aligned_frame_num--)   /* uint32_t */
  {
    bufsize = aligned_frame_num * bytes_per_frame;
    carry_size += bytes_per_frame;
  }
```

终止条件在条件表达式里，而循环体第一句就把 `bufsize` 改成一个**仍然不对齐**的值，
于是 `aligned_frame_num` 一路减到 0 再回绕成 ~40 亿，`bufsize` 变成 ~13 亿。
真机现象：

```
i2s_send: Required buffer size can't fit into DMA outlink (exceeds in 1300+ MB bytes)
es8311_processbegin: I2S transfer failed: -27
```

**触发条件极其常见**：WAV 流以 44 字节头开始，使首个 `samp_size = 8192 - 44 = 8148`
不是 64 的倍数。换言之**只要是 WAV 播放就必然踩到**。

修复：直接算出向下对齐的帧数（`(n / frames_per_line) * frames_per_line`），
无循环、无回绕，且当单帧大于一个 cache line 时也有定义。

### A.2.3 `esp_i2s.c` 的 carry 缓冲区只有 4 字节，却最多拷 64 字节

```c
struct esp_buffer_carry_s { uint32_t value; size_t bytes; };   /* value 只有 4 字节 */
...
memcpy(&priv->tx.carry.value, samp, priv->tx.carry.bytes);      /* 可能拷到 63！ */
```

cache 对齐会把最多 63 字节留给下一个缓冲区，而 `value` 只有 4 字节 ——
多出来的直接**越过 `value` 写进紧邻的 `bytes` 字段**，长度把自己写坏。
下一块读回来的"长度"其实是音频采样值（真机测得 `1298550118`），于是被判定超限。

真机现象与 A.2.2 相似（都是 `can't fit into DMA outlink`），但根因完全不同：
A.2.2 让 `bufsize` 变大，A.2.3 让 `bytes` 变大。**两者必须都修**，只修一个仍会复现。

修复：`value` 改为 `uint8_t value[64]`，加 `DEBUGASSERT` 上界，按字节数组语义使用。

### A.2.4 顺带修的分配大小

对齐逻辑把实际拷贝量减到 `samp_size - carry_size`，但缓冲区是按 `bfcontainer->nbytes`
分配的，而 carry 回填又会多写 `carry` 字节 → 堆越界。改为按 `samp_size` 分配。

## A.3 配置层面的两处真机发现

| 现象 | 真因 | 处置 |
|---|---|---|
| `AUDIOIOC_GETBUFFERINFO failed: 25` (ENOTTY) | `es8311.c` 里该命令被 `#ifdef CONFIG_AUDIO_DRIVER_SPECIFIC_BUFFERS` 包着，选项没开 | defconfig 打开该选项 |

## A.4 仍未完成（诚实记录）

- ~~`audiotest` 自检程序未能跑到收尾打印~~ —— **2026-10-26 已修复并验证**。

  两个真因，都在自检程序里（驱动侧一直是对的）：

  1. **消息队列的 `mq_msgsize` 设成了 32，而 `mq_receive` 只给 8 字节缓冲。**
     POSIX 规定接收缓冲小于队列声明最大值时直接返回 `EMSGSIZE`，**不截断**。
     于是每次 `mq_receive` 立刻失败、完成循环空转，随后 `AUDIOIOC_ENQUEUEBUFFER`
     在队列满时阻塞 —— 看起来像驱动卡死，实际是这一行。
     `nxplayer` 用的是 `attr.mq_msgsize = sizeof(struct audio_msg_s)`，照抄即可。
  2. **发流循环永远只用 `buffers[0]`**，即在缓冲区仍归驱动所有时重复入队同一个
     `ap_buffer_s`。必须按 DEQUEUE 回填、轮转使用。

  修复后真机实测（2 秒 / 24 kHz / 16bit 立体声）：

  ```
  audiotest: 192044 stream bytes in 4 x 8192 buffers
  audiotest: playing...
  audiotest: queued 192044 bytes
  audiotest: done
  ```

  并复测了变体：`-t 1 -s`（扫频）、`-t 3 -f 880`、`-t 1 -r 16000` 全部 `done`。
  **整条链路（应用 → pcm_decode → es8311 → I2S/GDMA → 扬声器）跑通并正常收尾。**
- **"扬声器里听到声音"仍未经人耳确认**（不在我手边）。已确认的是：全部
  192044 字节被驱动接收、DMA 完成、缓冲区逐块归还、程序正常退出。

# 附录 B：标准播放器路径（`nxplayer`）与第二个缓存缺陷（2026-10-26 下午）

## B.1 `nxplayer` 暴露的缓存同步缺陷（已修）

用自检程序播放是"自己写的程序 + 自己的驱动"，所以又用**标准播放器**验证了一遍：
先用 `audiotest -w /tmp/t.wav -t 2` 在板子上生成一个真正的 WAV（192044 字节），
再让 `nxplayer` 去放。`nxplayer` 立刻报出：

```
E (42861) cache: esp_cache_msync(126): start address: 0x4ffae600,
  or the size: 0x1fd4 is(are) not aligned with cache line size (0x40)B
```

`0x1fd4 = 8148`，正是"8192 − 44 字节 WAV 头"的块长度。真因在 `esp_i2s.c` 的
发送路径：缓冲区用 `kmm_memalign(64, samp_size)` 分配（**起始地址对齐**），
但回写用的是 `bfcontainer->nbytes`（**任意长度**，8148 不是 64 的倍数）。
`esp_cache_msync()` 对这种范围直接拒绝，于是 **DMA 有可能读到未回写的陈旧数据**。

修复两处：

1. 分配改为 `ALIGN_UP(samp_size, alignment)` —— 按整条 cache line 分配；
2. 回写改为 `ALIGN_UP(bfcontainer->nbytes, alignment)` —— 覆盖整条 line。

> 这是本轮第二个"只有用标准播放器才暴露"的驱动缺陷。自检程序之所以没踩到，
> 是因为它的块长恰好落在对齐边界上；真实播放器的块长则跟随文件长度。

## B.2 `nxplayer` 一退出就 panic —— 上游 NuttX 的 NULL 解引用（已修）

上一轮记录为"`device` 子命令会崩溃"，**这个结论是错的**。这一轮用
"只启动 + 直接 `q`"复现，确认崩溃与 `device`、`play` **都无关**：
**只要输入一个不带参数的命令**（`q`、`h`、`stop`、`pause`…）就 panic。
之前的两次 panic 全部来自脚本末尾那个 `q`，被误读成了 `device` 的问题。

### 根因（反汇编直接指认）

```
jalr  strtok_r                 ; cmd = strtok_r(buffer, " \n", &arg)
beqz  a0, <skip>               ; cmd 非 NULL，继续
lw    a5, 28(sp)               ; a5 = arg        <-- 此时 arg 是 NULL
lbu   a3, 0(a5)                ; *arg            <-- load access fault, MTVAL=0
```

`strtok_r()` 在"令牌之后没有更多内容"时把 `*saveptr` 置为 **NULL**
（`libs/libc/string/lib_strtokr.c`：`pend` 初值 NULL，只有在找到分隔符时才赋值，
末尾无条件 `*saveptr = pend`）。而 `apps/system/nxplayer/nxplayer_main.c` 里写的是：

```c
cmd = strtok_r(buffer, " \n", &arg);
if (cmd == NULL) continue;
while (*arg == ' ')   /* <-- arg 为 NULL 时直接解引用 */
  {
    arg++;
  }
```

所以 `device pcm0` 不崩（有参数），`q` / `h` 必崩。

### 修复

```c
if (arg == NULL)
  {
    arg = (FAR char *)"";
  }
else
  {
    while (*arg == ' ')
      {
        arg++;
      }
  }
```

### 同类缺陷

同一个模式还在 `apps/system/nxrecorder/nxrecorder_main.c`（录音器）里，
一并修了（本轮该应用未编入配置，属于预防性修复，**未经真机验证**）。
`nxlooper` 也用 `strtok_r`，但它没有解引用 `arg`，不受影响。

### 真机复验

```
=== $ nxplayer
NxPlayer version 1.05
h for commands, q to exit
nxplayer>
=== $ device pcm0
nxplayer>
=== $ play /tmp/t.wav
nxplayer>
=== $ q
nsh>                       <- 干净退出
```

**0 panic / 0 error**，且 `h`（无参帮助）也能正常执行。

> 这条缺陷的影响面远大于本项目：它是 `apps/system/nxplayer` 的通用问题，
> 任何用这个播放器的板子都会在退出时崩溃。

## B.3 自检程序的 `-w` 模式

`audiotest` 新增 `-w <file>`：把同一段流写成标准 WAV 文件而不是直接播放，
用来把"驱动能不能放"和"播放器能不能放"分开验证。

```
audiotest -w /tmp/t.wav -t 2      ->  wrote /tmp/t.wav (192044 bytes: 44-byte header + 192000 PCM)
audiotest -w /tmp/t.wav -t 1      ->  wrote /tmp/t.wav (96044 bytes: 44-byte header + 96000 PCM)
```

> 注意：`/tmp` 是 tmpfs，**复位即清空**。上电后要先重新生成再播。
> （排查过程中曾因为这一点误判成"文件存在却崩溃"，实际是文件没生成。）

## C.2 修掉的缺陷：INPUT 分支同样被 `ERANGE` 误拒

B.1/A.2.1 修的是 `AUDIO_TYPE_OUTPUT` 分支。`AUDIO_TYPE_INPUT` 分支有一模一样的写法：

```c
ret = es8311_setsamplerate(priv) == -ENOTTY ? OK : ret;
if (ret != OK) { break; }          /* ret 仍是 -ERANGE，必然 break */
ret = es8311_setbitspersample(priv) == -ENOTTY ? OK : ret;
```

三元表达式的 OK 依旧被丢弃，`ret` 停在函数开头设的 `-ERANGE`。
真机现象：`audiotest: input CONFIGURE failed: 34`，**采集根本配不起来**。
已按输出分支同样的方式修好（两个分支现在都不再使用那个三元写法）。

## C.3 没做成的一半：数据流不通

修完 ERANGE 后采集能配起来、能 START，但**入队的缓冲区不会被填满后归还**，
调用方卡在 `AUDIOIOC_ENQUEUEBUFFER` 上，最终占住 console。

因为"一个用起来会卡死的设备比没有这个设备更糟"，板级**没有**注册
`/dev/audio/pcm_in0`，`audiotest -c` 的代码保留在树里供后续调试。
判定：这是 ES8311 输入方向与 NuttX 音频上层之间还没打通，属于**未完成项**，

## C.5 第 10 轮的诊断证据（把范围缩到了一处）

重新注册 `/dev/audio/pcm_in0` 并加上**不会被 `-DNDEBUG` 编掉**的 `syslog` 打点后，
真机输出：

```
es8311_enq: mode=1 inflight=0 running=1 nbytes=8192
es8311_enq: mode=1 inflight=1 running=1 nbytes=8192
es8311_enq: mode=1 inflight=2 running=1 nbytes=8192
es8311_enq: mode=1 inflight=3 running=1 nbytes=8192
```

- `mode=1` 就是 `ES_MODULE_ADC` —— **方向选对了**
- `running=1` —— worker 线程在跑
- `inflight` 从 0 涨到 3 —— **4 个缓冲区全部入队成功**，`es8311_enqueuebuffer`
  本身**不会阻塞**（它只是挂链 + 发消息）

然后就停住了：`inflight` 再没降过。也就是说
**`I2S_RECEIVE` 的完成回调 `es8311_processdone` 从未触发 → RX DMA 从未完成**。

已排除的：

| 检查 | 结果 |
|---|---|
| `CONFIG_ESPRESSIF_I2S0_RX` | =1（已编入）|
| `CONFIG_ESPRESSIF_I2S0_DINPIN` | =11（与原理图一致）|
| `i2s_rxdma_start()` 是否启动通道 | 是：内部调用 `i2s_hal_rx_start()` 并置 `rx_started` |
| `i2s_txdma_start()` 是否也如此 | 是（TX 侧同样有 `i2s_hal_tx_start`）|
| MCLK 绑定 TX 时钟那段 | 只在 `role == I2S_ROLE_SLAVE` 分支里；本板是 **MASTER**，不走那里 |

**结论**：不是配置、不是方向、不是入队逻辑，而是
**RX 通道/DMA 在 master 模式下拿不到时钟或没有真正跑起来**。
下一个要看的是 `i2s_configure()` 里 master 分支的
`if (priv->config->rx_en && !priv->config->tx_en)` 这条路径——本板同时使能了
TX 和 RX（播放要用 TX、采集要用 RX），走的是"两者都开"的配置，而运行时只启动了
RX 通道，很可能 I2S 的主时钟来自 TX 侧、TX 没跑就没有 BCLK/WS。

**下一步试验建议**（成本最低的两条）：
1. 采集时顺带把 TX 通道也启动（哪怕没有数据），看 RX DMA 是否立刻开始完成；
2. 或把 `CONFIG_ESPRESSIF_I2S0_TX` 在纯采集配置下关掉，走
   `rx_en && !tx_en` 的专用分支。
