## 二、P0-1 · DNS 不可用

**现象**：NSH `nslookup api.xiaomimimo.com` → `getaddrinfo failed: 1`；ai_agent 侧任何走域名的 HTTPS（LLM）在解析阶段即失败。

**已排除 / 已确认**
- `nuttx.map` 中 **`dns_*` 符号数 = 0** → `CONFIG_NETDB_DNSCLIENT` 未编入（这是主因）。
- 镜像根 FS 只有 `dev/ proc/ tmp/ var/`，无 `/etc`、无 `/etc/resolv.conf`（次要因素）。
- eth0 本身正常（`10.0.0.2 RUNNING`，主机 ping 0% 丢包）。

**方案（推荐 A + B）**

A. 打开 DNS 客户端与配置文件支持（`boards/risc-v/esp32p4/esp32p4-function-ev-board/configs/nsh/defconfig`）：
```diff
+CONFIG_NETDB_DNSCLIENT=y
+CONFIG_NETDB_DNSCLIENT_ENTRIES=8
+# 根 FS 只读、/tmp 是 tmpfs，可写；与 ai_agent 现有 network_set_dns() 的落点一致
+CONFIG_NETDB_RESOLVCONF=y
+CONFIG_NETDB_RESOLVCONF_PATH="/tmp/resolv.conf"
```
> ⚠️ 前置坑：目前一旦启用 `CONFIG_DEBUG_FEATURES=y` 之类会扩大符号可见性的配置，
> CMake 的 kconfig 解析会报 `nuttx_kconfig.cmake:48/76: needs at least 5 arguments`
> 并让 configure 失败（见 §04 §八.4）。先复现并修这个解析问题，再叠加 DNS 配置。

B. 让 DNS 服务器真正进入解析器（两条路，任选其一）：
1. **板级 bringup 注入**：在 `esp32p4_bringup.c` 里调用 NuttX 的
   `dns_add_nameserver()`（用 `CONFIG_ESP32P4_FUNCTION_EV_BOARD_DNS_PRIMARY` 之类的 Kconfig 默认值，如 `192.168.1.1`）。
2. **agent 侧补全**：`network_set_dns()` 目前只 `fprintf("/tmp/resolv.conf")`；
   在写完文件后追加一次 `dns_add_nameserver()`（`#include <nuttx/net/dns.h>`），
   这样 `set_dns` 命令才会立刻生效。

C（可选，最省心）：改用 DHCP —— `CONFIG_NETUTILS_DHCPC=y`，由路由器同时下发地址与 DNS。

**验收（真机断言）**
```bash
python3 tools/board.py run "nslookup api.xiaomimimo.com" --expect "Address|10\.|192\." 
python3 tools/board.py run "ifconfig eth0" --expect "RUNNING"
# 且 nuttx.map 中 dns_ 符号数 > 0
```

## 三、P0-2 · 干净树连续构建失败（✅ 本轮已修）

**现象**：`rm -rf cmake_out` 后连续构建，第二次 configure 报
`git apply 失败：nuttx/esp32p4/include/sdkconfig.h:683/941` → `Configuring incomplete` → `build.sh: config fail`。

**修复（已提交，作品仓同步）**
1. 打补丁前 `git reset --hard ${ESP_HAL_3RDPARTY_VERSION}`，从已知内容开始；
2. 新增 `vela_apply_hal_patch()`：`git apply --check` 通过才 apply；反向 `-R --check`
   通过视为"已应用"；两者都不通过才 `FATAL_ERROR`（并提示 HAL drift）；
3. 固定顺序 **0002 → 0001**（两个补丁都动 `sdkconfig.h`，0001 的 hunk 落在 0002 的锚点上下文里）；
4. 删除 0001 中两段过时 hunk（`components/mbedtls/mbedtls` 的 submodule 指针噪声、HAL 已自带的 MEMPROT 注释）。

**回归验证（每次改构建都要跑）**

PATH=<prebuilts>/build-tools/linux-x86_64/bin:$PATH \
  ./build.sh nuttx/boards/risc-v/esp32p4/esp32p4-function-ev-board/configs/nsh/ --cmake -j8

#      产物 cmake_out/.../nuttx.bin + nuttx/mcuboot-esp32p4.bin

`nuttx_kconfig.cmake` 的 list 语义下被拆出空元素）。

## 四、P1-3 · 摄像头出帧（`VIDIOC_S_FMT` EINVAL）

**现象**：`camera` → `NOTE: capture_initialize() rc=-22`（板级已注册）、
`NOTE: skipping STILL_CAPTURE/JPEG`、`Failed to VIDIOC_S_FMT: errno = 22`；识别阶段正常
（`SC2336 chip ID: 0xcb3a` → `/dev/video0`）。

**为什么现在查不下去**：视频栈的错误日志走 `verr()`，默认**被编译掉**
（`CONFIG_DEBUG_VIDEO_ERROR` 未开），所以只有 errno 没有人话。

**方案（分三步）**

**Step 1（先让错误说话）**
- 先解决 §三 的 `DEBUG_FEATURES` 解析问题，然后打开
  `CONFIG_DEBUG_FEATURES=y` + `CONFIG_DEBUG_ERROR=y` + `CONFIG_DEBUG_VIDEO=y` + `CONFIG_DEBUG_VIDEO_ERROR=y`；
- 目标：拿到 `SC2336: WxH is not supported` / `CSI is configured for WxH` / `only 30 fps`
  这三类之一，直接定位拒绝点。
- 若解析问题短期修不掉，退路：在 `capture_try_fmt()`/`validate_frame_setting()` 临时
  用 `syslog(LOG_ERR, …)` 替代 `verr()`（走 syslog 不受 debug 开关影响），诊断完撤掉。

**Step 2（按定位结果修）**
- 若是**尺寸/帧率校验**：把 app 请求、sensor 表（`g_sc2336_framesizes[] = {1920,1080}`）、
  CSI 配置（`CONFIG_ESPRESSIF_MIPI_CSI_H_RES/V_RES`）三者对齐，并让 `validate_frame_setting`
  在失配时返回 `-EINVAL` 的同时打印双方尺寸（避免下次再盲查）。
- 若是**格式映射**：核对 `convert_to_imgdatafmt()` 对 `V4L2_PIX_FMT_SBGGR10` 的映射，
  以及 `esp_csi.c` 的 `input/output_color = CAM_CTLR_COLOR_RAW10` 通路口径。
- 若是**设备注册时序**：板级 `capture_register()` 未初始化 `capture_inf.clip/frame_interval/state`，
  参照老的 `capture_initialize(mngcfg)` 补齐（按 sensor/imgdata 能力填 clip 与 1/30 fps）。

**Step 3（真正的交付能力：接 ISP）**
- HAL 里已经有 `components/upper_hal_isp/` + `components/esp_hal_cam/isp_hal.c`；
- NuttX 侧把 ISP 串进 `esp_csi.c`：RAW10 → （demosaic/AWB/CCM）→ RGB565 或 YUV422，
  再在 `sc2336.c` 的 fmtdesc 里同时暴露 `V4L2_PIX_FMT_RGB565`/`YUYV`；
- 之后 `camera` 默认格式与 LVGL 预览都能直接用，`CONFIG_EXAMPLES_CAMERA_OUTPUT_LCD` 才有意义。

**验收**
```bash
python3 tools/board.py run "camera 1" --expect "Captured|saved|VIDIOC_S_FMT"   # 不再出现 errno=22
ls /data 或 /mnt 下应能看到抓拍文件（或帧计数递增）
```

## 五、P1-4 / P1-5 · 显示（`/dev/fb0`）与触摸（GT911）

**现象**
- 显示：`EK79007 DCS 0xb2 failed: -110` → `failed to register /dev/fb0: -5`；`ls /dev` 无 `fb0`；`lvgldemo` 无显示。
- 触摸：`GT911 not detected at 0x5d or 0x14`（随后仍注册 `/dev/input0`）。

**已排除**
- **I2C0 没问题**：SC2336 与 GT911 共用 I2C0，摄像头正常应答（`0xcb3a`）。
- 驱动逻辑：LDO→DSI host→DPI 配置→panel init 全流程都走到了，失败在面板无响应。
- SoC 侧：DSI host 已 `registered (2 lanes @ 900 Mbps)`。

**方案：先硬件、后软件**

**Step 1（硬件，0.5 天，必须优先）**
1. 断电重插 **LCD 模组的 FPC**（EK79007 + GT911 同在一块模组上）；
2. 检查 **J1 → J6 跳线**：`GPIO26`(背光) / `GPIO27`(复位) 只在装了跳线时才连到模组适配板
   （代码注释与日志都提示了这一点）；
3. 量模组供电（3V3 与面板 VDD）与复位电平；
4. 复核 FPC 方向与座子压合。

**Step 2（软件容错，1 天）**
1. panel init 失败时打印**更多上下文**（DSI host 状态、DCS 返回值、重试计数），并做 2~3 次
   复位重试（现在只试一次）；
2. 失败时**不注册 fb0 但保留明确的错误路径**（现在是 `-5` 就结束，LVGL demo 直接空白）；
   可选：注册一个 dummy/ramfb，让 `lvgldemo` 至少能跑起来截图自证；
3. 触摸：`gt9xx_register()` 前把"未探测到"与"已探测"区分成两个日志级别，
   并在 `open()` 失败时返回 `-ENODEV`（避免评审误以为触摸可用）；
4. 加一条开机 I2C 扫描日志（0x08~0x77），一眼区分"模组不在"与"地址不对"。

**验收**
```bash
python3 tools/board.py run "ls /dev" --expect "fb0"         # 硬件修好后
python3 tools/board.py run "lvgldemo"                        # 屏上出现 LVGL demo
# 若硬件暂时无法修：至少 lvgldemo 不再静默失败，日志给出明确原因
```

## 六、P2-6 · WebSocket 28789 主机侧不通

**现象**：板端日志 `WebSocket server started on port 28789`（监听已建立），
但从开发主机 TCP 连接被拒/超时；主机 `ip route get 10.0.0.2` → 经 `192.168.1.1`
转发（**非同一二层**），ICMP 通、TCP 不通。

**方案**
1. **把主机与板子放到同一网段**再测一次：板子 eth0 由 `10.0.0.2/24` 改为
   与主机同网段（或路由器加 10.0.0.0/24 的回程路由），这是判定"板端功能"还是"链路"的关键一步；
2. **板端自连用例**（常驻回归，和链路解耦）：`ws_server_start()` 后用 `127.0.0.1:28789`
   做一次 connect/close，日志打印 `ws self-test OK`；
3. 需要一条不依赖 UART0 的运维通道时，可顺带开 `CONFIG_SYSTEM_TELNETD` 或让 WS 打印握手日志。

**验收**：主机 `curl`/python socket 能完成 WS 握手；或板端自检日志 `ws self-test OK`。

## 七、P2-7 · agent 启动后 console 输入无响应

**现象**：agent 启动**前** NSH 交互完全正常（本轮在 USJ 口复验）；
`ai_agent` 一起，NSH 与 agent CLI 都不再回显输入。

**方案**
1. 明确 console 归属：agent CLI 不要和 NSH 抢 `/dev/console`。优先让 CLI 走独立设备
   （`/dev/ttyS0` / USJ 的 `/dev/ttyACM0`），或改为**网络 CLI**（WS/MQTT，复用已有通道）；
2. 若必须留在 console：把 CLI 的读循环放到独立线程并显式设置 termios（raw、非阻塞），
   且**不得**修改 NSH 已设置的终端属性；用 `poll()` + 超时避免独占；
3. 加一条"console 占用"日志（谁打开、谁设置 termios），便于下次 5 分钟定位。

**验收**：`ai_agent` 运行期间 `ps`、`free` 等 NSH 命令仍可执行；
或 agent CLI 在独立通道上可交互。

## 八、P3-8 · CP2102 UART 桥消失（环境）

**现象**：`/dev/ttyUSB0` 不存在；`lsusb` 只有 Espressif USJ（`303a:1001`），
无 CP2102（`10c4:ea60`）；`cp210x` 驱动已加载但无设备。

**处理**
1. 重新插拔板子的 USB-UART 口，或在 VMware 里把 CP2102 重新连接到该虚拟机；
2. **备用通道（已验证可用）**：把 console 切到 USJ 口即可继续调试：
```diff
+CONFIG_ESPRESSIF_USBSERIAL=y
+# CONFIG_UART0_SERIAL_CONSOLE is not set
+CONFIG_OTHER_SERIAL_CONSOLE=y
```
   构建后 `python3 tools/board.py run "uname -a" --port /dev/ttyACM0`；
   注意 USJ 口在**启动瞬态**会有多线程输出交错（本机实测），运行时正常。
3. 交付/演示仍保持 UART0 console（本轮诊断结束后已恢复并复验）。
