## 一、一句话介绍

**桌伴（DeskMate）** 是一块基于 **openvela + ai_agent** 的 7 英寸智能视觉中控屏：
它**能看见、会主动、会执行**——摄像头看到你进门就主动问候，早上到点自动播报天气与日程，
说一句"记一下明早 9 点开会"就记下并到点提醒，设备异常主动告警。

与"问答式"语音助手不同，桌伴的重点是**主动**：它不需要你先开口。

### 4.2 核心工作量说明（技术难度主攻）

1. **完整移植**：把 NuttX 上游 esp32p4 平台移植进 openvela（板级 + 芯片层 + 驱动），
   以 **4 棵文件树 + 325 条 manifest `<copyfile>`** 交付，评审 `repo sync` 即得完整工作树，**无任何部署步骤**。
2. **代码空间硬限制突破（本项目最硬的一战）**：
   - SIMPLE_BOOT 模式下代码只能跑在 512KB SRAM 窗口内，实测占用 460KB+，仅余几十 KB；
   - 证据链证明窗口**不可扩容**（ROM 保留区 + ROM 锁定 PMP + XIP-from-PSRAM 为死代码）；
   - **解法**：切 **MCUboot 二级引导**，text+rodata（约 400KB）迁入 16MB flash 以 XIP 执行
     → SRAM 静态占用 **460KB → 120.3KB**（9/17 干净树复测）；
   - 为此移植 MCUboot 的 esp32p4 端口（上游无此板支持），修 ABI/工具链/头文件五类障碍
     （固化为幂等补丁），并自研两个工具让 NuttX 应用能被 MCUboot 加载
     （`mcuboot_mkloadhdr.py`、`mcuboot_p4_loader_patch.py`：映射 IROM + 使能 L1 cache 总线）。
3. **空间释放后恢复被裁剪的 AI 能力**：`web_search`、`llm_vision`/`tool_vision`、`cron` 从弱桩变为真实实现。
4. **外设逐项落地**：MIPI-DSI 7" 屏（EK79007）+ GT911 触摸 + LVGL 触控 UI、摄像头（SC2336/CSI/DW-GDMA）、
   DNS/DHCP 全自动联网、PSRAM 33.9MB 可用。

### 4.3 AI 开发方式

- **全流程 AI Coding**：从移植到驱动调试到文档，均由 AI 辅助完成；对话日志导出至 `logs/`

  DSH 会话经 `tools/engineering/dsh_session_to_contest_log.py` 转换为赛事日志格式）。

  同时 manifest 登记自有技能仓 `ez-xu/openvela-skills` → 工作区 `.agents/`（19 个 skills，
  `repo sync` 自动拉取，评审可直接阅读）。

## 六、中间遇到哪些问题，怎么解决（诚实记录）

> 完整过程见 `docs/06_开发过程复盘与改进清单.md`（27 节）与 `docs/踩坑笔记_01~07`。
> 以下按"影响面从大到小"列出，**已解决**与**未解决**分开。

### 6.1 已修复的主要缺陷（按影响面排序）

#### A. 平台级驱动/内核缺陷（影响面大于本项目，9 个）

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | **ai_agent 一启动"整机失聪"**（9/17 定位，内核级） | `riscv_doirq()` 的早期引导保护 `if (g_running_task == NULL) return regs;` 把**所有** trap 吞掉，而 `up_exit()` 故意先置 NULL 再发 `ECALL(SYS_restore_context)` → 该 ECALL 被无限重发（实测 ≈49 万次/秒 ECALL 风暴），CPU 100% 卡 trap，节拍中断/网络/串口全哑；**与 agent 无关：子 shell 敲 `exit` 同样死机** | 保护只对硬件中断生效（`irq > RISCV_MAX_EXCEPTION`）；修复后 agent 启动完成 ping 5/6、TCP 28789 通（`logs/verify-2026-09-17/wedge_fix.txt`） |
| 2 | 板级 Kconfig 静默失效（9/11） | 残留 0 字节 `boards/dummy/Kconfig` 使板级 Kconfig 永不生效（影响所有 esp32p4 板） | 修正/清理 Kconfig；该板所有板级选项恢复生效 |
| 3 | UART 控制台输出丢字节（9/11） | `esp_lowputc_send_byte()` 未等 TX FIFO 空间即写，突发静默丢字节（实测吞 ~1.5KB 启动日志；影响所有 espressif 串口控制台） | 等待 FIFO 空间 + `CONFIG_UART0_TXBUFSIZE` 提到 2048 |
| 4 | GT911 触摸驱动缺 `ioctl`（9/11） | `gt9xx.c` 的 `ioctl = NULL` → `TSIOC_GETMAXPOINTS` 返回 -ENOTTY，LVGL 拒绝打开 `/dev/input0` | 补 ioctl；后另发现产品 ID 校验吃掉 NUL 补齐字节（9/14）一并修复 |
| 5 | V4L2 上层拒绝裸 Bayer（9/11） | `v4l2_cap.c` 格式白名单无裸 Bayer → 无 ISP 的 CSI 传感器无法出流 | 显式声明 `g_sc2336_frmintervals[]`（30fps）并放行 RAW10 |
| 6 | MIPI-DSI 显示不亮（9/14） | `mipi_dsi_device.c` 8 处 `struct mipi_dsi_msg` 未零初始化 → 一条 DCS **写**被当成**读**发 → 等 BTA 应答超时 `-110` | 零初始化结构体；真机 `/dev/fb0 ready 1024x600 RGB565` |
| 7 | 任务退出 → 整机死机（后台命令 `cmd &` 必崩） | openvela 自身引入的回归（与 LVGL 无关） | 定位为上游回归并绕过（`docs/06` §23.10） |
| 8 | 摄像头 DW-GDMA 中断（9/15） | DSI 非共享独占把最后一条空闲 CLIC 线打上 NONSHARED → CSI 摄像头共享申请被拒（初始化 -5） | DSI 改共享注册（`ESP_INTR_FLAG_SHARED`）；真机 `Camera registered on /dev/video0` |
| 9 | `up_enable_irq()` 从不置位 CLIC IE（9/15） | `esp_setup_irq_intrstatus()` 总带 `INTRDISABLED` → `esp_intr_alloc` 置的 IE 又被清掉；`esp_intr_enable()` 只重连路由矩阵不写 IE | `up_enable_irq()` 补 `esp_intr_enable_source(真实 intno)`（影响面很大） |

#### B. 配置与工具链路问题（本项目侧，已解决）

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 10 | DNS 不可用（9/14） | 三个叠加：`CONFIG_NET_UDP` 未开、`CONFIG_NETINIT_DHCPC` 未开（与 `NETUTILS_DHCPC` 区分）、netinit 不等链路就发 DHCP | 全开 + 等待链路；现 DHCP 全自动，`nslookup → 202.69.4.22`；MTU 576→1500 |
| 11 | 烧录/引导链路 | 旧单镜像流程失效；MCUboot 拒收 TCM 目标；引导器重建后启动循环 | 两镜像烧录固化 `usb_stable.sh`；TCM 校验放行改由 patch 脚本承载（`2d2e99d`） |

### 6.2 关键工程难题（已解决）

| 难题 | 根因 | 解法 |
|---|---|---|
| **PSRAM 写 hang**（9/3–9/4，40+ 项排除） | bootloader PMP 时序缺陷（非硬件 bug）：引导器在 PSRAM 初始化前锁了 PMP | 跳过 bootloader 的 PMP 设置（`#if 0` 固化）；OpenOCD 决定性诊断；PSRAM 32MB 完全可用 |

| **API key 泄露事件**（9/7 发现、9/10 处置） | key 编在 `agent_config.h` 随代码提交 | 移除内嵌 key → `agent_secrets.h`（.gitignore 忽略）注入机制；历史重写；**后续日志导出又发现 4 处残留，已脱敏（`5663907`）**；⚠️ 平台侧轮换仍未完成（见 §六.4） |

| **LLM 端到端不通**（9/17 晚，三个独立缺陷） | ① 端点不对：key 属于 Token Plan 网关（`token-plan-cn.xiaomimimo.com`，默认 `api.xiaomimimo.com` 401）；② `CONFIG_NET_TCPBACKLOG` 未开 → 连接被 RST；③ 计时用了会被 TLS 改写的墙上时钟 → 好答案被当超时丢掉 | 三处全修 → **真机端到端对话成功**（`agent_llm_ws.txt`） |

### 6.3 开发方法论上的坑（如实记录）

- **先做对照组**：多次被"现象"带偏（如先被"没喂狗"带偏、先判"LCD 模组硬件坏"——真因是驱动缺陷）。
- **halt 伪迹**：JTAG halt 期间读寄存器会得到"假现场"；帧缓冲导出会冻结画面。
- **症状 ≠ 病因**："整机失聪"先怀疑 agent 逻辑，判别实验（子 shell `exit` 同样死机）才转向内核。
- **生成文件陷阱**：`esp_loader.c` 是构建时生成的文件，手改会被覆盖 → 修复必须落在生成器（patch 脚本）。
- 以上已固化为 `docs/06` §26.8 的方法学教训。
