# WiFi（板载 C6 / SDIO + ESP-Hosted）交付说明

> 2026-10-28 · 这份文档把 WiFi 这一项的**实际状态、证据、与待办**说清楚。
> 详细排查过程见 `docs/08_WiFi_SDIO实现.md` 附录 A–S。

## 二、两个关键 bug（都是真实的，都影响过判断）

### 1. SDIO PLL 从未被 PMU 上电 → CIU 一条命令都不执行

`sdmmc_ll_enable_sdio_pll()` 在 IDF 里是给 PLL **上电**（PMU 寄存器），
不是写时钟门控。本驱动从未调用它，于是 SDIO 时钟源一直处于掉电状态，
CIU 从不执行任何命令 —— 表现为"每个寄存器读回都正确，却什么都不动"。

补上后，CIU 立刻开始执行、时钟第一次出现在焊盘上。

### 2. `waitresponse()` 忽略命令字里的响应标志 → CMD5 从未发出

NuttX 的 `sdio_sendcmdpoll()` 对**每条**命令都调用 `SDIO_WAITRESPONSE`。
本驱动的 `waitresponse()` 开头是 `UNUSED(cmd)`，不看响应标志，
于是**无响应的 CMD0 也去等响应**，超时返回 `-ETIMEDOUT`，
`sdio_probe()` 随即退出 —— **CMD5 从来没被发出去过**。

此前几十轮观测到的 `-110` 都不是"等不到从机回应"，而是 CMD0 在等一个
它本就不该等的响应。修复后线上立刻同时出现 CRC 合法的 CMD0 与 CMD5。

## 三、卡在哪里

**从机（C6）对合法的 CMD0/CMD5 一条响应也没有。**

已排除（全部有仪器读数或实验支撑）：

- 时钟频率、连续性、初始化时钟数量
- 引脚、slot、GPIO 矩阵路由、SDMMC 信号索引
- 时钟源（PLL_F160M 与 SDIO_PLL）、低速/高速路径
- 等待时间（1000 ms 与 2500 ms）
- **时钟边沿对齐：主机驱动/采样两个相位的四种组合全部试过**
- C6 是否被复位（实测被复位，启动日志零错误）

用户已确认**整条链路的每一根线同时接到 P4、C6 和逻辑分析仪**，
因此分析仪在 P4 侧看到的波形就是 C6 引脚上的波形 ——
**C6 确实收到了合法的命令，却不回应。**

## 四、怎么继续（两步，都需要人工/硬件）

### 步骤 1（需按键，约 1 分钟）

C6 固件已用 esp-hosted-mcu **v3.0.10** 重新构建，配置与原固件逐项一致，
四个镜像在 `tools/build_flash/c6_hosted_new/`。

这颗 CP2102 的 DTR/RTS 没有接到 C6 的 EN/BOOT，且 **P4 也拿不到 C6 的 BOOT**
（原理图：`C6_EN` 接 GPIO54，`C6_IO9`(BOOT) 未连任何 P4 GPIO）。所以必须：

> 按住板上 **BOOT**（GPIO9）→ 按一下 **RESET** → 松开 **BOOT**

然后运行：

```sh
tools/build_flash/c6_hosted_new/flash.sh
```

若这份"干净重建 + 配置核对过"的固件仍不应答，即可**排除 C6 固件内容**这一项。

### 步骤 2（需万用表）

量 P4 ↔ C6 六根线的通断：

| P4 | C6 |
|---|---|
| GPIO18 (CLK) | IO19 |
| GPIO19 (CMD) | IO18 |
| GPIO14 (D0) | IO21 |
| GPIO15 (D1) | IO22 |
| GPIO16 (D2) | IO23 |
| GPIO17 (D3) | IO20 |

不通即确定是硬件，与软件无关。

## 五、诚实的结论

- **主机侧：完成，且有仪器级证据。** 两个关键 bug 的修复是真实进展 ——
  在此之前 CIU 根本不执行命令、CMD5 根本不发。
- **从机侧：未通。** 到本说明为止，主机侧可调项已穷举，剩余疑点在 C6
  固件或硬件，而这两者都需要上述人工步骤才能推进。
- **协议层与 WiFi netdev：未开始**，阻塞于枚举。

按"能真机复现"的标准，本任务当前可交付的是 **ES8311 音频与语言播放**
（见 `docs/07_ES8311音频驱动实现.md`、`docs/STATUS.md`）；WiFi 部分交付的是
主机侧驱动与完整的排查记录。
