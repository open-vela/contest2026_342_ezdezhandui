# 驱动层优化（相机/触摸/显示）——前后对比与判据

> 数据来源：真机 ESP32-P4X-C5-Function-EV-Board，JTAG 单次读取 + 自检窗口指标。
> 完整叙述见 `docs/30_实现/应用层_DeskMate_UI.md` §18。

## 1. 触摸（I2C0 共享总线）

| 指标 | 优化前 | 优化后 | 手段 |
|---|---|---|---|
| 触摸读单次最坏 | **1539 ms** | **419 ms** | `gt9xx_read()` 的 `devlock` 改 `nxmutex_trylock`（`docs §18.2`） |
| 触摸 I2C 读最坏 | 419 ms | **310 ms** | I2C 传输处加 60ms 有界等待（两份 `esp_i2c.c` 都改，`§18.13`） |
| （同一指标的波动范围） | — | **70 ~ 800 ms** | 随 I2C0 负载波动；最坏仍可达 800ms（`§18.14`） |

**结论**：三层缓解都落地了，但"拿到总线后的那次传输本身"最长 800ms，
属**驱动/硬件层**（I2C0 由触摸 + 相机 SCCB + ES8311 共用；GT911 的 INT 未引出，只能轮询）。

## 2. 显示刷写（P3c 评估）

真机 80 秒相机页窗口：

| 指标 | 值 | 说明 |
|---|---|---|
| `flush_calls` | 579（≈7/s） | 每脏区一次，**不是整帧刷** |
| `flush_px` | 53,110,562（均 92 kpx/次） | 脏区面积合理 |
| `flush_max_px` | 614,400（= 全屏 1280×480） | 仅页面切换/整屏失效时出现 |
| `flush_us_max` | 10 ms | 刷写不是瓶颈 |

**结论**：现有"脏区刷写"策略已正确，**无需**改成整帧或双缓冲直接扫描。

## 5. 屏幕卡死与触摸解耦（2026-11-04）

### 5.1 显示：卡死根因与三层解法

| 配置（同页 25~30s，JTAG 计数） | 显示提交 `g_disp_commits` | 相机 fps |
|---|---|---|
| ISP **连续流**（卡死那版） | **3.2/s** ❌ | 13.6 |
| RAW8 连续（默认） | 5.6 ~ 7.7/s | 13.8 |
| **ISP + 让路（12 帧 / 80ms）** | **11.4/s** ✅ | 13.7 |

- 流量差：ISP 出 RGB565 每帧 **1,843,200 B** vs RAW8 **921,600 B**（翻倍）；
- 看门狗人为停摆测试：`stalls=6` / `reinits=3`；健康运行 `stalls=0`（无误报）；
- 重建入口直接调用：`display: reinit OK`，之后提交继续增长（116 次/15s）。

### 5.2 触摸：把读搬出 UI 线程

| 指标 | 改前 | 改后 |
|---|---|---|
| `ui:responsive` 的 `max_busy` | 130 / 180 / 250 / **1540 ms** | **20 ~ 30 ms** |
| 触摸判据 / 完整自检 | PASS / 29/29 | **PASS / 29/29** |

触摸读耗时构成（30s 窗口）：读总耗时 6560ms 中 **I2C 传输占 5520ms（84%）**，
327 次、平均 16.9ms、单次最大 570ms；**开相机比不开相机更慢**（16.9 vs 10.2ms/次）。
两个否证：tick 10ms→1ms 无效；I2C 超时 500ms→50ms 后**单次最大仍 501ms**
（⇒ 那 500ms 是抢占墙钟，不是超时）。详见 `docs/50_排障经验/10_触摸停顿与UI解耦.md`。
