# 10_触摸 I2C 停顿与"把读搬出 UI 线程"

> 写于 2026-11-04。**触摸一按 UI 就顿一下 / `ui:responsive` 出现几百毫秒尖峰**时读这篇。

## 一句话结论

**触摸读原本跑在 LVGL 的输入定时器里（也就是 UI 线程里），而这条 I2C0 与相机 SCCB、
ES8311 共用，单次读的墙钟最坏可达 230~800ms ⇒ UI 跟着卡。
解法不是去优化 I2C，而是"换个人去等"：把读搬到独立线程，UI 只读最新样本。**

## 根因链（每一环都有实测）

1. `lv_nuttx_init()` 收到 `input_path` 就会建一个**设备 indev**，它的
   `read(/dev/input0)` 由 LVGL 的输入定时器调用 —— 也就是在
   `lv_timer_handler()`（UI 线程）里执行。
2. 这条 I2C0 上不只触摸：**相机 SCCB、ES8311 共用**（板级事实）；
   GT911 的 **INT 引脚没有引到 SoC**，只能轮询（`esp32p4_touch_gt911.c` 注释写明）。
3. 实测触摸读墙钟：**1539ms**（改 `gt9xx` 的 `devlock` trylock 前）→ **419ms** → 310ms →
   **最坏 800ms**。`ui:responsive` 的 `max_busy` 随之在 130 / 180 / 250 / **1540 ms** 之间跳。

## 两个决定性否证（别再往这两个方向使劲）

| 试过 | 结果 | 结论 |
|---|---|---|
| 把 I2C 总线锁改成**有界等待**（60ms） | 单次最大 419 → 310ms，仍会很大 | 只压住"等锁"，压不住传输本身 |
| 把系统 tick 10ms → **1ms** | 平均 16.9 → 13.6ms，最大仍 ~500ms | 不是 tick 粒度 |
| 把 I2C 超时 500ms → **50ms** | **单次最大仍是 501ms** | **那 500ms 不是超时，是线程被抢占的墙钟** |
| 把 LVGL 输入读周期 30 → 50ms | 反而更差（撞上更长的停顿） | 读得少≠停顿少 |

⇒ **触摸读的墙钟 = 极短的总线时间 + 调度延迟（被抢占）**。

## 解法：把"等"移出 UI 线程

```c
/* dm_display.c：别把设备交给 LVGL（否则 read() 会回到 UI 定时器里） */
info.input_path = NULL;

/* dm_touch.c：独立低优先级线程轮询，UI 只读快照 */
fd = open(DM_INPUT_PATH, O_RDONLY | O_NONBLOCK);
for (;;) {
    poll(&pfd, 1, 50);                 /* 带超时 */
    read(fd, &sample, sizeof(sample)); /* 非阻塞 */
    /* 写进无锁 seq 快照：g_hw_x / g_hw_y / g_hw_pressed / g_hw_seq */
}
/* LVGL indev 回调：只读快照，零阻塞（注入优先，其次硬件样本） */
```

**实测效果**：

| 指标 | 改前 | 改后 |
|---|---|---|
| `ui:responsive` 的 `max_busy` | 130 / 180 / 250 / **1540 ms** | **20 ~ 30 ms** |
| 触摸判据（自检） | PASS | **PASS** |
| 完整自检 | 29/29 | **29/29** |

关键断言：**`g_dbg_touch_i2c_us_max` 依旧可以很大，但 UI 不受影响** ——
I2C 再慢也只影响"触摸样本的新鲜度"。

## 配套诊断量（JTAG 可读）

`g_dbg_touch_i2c_us(_max)`（读总耗时）、`g_dbg_touch_xfer_calls/_us/_us_max`
（**只算 `I2C_TRANSFER`**）、`g_dbg_touch_hw_reads/_us/_us_max`（轮询线程侧）。

> 计时器要放在**确定被链接**的文件里（这里是 `nuttx/drivers/input/gt9xx.c`）——
> 详见 [08_驱动层调优与多副本陷阱.md](08_驱动层调优与多副本陷阱.md)。

## 教训

- **别让 UI 线程碰慢设备**：只要回调在 `lv_timer_handler` 里，任何慢 I/O 都会变成整屏卡顿；
  正确做法是"生产者线程 + 最新样本快照"。
- **优化前先分清"谁在等"**：本次三个看似合理的优化方向（锁、tick、超时）全部无效，
  真正的答案是改变等待发生的位置。

## 附：改了之后"触摸没反应"怎么查（本项目的实战顺序）

1. **先分清是"屏幕冻住"还是"触摸坏"**：读驱动维护的 `g_disp_commits` 是否增长。
   冻住是相机抢带宽（见 [09_显示卡死复盘.md](09_显示卡死复盘.md)），不是触摸问题。
2. **看轮询线程的计数**：`g_dbg_touch_hw_reads / _ok / _err / _hits`。
   - `reads` 不涨 ⇒ 线程没起来；
   - `err` 涨 ⇒ read 被驱动拒（长度/缓冲不匹配，按 LVGL 做法用
     `ioctl(TSIOC_GETMAXPOINTS)` + `SIZEOF_TOUCH_SAMPLE_S(maxpoint)`）；
   - `ok` 涨但 `hits` 永远 0 ⇒ **没人按**或驱动没报按下 → 用 `--touch-wr x y`
     直接往 GT911 寄存器造一次按下，看 `hits` 是否增长（这会端到端验证整条链路）。
3. **`hits` 会涨但 UI 不响应** ⇒ 问题在坐标/控件层；注意 **按下帧可能只报一帧**
   （GT911 轮询型），要加**按下锁存**（本项目用 120ms），否则点击会丢。

# 追加（2026-11-06）：用逻辑分析仪定量，并推翻上文两个"重要"结论

> 上文写于 2026-11-04，当时只有串口和 JTAG。这一轮用 **PXView 逻辑分析仪
> （PX_Tool PX-Logic U2，32 通道，1 MS/s，通道 0 = ESP_I2C_SDA / 通道 1 =
> ESP_I2C_SCL）** 直接测总线，把"猜"换成了"量"。结论有三条是**推翻上文**的，
> 已就地标注。

## 一、上文说"I2C0 与相机 SCCB、ES8311 共用 ⇒ 抢总线" —— **实测不存在**

20 秒抓包，I²C 解码器（`0:i2c`，SCL=ch1，SDA=ch0）共 141 次完整读周期、
423 笔事务，线上**只有一个地址 0x14/0x15**（GT911，注意是**备用地址**，
不是 0x5d —— 与 JTAG 读到的 `g_gt911_addr = 0x14` 一致）。

| 探针 | 实测 |
|---|---|
| 0x30（SC2336 SCCB） | **0 次** |
| 0x18（ES8311） | **0 次** |
| DSI 相关事务 | **0 次**（DSI 控制走 DCS，根本不在这条 I²C 上） |
| 总线占用率 | **0.71 %** |

⇒ **稳态下总线上只有触摸在说话，相机/音频都不发周期事务。**
"共享总线争抢"不是触摸延迟的原因，从来不是。

## 二、上文说"墙钟 = 总线时间 + 调度延迟" —— 方向对，但比例远超预期

| 指标 | 实测（20 s，141 周期） |
|---|---|
| 单次读**纯总线时间** | p50 **0.988 ms** / max 1.148 ms |
| 单次读**端到端** | p50 17.7 / p90 94.8 / p99 199 / max **204.6 ms** |
| 读内部**三笔事务之间的间隙** | p50 0.80 / p90 55.1 / max **182.5 ms** |
| 慢读占比 | `>20 ms` 48 %，`>80 ms` 16 % |
| **有效采样率** | p50 间隔 **120 ms** = **7.1 Hz** |

⇒ **97 % 的时间不在总线上，而在"线程没被调度到"。** 三个叠加原因：

1. `dm_touch.c` 用 `poll(&pfd, 1, 50)`，而 `poll_notify()` **从未被调用过**
   （`gt9xx.c` 里 `work_queue` / `wd_start` 出现 0 次，那个 `poll_notify` 在
   永不触发的 ISR 里）→ 每次 poll 都**必然睡满 50 ms**；
2. `CONFIG_USEC_PER_TICK=10000`（10 ms tick）→ `wd_start(MSEC2TICK(8))` 只能
   取到 1 个 tick，且每次重挂要对齐下一个 tick 边界 ⇒ **8 ms 的周期被量化成 20 ms**；
3. 应用层用 `g_hw_hold_until = now + 120 ms` 和 `g_cb_hold = 4` 两个常数去
   "猜"手指还在不在 —— 而 120 ms **比最坏的一次读（204 ms，JTC 计数器记到 710 ms）还短**，
   所以按下会丢、抬手还拖着。

## 三、改了什么（驱动 + 应用两侧）

**驱动侧（`nuttx/drivers/input/gt9xx.c`，改动最大）**

| 之前 | 之后 |
|---|---|
| 无事件源：`work_queue`/`wd_start` 0 次，`poll_notify` 永不触发 | `wd_start` 自挂链 + `work_queue(LPWORK)` worker，**每 8 ms 采一次样并 `poll_notify()`** |
| `read()` 里阻塞 `nxmutex_lock` + 3 笔 I²C（状态/坐标/清状态） | `read()` **只读快照**（`nxmutex_trylock`，失败返 `-EAGAIN`），**完全不碰总线** |
| 3 笔事务 | **1 笔 8 字节读**（0x814E..0x8155 连读）+ 1 笔清状态 |
| 只会产 `TOUCH_DOWN`；重复坐标被 `memset` 成 `npoints=0`；抬手靠下一次读伪造一次 UP | **DOWN → MOVE（按住就一直报）→ 恰好一次 UP** |
| 无 | 延迟直方图 + 锁等待分开计（`gt9xx_stats()`） |

> ⚠️ 合并读时**坐标偏移必须从 1 改到 2**：GT9xx 从 0x814E 顺序排布是
> `[0x814E]=status, [0x814F]=track_id, [0x8150..0x8153]=x/y`。按老的
> `touch[0..3]` 去解 `buf[1..4]` 会解出"track_id + x 低字节"，看着像坐标但是错的。

**应用侧（`dm_touch.c`）**

- 删掉 `g_hw_hold_until`（只写不读）和 `g_cb_hold`；
- `poll(&pfd, 1, -1)` → `poll(&pfd, 1, 200)`：200 ms **不是采样周期**，只是
  "多久回来看一次退出标志"，有事件时 `poll_notify` 会立刻唤醒；
- 按下判据从"只认 `TOUCH_DOWN`"改成 `(TOUCH_DOWN | TOUCH_MOVE)`；
- `read()` 返回 `npoints==0` 不再当"抬手"（那是"这一拍没有新事件"）；
- `-EAGAIN` 单独计数，**不算错误**（原来会被算进 `g_dbg_touch_hw_err`）。

## 四、改完之后的实测（同一套 PXView 方法复测）

| 指标 | 改造前 | 改造后 |
|---|---|---|
| **采样率** | **7.1 Hz** | **79.4 Hz**（三次复测 78.5/78.9/79.4；p50 9.0 ms，p90 9.0 ms） |
| 单次读端到端 p50 | 17.7 ms | **≈0**（read 不再做 I²C） |
| 单次事务耗时 | — | p50 < 2 ms（直方图 78 % 落在 <2 ms 桶） |
| 总线占用 | 0.71 % | 12.6 %（100 kHz 下余量仍充足） |
| 事务形状 | `Wdd / Rd / Wddd` ×3 | `Wdd / Rddddddd / Wddd`（一次读回 8 字节） |
| 事件语义 | 只有 DOWN | DOWN/MOVE/UP（`events` 计数随手指动作增长） |
| `ui:responsive` max_busy | **620 ms** | **34 ms** |
| 自检 | — | **28/28 PASS** |

**A/B 实测（同一场景）：`CONFIG_USEC_PER_TICK` 10 ms vs 1 ms**

| tick | ticks/5s（定时器） | xfers/5s（实际采样） | 采样率 |
|---|---|---|---|
| 10 ms | 251 | 179 | **35.2 Hz** |
| 1 ms | 557 | 394 | **79.4 Hz** |

⇒ 上文"改 tick 没收益"的结论**只在"读仍在 read() 里同步做 I²C"时成立**
（那时瓶颈是抢占，不是 tick 粒度）。把传输搬进 worker 之后，tick 粒度**就成了**
限制项 —— 现已把 `CONFIG_USEC_PER_TICK=1000` 写进板级 defconfig。

**A/B 实测：相机采集线程优先级**

| 优先级 | cam:fps | ui:responsive max_busy |
|---|---|---|
| 100（与 UI 同权，默认） | 4 fps | 70 ms |
| 90（低于 UI） | **2 fps** | **219 ms** |

⇒ 压住采集线程 **两边都变差**：它只是在 poll/mutex 上等更久，一旦拿到 CPU 仍要
一次性做完整帧转换，尖峰反而更大。**不要靠调优先级解决，要降低单帧转换成本。**

## 五、这一轮踩到的两个"看错地方"的坑（值得单独记）

1. **线程栈压小会让崩溃报在毫不相关的地方。**
   把相机采集线程栈设成 4096（默认 16384），症状是相机起来几十毫秒后
   `Load access fault`，`EPC` 落在 `lv_obj_get_screen`，`MTVAL` 是 `0x7d` 这种
   明显不是指针的小整数 —— 那是栈溢出冲掉相邻堆对象的典型指纹。
   **除非有栈水位证据，不要给工作线程压栈。**

2. **同一个 NSH 会话里跑两次 `deskmate` 必崩（已改为明确拒绝）。**
   `lv_deinit()` 会释放所有 LVGL 对象，但 `dm_ui.c` 的 `static lv_obj_t *g_*`
   和 5 个页面模块的 `static lv_obj_t *s_*` 都是我们自己的变量、不会清零。
   第二轮建页面时就会在已释放的对象上做 `lv_*` 调用，崩溃点是
   `lv_obj_get_screen`，`MTVAL` 是个明显不是指针的小整数（实测 0x7d / 0x3d）。

   只给 `dm_ui.c` 置 NULL **不够**（试过，仍崩）；要彻底修得把 5 个页面模块的
   static 指针也一起管理，而收益只在于"同一次开机里连跑两次"。当前做法是
   在 `deskmate_main()` 里用进程内静态标志**明确拒绝第二轮**并把原因打出来：

   ```
   nsh> deskmate
   [dm] deskmate 已在本进程里跑过一轮；LVGL 的静态对象指针无法安全复用。请复位后重跑…
   nsh>
   ```

   需要重跑时复位板子即可。**把"崩"换成"一句话说清楚"**，比留一个随机
   load fault 好得多 —— 这一条也是本轮唯一一个"用拒绝代替修复"的取舍。
