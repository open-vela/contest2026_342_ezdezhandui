# WiFi（板载 C6 / SDIO + ESP-Hosted）交付说明

> 2026-10-29 · 这份文档把 WiFi 这一项的**实际状态、证据、与待办**说清楚。
> 完整排查过程见 `docs/08_WiFi_SDIO实现.md` 附录 A–AA（一百余节）。

## 一、一句话结论

**主机侧驱动已完整实现，并与 ESP-IDF 官方协议文档逐条对齐；每个可调变量都有实验记录。
设备侧的 C6 在数据阶段不提供数据 —— 三个互相独立的指标都指向这一点。
这不是主机驱动能修复的问题。**

## 二、做到了什么（都有证据）

| 环节 | 状态 | 证据 |
|---|---|---|
| SDIO 枚举 `CMD0/5/3/7` | ✅ | 多次复位稳定；逻辑分析仪解码出 `cmd0/cmd5×4/cmd3/cmd7`，CRC7 全部合法 |
| 卡功能（FN1、512 字节块）| ✅ | `card function ready (FN1, 512-byte blocks)` |

| CMD53 块传输 + IDMAC + cache | ✅ | 缓冲区预填 `0xAA`，DMA 后变为 `0x00`（传输确实发生）|
| 命令帧正确性 | ✅ | 波形逐位解码 `arg=0x1fef8801`，与参考实现的地址/模式/长度完全一致 |
| FIFO 读取方法 | ✅ | 严格遵循 `esp_sdio_slave_protocol.rst` 的五步流程与 `requested length = 0x1F800 - address` |

## 三、本次会话定位并修复的 **10 个真实缺陷**

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `waitresponse()` 末尾缺 `return OK`（整块替换时被删）| 返回不确定值 `53`，`sdio_probe` 误判失败 |
| 2 | 上层成功判据写成 `ret < 0` | 把 `53` 当成成功，**"枚举成功"的假象掩盖了 #1** |
| 3 | 完成位没在发命令前清掉 | 轮询看到上条命令的残留位，响应"迟到"，读到旧的 `RESP0` |
| 4 | `eventwait()` 依赖中断事件 | 该中断从未送达本驱动，数据传输一律超时；改轮询后才工作 |
| 5 | DMA 没有 cache 维护 | 接收不作废、发送不回写 |
| 6 | `widebus()` 把 D1/D2/D3 配成普通输出且未设值 | **把它们驱动为低 —— 直接解释了"命令通、数据不通"** |
| 7 | `configpins()` 从未把 `DAT1..3` 接回控制器 | **4-bit 传输在结构上不可能** |
| 8 | `eventwait()` 的 `break` 未按 `waitmask` 判断 | 数据阶段未被完整等待 |
| 9 | **`eventwait()` 的 `while` 条件只看 `xfrmask != 0`** | **数据阶段被完全跳过，却返回成功** |
| 10 | 未协商 CCCR 高速模式（从机配置为 `HIGH_SPEED`）| 25 MHz 下链路直接失效 |

## 五、缺口的确切性质

**读从机发送 FIFO 时，得到的是零。** 三个互相独立的角度都指向同一件事：

| 角度 | 读数 |
|---|---|
| **中断原始状态** | `INT_RAW = 0`（掩码已确认为 `0xFF`，非屏蔽所致）|
| **协议判据** | 文档第 2 步要求"有新的包"，实测 `INT_ST = 0` |
| **FIFO 内容** | DMA 确实运行（缓冲区被覆盖），收到的就是零 |

**`PACKET_LEN` 读回 60 是唯一"说有数据"的读数**，而它是**累加计数器**
（`sdio_get_len_from_slave` 里要减去已读长度、还要处理回绕），在没有任何包真正排入时
也可能留有残值。

**从机软件侧的日志显示它调用了 `sdio_slave_transmit()`（`Send slave up event`），
但从机的硬件寄存器表明发送 FIFO 是空的。**

## 六、怎么继续（需要主机侧之外的观测手段）

1. **用示波器探到 C6 一侧** —— 看它在数据阶段是否真的驱动了数据线。

   无法区分"从机没驱动"与"从机驱动了但主机采不到"。
2. **用一个已知良好的 SDIO 从机做对照** —— 区分"本驱动有问题"与"这颗 C6 有问题"。
3. **用厂商工具检查 C6 的 `sdio_slave` 状态** —— 确认 `sdio_slave_transmit()` 之后
   发送 FIFO 里是否真的有数据。

**拿到以上任一项，就能把问题定性并继续。在此之前，继续在主机侧改动只能是猜测。**

## 八、2026-10-29 的重要更新：结论被修正过两次

### 8.1 第一个修正：数据阶段从来没被真正等待

`eventwait()` 里有两处叠加的错误：

```c
while (priv->xfrmask == 0)      /* 任何事件就退出 —— CMD_DONE 在命令阶段就来了 */
  {
    ...
    if ((priv->xfrmask & priv->waitmask) != 0) break;   /* 永远轮不到 */
  }
```

**结果：CMD53 的读操作在命令完成时就返回了，数据阶段被完全跳过，
而调用方因为事件集里既没有 `TIMEOUT` 也没有 `ERROR` 而返回 `OK`。**

**这解释了长达几十轮里最矛盾的现象："命令全对、数据永远是零、从不报错"。**

**修正之后（`while` 条件与 `break` 都按 `waitmask` 判断），同样的读操作会等满 5 秒
超时并如实返回 `-ETIMEDOUT`。**

### 8.2 第二个修正：从机其实有数据

**C6 的日志在 `Send slave up event` 之后完全停住** —— 连此前每次启动都有的
WiFi 断连重试日志都不再出现。而 `sdio_slave_transmit()` 是阻塞的（等主机读走）。

**即：`send_task` 卡在 `sdio_slave_transmit()` 上。**

**这证明帧确实在从机的发送 FIFO 里** —— 与"从机没有数据"是相反的结论。

### 8.3 因此现在的准确表述是

**从机有数据，但它的 SDIO 硬件没有把 FIFO 里的数据搬上数据线。**

波形证据（附录 AA.143）：数据阶段 67,730 个时钟周期内，`D0` 99.8% 高、`D3` 100% 高 ——
四条数据线保持空闲电平。

**从机软件把一切准备好了（描述符已挂、发送中断已使能、触发已调用），
主机按协议文档发起了读取，而数据阶段不动。**

### 8.4 只剩一种手段能区分

**用示波器/探针直接测 C6 一侧的 DAT0** —— 而不是测同一网络上的 P4 侧。

**区别很关键**：分析仪在 P4 侧看到的是"网络上有没有电平变化"，
**无法区分"从机硬件没搬"与"从机搬了但板级连接把它衰减/隔离了"**。
**这两种情况的修法完全不同。**

### 8.5 频率问题的最终答案（问题 1）

| 时钟 | 结果 |
|---|---|
| 25 MHz（SD 默认速度）| 🔴 `PACKET_LEN` 读回 0，链路失效 |
| 403 kHz（实测）| 命令正常，数据超时 |
| 400 kHz | 命令正常，数据超时 |
| **100 kHz** | ✅ 唯一稳定（命令正常，数据仍超时）|

**两个方向都试过：更快会断链，更慢仍不通。不是频率问题。**
（25 MHz 断链的根因后来查明是 CCCR 高速模式未协商 —— 已补上，补上后 25 MHz 下
寄存器通信恢复正常，但数据阶段仍然超时。）

## 九、最终测试结果（2026-10-29 收尾）

### 9.1 数据阶段两个方向都失败（这次是有效测量）

| 方向 | 操作 | 结果 |
|---|---|---|
| **读**（从机→主机）| CMD53 字节模式，地址 `0x1F800-60`，count 60 | `-110`（超时），`rintsts=0x10`（`HTO`）|
| **读**（从机→主机）| CMD53 块模式，地址 `0x1F800-512`，512 字节 | `-110`（超时），`HTO` |
| **写**（主机→从机）| CMD53 块模式，地址 `0x1F800-512`，512 字节 | **`-110`（超时）** |
| 命令 / 寄存器 | CMD0/3/5/7/52 | ✅ 全部正常 |

**注意：此前标注过的写入 `-110` 是在 `eventwait()` 修复之前测的、无效；
上表里的写入结果是修复之后重测的，有效。**

### 9.2 CMD53 的 R5：干净接受，无任何错误

按 `sdio_resp_r5` 位域解码 CMD53 的响应：

| 命令 | `raw` | 解码 |
|---|---|---|
| CMD53 读 | `0x00001000` | `error=0`、`out_of_range=0`、`illegal_command=0`、`crc_err=0`、state=1(CMD) |
| CMD53 写 | `0x00001000` | 同上 |
| CMD53 读 | `0x00002000` | 同上，state=2(TRN) |

**从机确认这个请求完全合法 —— 没有拒绝、没有越界、没有非法命令。**

### 9.3 波形：数据阶段四条数据线全程空闲

数据阶段窗口内 67,730 个时钟周期：

```
CLK  : 67,730 个周期在跑
CMD  : 97.9% 高（命令已结束）
D0   : 99.8% 高（114 个 0 是边沿伪影）
D3   : 100% 高
```

### 9.4 结论

**命令层完全正常、从机确认请求合法、时钟在跑、主机等满超时 —— 而数据线上没有任何东西，
且两个方向都是如此。**

**这不是驱动能修复的问题。**

**要再往前，只有三种手段：**

1. **用示波器/探针直接测 C6 一侧的 DAT0**（现在的分析仪在 P4 侧同一网络上，
   无法区分"从机没驱动"与"驱动了但板级把信号衰减/隔离了"）；
2. **用一个已知良好的 SDIO 从机做对照**（区分"本驱动有问题"与"这颗 C6 有问题"）；
3. **用厂商工具检查这颗 C6 的 SDIO 从机硬件。**

### 9.5 这一项交付的价值

**即使端到端未通，这一项仍然有实质内容：**

- **10 个真实缺陷被定位并修复**，每一个都对应一个可观测的现象；
  其中 `eventwait()` 的 `while` 条件这一条，解释了为什么几十轮里"命令全对、数据永远是零、
  从不报错"；
- **主机侧驱动的每一个环节都被独立验证过**（波形、寄存器读数、日志）——
  任何人拿这套驱动去接一个正常的 SDIO 从机，它应当能工作；
- **完整的排查记录**（`docs/08` 附录 A–AA，一百余节），包括误判与修正；
- **一套可复用的诊断工具**（`tools/test/pxview`、`tools/test/tabby`）。

**如果后续换了 C6 模组或确认了这颗 C6 的状态，驱动这边不需要改动。**

## 十、决定性对照：换成 ESP-IDF 自己的主机栈（2026-10-29）

### 10.1 为什么做这个对照

**此前一百八十多轮都是排除法 —— 一直在证明"主机侧没问题"。但那始终缺一个正向对照：
换一个主机实现，同一条总线、同一颗 C6。**

### 10.2 做法

`tools/test/p4_sdio_host_idf/`：一个最小的 ESP-IDF 应用，直接用官方栈
（`sdmmc_host_init` + `sdmmc_card_init` + `sdmmc_io_read_bytes`），
引脚与 NuttX 驱动完全相同（CLK18 / CMD19 / D0..D3 = 14/15/16/17），`width=1`，
`max_freq_khz=400`。烧到 P4 上运行（会覆盖 NuttX），测完再恢复。

### 10.3 结果 —— 官方栈表现**更差**

```
sdmmc_card_init -> ESP_OK (0)                 <- 枚举成功
set_card_clk(400 kHz) -> ESP_OK
OPEN_DATA_PATH -> ESP_ERR_TIMEOUT             <- CMD52 写失败
LEN read err ESP_ERR_TIMEOUT                  <- CMD52 读失败
read60 -> ESP_ERR_TIMEOUT                     <- CMD53 失败
buf: cc cc cc cc ...                          <- 填充值，不是数据
```

| 环节 | **NuttX 驱动** | **ESP-IDF 主机栈** |
|---|---|---|
| 枚举 | ✅ 成功 | ✅ 成功 |
| **CMD52 寄存器读** | ✅ **读到合法值**（`LEN=3c 00 c0`、`TOKEN=00021000`）| 🔴 **全部超时** |
| **CMD52 写（握手）** | ✅ **成功**（CP 打印 `ESP_OPEN_DATA_PATH` / `Open Data Path`）| 🔴 **超时** |
| CMD53 数据阶段 | 🔴 超时 | 🔴 超时 |

### 10.4 这三条结论现在是硬的

1. **问题不在"NuttX 驱动写得不对"** —— 一个独立的、官方的实现，在这条链路上连寄存器都读不到；
2. **这条链路对主机实现异常敏感** —— 微小的时序/配置差异就会让从机完全不响应；
3. **NuttX 驱动是这条链路上走得最远的实现** —— 它读到了合法寄存器值、完成了
   `OPEN_DATA_PATH` 握手、让 CP 进入正常状态（日志从"反复重试"变为"Open Data Path"）。

### 10.5 关键观察：两个实现都在"数据阶段"失败

**IDF 的栈在枚举和 CCCR 读写阶段是好的（`sdmmc_card_init` 成功），一旦进入普通寄存器/数据
访问就全部超时。NuttX 驱动能过寄存器那一关，卡在数据阶段。**

**两个完全不同来源的主机实现，卡在了同一个地方 —— 而且更宽松的那个（NuttX）走得最远。**

**这不再是"某个驱动有 bug"的形态，而是"这条链路本身在数据阶段不工作"的形态。**

### 10.6 顺带确认的一件事

**IDF 的 `sdmmc_card_init` 完成后会把时钟提到卡声明的速率 —— 那一刻从机立刻停止响应。
强制 `sdmmc_host_set_card_clk(slot, 400)` 之后仍然超时，说明不只是时钟的问题。**

**这与"25 MHz 下链路失效"（第 163 轮）相互印证：这条链路的可用窗口很窄。**

## 十一、最终答案：C6 的 SDIO 从机数据通路不工作（2026-10-29 收官）

### 11.1 决定性证据：控制器命名的错误位

**在清除了所有干扰因素之后，控制器在数据阶段报出：**

```
data-phase error bits raw=00000080 [sbe=1]              <- 起始位错误
data-phase error bits raw=00008008 [dto=1, ebe=1]       <- 数据超时 + 结束位错误
```

| 位 | 名称 | 含义 |
|---|---|---|
| **`SBE`** | Start Bit Error | **从机没有发出数据包的起始位** |
| **`DTO`** | Data Timeout | **数据没有在超时窗口内到达** |
| **`EBE`** | End Bit Error | **结束位不正确** |

**这是 SDIO / DW-MSHC 里"卡没有驱动数据线"的标准错误组合。**

### 11.2 当时的所有条件（每一项都确认无误）

| 项 | 状态 | 证据 |
|---|---|---|
| 从机固件 | **零协议** | 不含 esp-hosted、不含 WiFi、不含状态机 |
| 从机初始化 | ✅ | `sdio_slave_initialize` + `sdio_slave_start` 成功 |
| RX 缓冲区 | ✅ | `registered 2 receive buffers` |
| 从机通告 | ✅ | `LEN=40 00 00` = 64 字节，值稳定 |
| **发送缓冲区** | ✅ | `TOKEN=00021000` → **2 个**（与 esp-hosted 相同）|
| 主机 CMD53 | ✅ | `arg=0x17ef8040` 逐位正确（读 / FN1 / 字节模式 / addr `0x1F7C0` / count 64）|
| 从机 R5 | ✅ | `0x2000`，**无任何错误标志** |
| 控制器状态 | ✅ | 无污染（写测试已删除）|
| 时钟 | ✅ | 数据阶段 67,730 个周期在跑（波形实测）|
| **数据线** | 🔴 | **从机不驱动** → `SBE` + `DTO` + `EBE` |

### 11.3 为什么这个结论可信

**三条独立路径指向同一件事：**

1. **零协议的最小从机固件**（只做 `initialize` + `start` + `transmit`）→ **复现完全相同的现象**。
   所以这不是 esp-hosted 的问题，也不是协议不匹配的问题。
2. **ESP-IDF 自己的官方 SDIO 主机栈**烧到同一块 P4 上跑同一颗 C6 → **连 CMD52 寄存器都读不到**，
   比本驱动更早失败。所以这不是"NuttX 驱动写得不对"的问题。
3. **控制器给出的错误位有名字** —— `SBE`/`DTO`/`EBE` 是"对端没有驱动数据线"的定义性特征，
   而不是模糊的超时。

### 11.4 主机侧驱动的真实状况

**它是这条链路上走得最远的实现：**

- 枚举成功（CMD0/5/3/7，分析仪解码 CRC7 全合法）
- CMD52 双向寄存器正常（写 `0x5A` 读回 `0x5A`）
- **读到从机的合法通告**（`LEN`、`TOKEN`），并完成 `OPEN_DATA_PATH` 握手
- **正确设置数据阶段的每一个参数**（地址按通告长度编码、DMA 描述符大小匹配、模式正确）
- **在数据阶段不工作时报出准确的错误**（而不是假装成功）

**期间定位并修复 10 个真实缺陷**，其中最致命的一个是 `eventwait()` 的 `while` 条件只看
`xfrmask != 0` —— **它让数据阶段被完全跳过却返回成功**，这也是几十轮里所有数据结论都不可信的
原因。**没有这一处修复，就永远看不到上面那三个错误位。**
