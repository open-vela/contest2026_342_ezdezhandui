# 13_用逻辑分析仪定位触摸延迟（方法学）

> 写于 2026-11-06。**"触摸不灵 / 采样不够"这类问题，串口日志和 JTAG 都只能
> 看到"结果"，看不到"总线上一共发生了几次真实采样"。** 本文记录怎么用
> PXView 逻辑分析仪把这件事量出来，以及这套方法能证伪哪些常见猜测。

## 为什么需要它

改驱动前我们手里只有两类证据：

- **应用侧计数**（`g_dbg_touch_hw_reads/_us_max`）—— 只能说明"读花了多久"；
- **JTAG 读全局变量** —— 只能看到"某一时刻的累计值"。

两者都**回答不了**这三个问题：

1. 驱动到底有没有按预期频率去采？（很多"驱动没跑起来"和"跑了但没被调度"
   在应用计数上长得一模一样）
2. 总线本身是不是瓶颈？
3. 上一条"读一次"在线上到底是几笔事务、每笔多长？

逻辑分析仪直接挂在 SDA/SCL 上，这三个问题都能定量回答。

## 接线与配置（本项目实测可用）

| 项 | 值 |
|---|---|
| 设备 | `PX_Tool PX-Logic U2 channel 32`（PXView，USB3） |
| 模式 | **Logic**（device `2`，`mode=0`） |
| 采样率 | **1 MS/s**（100 kHz I²C 下每 bit 10 点，足够解出边沿） |
| 通道 | **ch0 = ESP_I2C_SDA，ch1 = ESP_I2C_SCL**（其余通道全 0，说明总线上就这两根） |
| 解码器 | `0:i2c`，`channelMap = {scl: 1, sda: 0}` |
| 窗口 | 10~20 s（够统计出百分点） |

MCP 调用顺序：

```
start_capture({deviceId:'2', mode:0, sampleRate:1000000,
               channels:[0,1], durationMs:20000})
get_capture_status({})                       # state == 'completed'
add_analyzer({decoderId:'0:i2c', channelMap:{scl:1, sda:0}})
get_analyzer_results({analyzerId:'<返回的 id>', maxCount:800000})
```

**两个坑**：

- `add_analyzer` 必须传 `channelMap`，否则报 `Required channel(s) not mapped`；
- 每次 `start_capture` 之后**旧 analyzer 的 instance id 会失效**，要重新
  `add_analyzer` 拿新 id，并且**解码是异步的** —— 刚 add 完立刻 `get_analyzer_results`
  可能返回 0 条，等一下再问。

## 怎么把 annotations 还原成"一次 read"

GT9xx 的一次采样在线上是固定的三笔事务：

```
W[0x28] 81 4E            ← 写寄存器指针 0x814E（GT911 状态寄存器）
R[0x29] .. ..            ← 读状态 + 坐标（改造后一次读 8 字节）
W[0x28] 81 4E 00         ← 写 0 = 清状态
```

所以按 `Start`/`Repeat start` 切分事务、**每 3 笔归为一组 = 一次 `read()`**，
组的首笔 `start_sample` 就是采样时刻。相邻两组的时间差就是**真实采样间隔**。

```python
reads = [txs[i:i+3] for i in range(0, len(txs)-2, 3)]
start = [g[0][0]['start_sample'] for g in reads]
gap_ms = [(start[i+1]-start[i])/1000.0 for i in range(len(start)-1)]
```

`1000/mean(gap_ms)` 就是有效采样率 —— **这个数字和"配置的轮询周期"经常差 5~10 倍**，
差的那部分正是本文要抓的东西。

## 三个可判定的指标

| 指标 | 算法 | 它回答什么 |
|---|---|---|
| **采样率** | `1000 / mean(组首间隔)` | 驱动实际多久采一次（改造前 7.1 Hz，配置值是 50 ms） |
| **纯总线时间** | 组内每笔事务 `end-start` 求和 | 总线/控制器本身慢不慢（实测 p50 0.99 ms） |
| **事务间隙** | 组内相邻事务之间 `start_prev_end` | **线程有没有被抢占**（p90 55 ms、max 182 ms） |

第三项是关键：**纯总线 1 ms 而端到端 17.7 ms ⇒ 97 % 的时间不在总线上。**
这一条直接否掉了"优化 I²C 频率/超时/优先级"这一整类方案。

## 顺带可以证伪的猜测

| 猜测 | 抓包结果 |
|---|---|
| 和相机 SCCB(0x30) 抢总线 | 20 s 内 **0 次** 0x30 事务 |
| 和 ES8311(0x18) 抢总线 | **0 次** |
| 总线被跑满 | 占用率 **0.71 %** |
| DSI 也在这条 I²C 上 | **0 次** DSI 事务（DSI 控制走 DCS） |
| 地址是 0x5d | 线上只有 **0x14**（`0x28/0x29` 左移前） |

## 改造后的复测（同一方法）

| 指标 | 前 | 后 |
|---|---|---|
| 采样率 | 7.1 Hz | **78.5 Hz** |
| 单周期总线时间 | 0.99 ms | 1.50 ms |
| 事务间隙 p90 | 55 ms | 组内已无长间隙 |
| 总线占用 | 0.71 % | 11.8 % |
| 事务形状 | `Wdd / Rd / Wddd` | `Wdd / Rddddddd / Wddd` |

**判据**：改造必须同时满足"采样率上升"和"总线占用仍在安全区（< 30 %）"。
只升采样率把占用推到接近饱和，等于把延迟问题换了个位置。

## 结论

1. **先量采样率，再看单次耗时。** 采样率不够时，任何"单次读优化"都救不了手感。
2. **把总线时间和端到端时间分开量。** 两者差一个数量级以上时，问题在调度不在总线。
3. **占用率是安全阀。** 它低说明"还有余量可以提频"，它高说明"该降低单次成本"。
